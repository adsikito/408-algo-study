# 模块一：TFTP文件传输项目（P1-P35）

## 知识点1：TFTP协议概述（P1）【重点】

**①是什么**：TFTP（Trivial File Transfer Protocol，简单文件传输协议）是基于 **UDP** 的简单文件传输协议，默认端口 **69**。设计简单、易实现，常用于传输小文件或简单环境。仅支持五种报文：

| 报文 | 全称 | 作用 |
|------|------|------|
| RRQ | Read Request | 客户端请求读取（下载）文件 |
| WRQ | Write Request | 客户端请求写入（上传）文件 |
| DATA | Data | 数据传输报文 |
| ACK | Acknowledgement | 确认报文 |
| ERROR | Error | 错误报文 |

**生活化比喻**：TFTP 像"快递驿站的简版寄取件"——不核对身份证不签合同（无连接、无认证），只按单号（块编号）一件件交接，丢了就重发。

**②为什么**：为什么基于 UDP？——协议要"简单"，省掉 TCP 的连接管理和流量控制；那可靠性靠什么？——靠块编号 + ACK 确认 + 超时重传在应用层实现。

**错误码表**（课件 P2）：

| 错误码 | 含义 |
|--------|------|
| 0 | 未定义，差错错误信息 |
| 1 | File Not Found（文件未找到） |
| 2 | 访问违规 |
| 3 | 磁盘满或分配超出 |
| 4 | 非法操作 |
| 5 | 未知的传输 ID |
| 6 | 文件已存在 |
| 7 | 没有该用户 |

## 知识点2：TFTP通信流程（P1）【重点】

**①是什么**：分两阶段——

**请求阶段**：
1. 客户端向服务器 69 端口发送 RRQ 或 WRQ（含文件名和传输模式，通常 "netascii" 或 "octet"）；
2. 服务器响应：**分配一个新的 UDP 端口用于数据传输**，对 WRQ 回 ACK，对 RRQ 直接发 DATA。

**传输阶段**：
- RRQ（下载）：服务器发 DATA（含块编号+数据块），客户端收后回 ACK 确认；
- WRQ（上传）：客户端发 DATA，服务器回 ACK；
- **块编号**：16 位，从 1 开始递增，保证有序传输和确认；
- **结束标志**：DATA 数据部分 **小于 512 字节**表示传输结束。

**传输时序图**（下载）：

```
客户端                          服务器
  │── RRQ(文件名, octet) ──────→ │  (69端口)
  │                              │  分配新端口
  │←──── DATA #1 (≤512B) ─────── │  (新端口)
  │── ACK #1 ──────────────────→ │
  │←──── DATA #2 ─────────────── │
  │── ACK #2 ──────────────────→ │
  │   ...                        │
  │←── DATA #n (<512B 结束) ───── │
  │── ACK #n ──────────────────→ │
```

> 人话总结：请求走69，传输换端口，块号递增，短包收尾。

## 知识点4：TFTP服务器实现与CMake构建（P15-P22）【重点】

**①是什么**：TFTPServer 类绑定 69 端口监听请求；收到 RRQ 走 handleReadRequest（逐块读文件发 DATA、等 ACK），收到 WRQ 走 handleWriteRequest（回 ACK 后收 DATA 写文件）；每次传输使用新端口区分会话。

**服务器核心流程**：

```
TFTPServer::run() 循环：
  recvfrom(69端口) 收请求
    ├─ 解析操作码（2字节）
    ├─ 1=RRQ → handleReadRequest：开文件 → 发DATA#1 → 等ACK#1 → ... → 短包收尾
    ├─ 2=WRQ → handleWriteRequest：回ACK#0 → 收DATA → 写文件 → 回ACK → ... → 收到短包结束
    └─ 其他 → 发 ERROR 报文
```

**服务器主程序**（课件）：

```cpp
int main(int argc, const char* argv[]) {
    try {
        // 外部传入要共享的目录，否则用当前路径
        string root_dir = (argc > 1) ? argv[1] : ".";
        TFTPServer server(root_dir);
        server.run();
    } catch (const std::exception& e) {
        std::cerr << e.what() << '\n';
        return -1;
    }
    return 0;
}
```

**CMake 构建**（课件）：

```cmake
cmake_minimum_required(VERSION 2.8)
project(tftp_server)
set(CMAKE_CXX_STANDARD 11)          # C++11 标准
set(CMAKE_CXX_STANDARD_REQUIRED ON)
add_executable(${PROJECT_NAME}
    src/main.cpp
    src/tftp_server.cpp)
target_include_directories(${PROJECT_NAME}
    PRIVATE ${PROJECT_SOURCE_DIR}/header)   # 头文件路径
```

**④注意事项**：
- 服务器对每个传输会话要用独立端口/套接字，避免多客户端串包；
- 块编号要用网络字节序（htons/ntohs）传输；
- 文件读写失败要回 ERROR 报文（错误码 1 等），不能静默断开。

> 人话总结：服务器守 69 分请求，读写两条处理线，会话独立端口。

**用户表初始化**（两条建表语句一次执行 + 状态重置）：

```cpp
bool DatabaseManager::initializeUserDB() {
    lock_guard<mutex> lock(usr_mutex_);   // 互斥锁防多线程竞态
    const char* sql = "create table if not exists usr("
        "name text primary key,"          // 用户名（主键）
        "passwd int,"                     // 密码
        "stage int);"                     // 状态：0离线 1在线
        "create table if not exists history("
        "name text, word text, mean text, time text);";  // 查询历史
    if (!executeSQL(usr_db_, sql)) return false;
    sql = "update usr set stage=0;";      // 服务重启，全员置离线
    return executeSQL(usr_db_, sql);
}
```

**单词库初始化**（预编译查询判空 → 按需导入）：

```cpp
bool DatabaseManager::initializeDictDB() {
    lock_guard<mutex> lock(dict_mutex_);
    const char* sql = "create table if not exists dict(word text, mean text);";
    if (!executeSQL(dict_db_, sql)) return false;
    // 预编译查询记录数
    sql = "select count(*) from dict;";
    sqlite3_stmt* stmt;
    if (sqlite3_prepare_v2(dict_db_, sql, -1, &stmt, NULL) != SQLITE_OK) return false;
    bool need_import = false;
    if (sqlite3_step(stmt) == SQLITE_ROW)
        if (sqlite3_column_int(stmt, 0) == 0) need_import = true;  // 空表
    sqlite3_finalize(stmt);               // 释放预编译资源
    return need_import ? dictToDatabase() : true;   // 空则从 dict.txt 导入
}
// dictToDatabase：ifstream 打开 dict.txt 逐行读（单词+释义），插入 dict 表
```

**④注意事项**：
- 多线程访问 SQLite 必须加锁（课件用 `lock_guard<mutex>`）；
- `sqlite3_prepare_v2` 后必须配对 `sqlite3_finalize` 释放；
- 构造函数失败用异常上报，不要让对象"半初始化"继续运行。

> 人话总结：词典服务 = 线程管理客户端 + 双库管理数据，锁和异常一个不能少。

# 模块三：聊天室项目（P26-P38）

## 知识点7：聊天室服务器（chatServer）【重点】

**①是什么**：基于 TCP 的多客户端聊天室——服务器内置**线程池**处理连接，支持登录/聊天/退出三种消息，登录和退出全员广播，聊天消息转发给除自己外的所有人。

**消息协议**（客户端/服务器共用的 MSG 结构体）：

```cpp
#define N 128         // 消息缓冲区大小
#define LOGIN 1       // 登录
#define CHAT  2       // 聊天
#define QUIT  3       // 退出
struct MSG {
    int type;         // 消息类型
    char name[20];    // 客户端名称
    char text[N];     // 消息内容
    string serialize() const;              // 结构体 → 二进制串
    void deserialize(const string& data);  // 二进制串 → 结构体
};
```

**序列化实现走读**（课件核心手法：按内存布局拼接/拆解）：

```cpp
string serialize() const {
    string data;
    data.append(reinterpret_cast<const char*>(&type), sizeof(type)); // 类型4字节
    data.append(name, sizeof(name));   // 名字20字节（定长）
    data.append(text, sizeof(text));   // 正文128字节（定长）
    return data;                       // 共 152 字节定长协议
}
void deserialize(const string& data) {
    size_t offset = 0;
    memcpy(&type, data.c_str() + offset, sizeof(type)); offset += sizeof(type);
    memcpy(name, data.c_str() + offset, sizeof(name));  offset += sizeof(name);
    memcpy(text, data.c_str() + offset, sizeof(text));
}
```

**③服务器类结构与关键流程**：

```
chatServer
├── 成员：sfd、vector<Client> clients、client_mutex（保护客户端列表）
├── 线程池五件套：workers / tasks / task_mutex / task_cv / stop
└── 函数：构造（socket+SO_REUSEADDR+bind+listen+启动线程池）
         run（accept → addTask(handleClient)）
         handleClient（recv 循环 → 反序列化 → switch 分发）
         broadcast（序列化 → 遍历 clients 逐个 send，可排除某人）
```

**handleClient 分发逻辑**（课件走读）：

```cpp
while (true) {
    int recv_len = recv(client_fd, buffer, sizeof(buffer), 0);
    if (recv_len <= 0) {            // 客户端掉线：从列表移除并关闭
        // 遍历 clients 找到该 fd → erase → break
        close(client_fd); break;
    }
    msg.deserialize(string(buffer, recv_len));
    switch (ntohl(msg.type)) {      // 网络序转主机序
    case LOGIN:                     // 加锁 → 入列 → 广播"登录成功"
    case CHAT:                      // 加锁 → broadcast(msg, client_fd) 排除自己
    case QUIT:                      // 加锁 → 移除 → 广播"退出" → close
    }
}
```

**④注意事项**：

```cpp
// 错误示范：不加锁操作 clients（多个线程池线程同时增删 → 数据竞争崩溃）
// 正确：所有读写 clients 都套 unique_lock<mutex>(client_mutex)
// 错误示范：直接发结构体不做字节序转换
// 正确：type 用 htonl/ntohl 转换（跨平台兼容）
```

> 人话总结：服务器 = 线程池接单 + 加锁管名单 + 序列化广播。

## 知识点8：聊天室客户端（ChatClient）【重点】

**①是什么**：菜单驱动的 TCP 客户端——构造时连接服务器并自动发登录消息；主线程读终端发消息，**分支线程**非阻塞收服务器广播。

**③关键实现走读**：

```cpp
// 构造：创建套接字 → connect → 发 LOGIN
ChatClient::ChatClient(const char* ip, int port, const string& name)
    : name(name), running(true) {
    cfd = socket(AF_INET, SOCK_STREAM, 0);
    struct sockaddr_in sin;   // 填 family/port/ip
    connect(cfd, (struct sockaddr*)&sin, sizeof(sin));
    sendMsg(LOGIN);           // 连接成功即登录
}
// 析构：发 QUIT 再关闭
ChatClient::~ChatClient() { sendMsg(QUIT); close(cfd); }
// run：收线程 + 主线程发送
void ChatClient::run() {
    thread recvThread(&ChatClient::recvMsg, this);  // 分支线程专职接收
    string text;
    while (running) {
        getline(cin, text);
        if (text == "quit") { running = false; break; }
        sendMsg(CHAT, text);
    }
    recvThread.join();
}
// sendMsg：组 MSG（type 转网络序 + 拷贝名字/正文）→ 序列化 → send
// recvMsg：MSG_DONTWAIT 非阻塞收 → EAGAIN 则 sleep 100ms 重试
//          → 收到数据则反序列化打印 "name：text"
```

**CMake**（服务器/客户端通用模式）：


# 模块四：线程池与学生管理项目（P23-P46）

## 知识点9：线程池原理与实现（P23-P26）【重点】

**①是什么**（课件原文）：线程池是一种**预先创建一组线程**的机制——应用启动时线程就创建好、等待任务；有新任务时从池中分配空闲线程执行，而不是每个任务都新建线程。

**生活化比喻**：出租车公司——车（线程）提前备好停在车场，乘客（任务）来了直接派车，不用每个乘客现造一辆车；车用完回场等下一单。

**②为什么用线程池**（课件四点）：
1. **提高性能**：创建/销毁线程开销大，重用现有线程降低开销；
2. **控制并发量**：限制线程数量，防止 CPU 过载、内存不足；
3. **简化线程管理**：免手动管理生命周期，提供任务排队和调度；
4. **使用场景**：服务器应用（套接字/Web）、高性能计算、无依赖的异步任务并行。

**原理图**：

```
主线程 ──addTask()──→ ┌──────────────┐
                      │ tasks 任务队列 │ ← mutex 保护 + condition_variable 通知
                      └──────┬───────┘
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
          worker1        worker2        worker3   （vector<thread> workers）
        取任务→执行      取任务→执行     取任务→执行
```

**③完整实现走读**（课件代码，现代线程池的最小完整形态）：

```cpp
class threadPool {
private:
    vector<thread> workers;            // 工作线程容器
    queue<function<void()>> tasks;     // 任务队列
    mutex task_mutex;                  // 互斥锁
    condition_variable task_cv;        // 条件变量（通知有新任务）
    bool stop;                         // 停止标志
    void startThreadPool(size_t numThreads);
public:
    threadPool(int threadPoolSize);
    ~threadPool();
    void addTask(function<void()> task);
};

threadPool::threadPool(int threadPoolSize) : stop(false) {
    startThreadPool(threadPoolSize);   // 构造即启动
}

threadPool::~threadPool() {
    {   // 加锁置停止标志
        unique_lock<mutex> lock(task_mutex);
        stop = true;
    }
    task_cv.notify_all();              // 唤醒所有等待线程
    for (auto& worker : workers) worker.join();   // 逐一回收
}

void threadPool::addTask(function<void()> task) {
    {
        unique_lock<mutex> lock(task_mutex);
        tasks.push(task);              // 入队
    }
    task_cv.notify_one();              // 唤醒一个线程干活
}

void threadPool::startThreadPool(size_t numThreads) {
    for (int i = 0; i < numThreads; i++) {
        workers.emplace_back([this] {          // lambda 当线程体
            while (true) {
                function<void()> task;
                {
                    unique_lock<mutex> lock(task_mutex);
                    task_cv.wait(lock, [this] {
                        return stop || !tasks.empty();   // 停止或有活才醒
                    });
                    if (stop && tasks.empty()) return;   // 收工条件
                    task = move(tasks.front());          // 取任务
                    tasks.pop();
                }
                task();                                  // 锁外执行任务
            }
        });
    }
}
```

**主程序测试**（课件）：

```cpp
int main() {
    threadPool mypool(3);              // 3 个工作线程
    for (int i = 0; i < 20; i++)
        mypool.addTask([i]() {         // 20 个任务
            cout << "任务：" << i << " 正在执行，tid=" << this_thread::get_id() << endl;
            this_thread::sleep_for(chrono::milliseconds(500));
        });
    this_thread::sleep_for(chrono::seconds(5));   // 等任务完成
    return 0;   // main 结束 → mypool 析构 → stop=true → notify_all → join 回收
}
```

**④注意事项**：

```cpp
// 错误示范：在锁内执行 task()（任务耗时会卡住整个池）
// 正确：取出任务后离开锁的作用域再执行（课件写法）
// 错误示范：析构不 join（std::thread 析构时若 joinable 会 terminate）
// 正确：置 stop → notify_all → 逐个 join
```

> 人话总结：队列存任务，条件变量喊人，锁内取活锁外干。

# 第三阶段：补

## 难点重讲一：TFTP 的"新端口"机制（放慢节奏）

1. 服务器 69 端口是"接待前台"，只收最初的请求；
2. 收到请求后为这次传输开一个**新套接字/新端口**——这样多个客户端可以并行传输互不干扰；
3. 客户端必须从**第一次响应**里拿到对端地址（recvfrom 的 addr 参数），之后的 ACK/DATA 全发这个新地址；
4. 如果客户端继续往 69 发，服务器会当成新请求处理 → 传输错乱。

## 难点重讲二：序列化/反序列化与字节序（放慢节奏）

1. 网络传输的是字节流，结构体不能直接"整体发送"（含指针、内存对齐不可控）；
2. 课件采用**定长字段协议**：type(4) + name(20) + text(128) = 152 字节，按内存布局 memcpy 拼接；
3. 整型字段（type）跨平台必须转字节序：发送 `htonl`，接收 `ntohl`；
4. 收到数据后按同样偏移量拆解回结构体。定长协议简单但浪费（短消息也占 152 字节）——工业级会用变长协议（长度前缀 + 内容）。

## 常见陷阱专题（3 个最易错点）

### 陷阱1：线程池在锁内执行任务

- **错误写法**：`task()` 写在 `unique_lock` 作用域内
- **后果**：任务耗时时所有线程拿不到锁，池瘫痪
- **正确写法**：锁内只做取任务，锁外执行
- **如何记住**：锁内取活，锁外干活

### 陷阱2：聊天室客户端列表无锁并发

- **错误写法**：多个工作线程直接 `clients.push_back/erase`
- **后果**：vector 数据竞争，崩溃或逻辑错乱
- **正确写法**：所有读写套 `client_mutex`
- **如何记住**：共享名单必上锁

### 陷阱3：TFTP 传输阶段用错端口

- **错误写法**：ACK 继续发往 69 端口
- **后果**：服务器按新请求处理，传输中断
- **正确写法**：首次响应记住对端新地址，后续全用它
- **如何记住**：69 只接单，干活换端口

## 易错点速查卡

| 错误现象 | 错误原因 | 正确写法 | 后果 |
|----------|----------|----------|------|
| 线程池假死 | 锁内执行任务 | 锁外执行 | 池瘫痪 |
| thread 析构崩溃 | 未 join | 析构置 stop+notify+join | terminate |
| 聊天室崩溃 | clients 无锁 | 加 client_mutex | 数据竞争 |
| 消息类型错乱 | 未转字节序 | htonl/ntohl | 跨平台错误 |
| TFTP 传输出错 | ACK 发 69 端口 | 用响应中的新端口 | 传输中断 |
| sqlite 报错无提示 | 未用 errmsg | 打印并 `sqlite3_free` | 调试困难、泄漏 |
| SQL 注入 | sprintf 拼接用户输入 | 预编译+参数绑定 | 安全事故 |
| 条件变量虚假唤醒 | wait 不带谓词 | `wait(lock, 谓词)` | 空队列取任务 |

## 新手最常问的5个问题

**Q1：线程池为什么用条件变量而不是忙等？**
忙等（循环检查队列）空转烧 CPU；条件变量让线程睡到"有任务"才被唤醒，省资源。必须配互斥锁防竞态，且用带谓词的 wait 防虚假唤醒。

**Q2：聊天室为什么用定长消息结构？**
定长协议实现最简单——收满 152 字节就是一条完整消息，不用处理粘包/拆包。代价是带宽浪费，工业级用"长度前缀"变长协议。

**Q3：TFTP 和 FTP 有什么区别？**
TFTP 基于 UDP、无认证、极简（五种报文），适合小文件/嵌入式；FTP 基于 TCP、有账号权限、功能全，适合正式文件服务。

**Q4：SQLite 多线程使用要注意什么？**
SQLite 支持多线程模式，但同一连接并发写需要串行化——课件用 `mutex + lock_guard` 保护；不同连接（如用户库/词典库分开）可并行。

**Q5：这些项目为什么都写成"类 + run() 入口"？**
面向对象组织：构造函数做资源初始化（RAII）、析构释放、run 承载主循环——结构清晰、可测试、便于扩展（加新消息类型只需加 case）。

## 专项补充

**粘包/拆包问题（TCP 必知）**：TCP 是字节流，一次 send 的数据可能被拆成多次 recv，或多次 send 粘成一次——定长协议靠"收满固定长度"天然规避；变长协议必须自己按长度字段切分。聊天室 MSG 定长 152 字节正是这个原因。

```
    ├── 线程池：tasks/workers/mutex/cv/stop
    └── 学生管理：sprintf 拼 SQL + 回调打印
```

## 3条随身速记口诀

1. **TFTP 走 UDP，69 接单换端口；五种报文记清楚，短包一到就收尾。**
2. **线程池里五件宝：队列线程锁和条件，外加 stop 管收工；锁内取活锁外干。**
3. **聊天协议定长好，memcpy 拼拆错不了；整型记得转字节序，名单操作先上锁。**
