## 模块一：异常处理基础

### 知识点 1. 异常处理概述（P4-P6）【了解】

#### ① 是什么

**一句话定义**（P5 原文归纳）：C++ 中的异常处理是**处理运行时错误的过程**——即使在运行时出现错误后，也能保持应用程序的正常流转；异常是在运行时抛出的事件或对象，**所有异常都派生自 `std::exception` 类**，如果不处理它，程序就打印异常消息并终止。

**生活化比喻**：异常处理像飞机上的氧气面罩系统——巡航（正常流程）时你完全感觉不到它存在；一旦舱压异常（运行时错误），面罩自动落下，把乘客（程序控制权）从"窒息坠毁"（崩溃）转到"继续呼吸"（被 catch 处理后平稳飞行）。你不装面罩（不写 try-catch），出事就只能坠机。

#### ② 为什么（追问三层）

- **为什么需要异常处理？** 因为错误发生在运行时，且发生点和能处理点往往不在同一个函数里——底层函数发现除数为 0，但只有上层业务才知道"该报错还是该用默认值"。
- **为什么不用返回值传错误？** 返回值只有一个，函数的"正常结果"和"错误信息"抢一个通道会互相污染；而且多层调用时每层都要手写 if 检查返回值，代码淹没在错误分支里。
- **为什么 C++ 要把它做成语言机制？** 直达本质：`throw` 是一种**转移程序控制权的方式**（P6 原话）——它跳过多层调用栈直接落到最近的匹配 catch，同时保证沿途局部对象被正确析构（资源不泄漏）。这是 if-return 做不到的。

#### ③ 怎么用

三个关键字的职责分工（P6）：

| 关键字 | 职责（P6 原文要点） | 比喻角色 |
|--------|---------------------|----------|
| `try` | 框住"将被激活特定异常"的代码，称为**保护代码**，后面通常跟一个或多个 catch | 危险区域的护栏 |
| `throw` | 问题出现时**抛出**异常，由程序员主动触发 | 按下警报按钮 |
| `catch` | 在你想要处理问题的地方**捕获**异常 | 接警处理中心 |

```cpp
#include <iostream>
using namespace std;
double divide(double a, double b) {
    if (b == 0) throw "division by zero";   // throw：拉警报
    return a / b;
}
int main() {
    try {                                    // try：护栏圈住危险代码
        cout << divide(10, 0) << endl;
    } catch (const char* msg) {              // catch：接警处理
        cerr << "错误: " << msg << endl;     // 输出：错误: division by zero（走 stderr）
    }
    cout << "程序继续运转" << endl;           // 输出：程序继续运转
    return 0;
}
```

**人话总结**：异常就是出错时的紧急出口。

#### ④ 注意事项 + 错误示范

**P4 案例逐行走读——"这段代码有什么问题吗？"**

```cpp
#include <iostream>
using namespace std;
int main()
{
    int num1 = 100, num2 = 0, num3 = 0;  // num2 初始化为 0
    num3 = num1 / num2;                  // 整数除以 0！
    cout << num3 << endl;                // 可能永远执行不到
    //do something
    return 0;
}
```

内存/状态走读：`num1`、`num2`、`num3` 依次在栈上分配（假设地址递增），`num2` 槽位写入 0；执行 `num1 / num2` 时 CPU 发出 idiv 指令，除数为 0 触发硬件级 #DE 异常——这**不是** C++ 的 throw 异常，操作系统直接接管：Windows/Dev-C++ 弹"Runtime Error!"对话框（常见 exit code 255），Linux 发 SIGFPE，`cout` 行被跳过，main 之后的代码全部作废。

**inf / nan 的含义（P10 侧栏原文）**：`inf` = infinity（Linux 下的表示），等同于 Windows 的 `#INF:`；`nan` = not a number，等同于 `#IND:`（indeterminate）。**inf 一般是因为得到的数值超出浮点数表示范围（溢出，即阶码部分超过其能表示的最大值）；nan 一般是因为对浮点数进行了未定义操作，如对 -1 开方**。浮点除 0 属于 IEEE 754 定义的"合法产生无穷"的路径，所以不崩溃、只悄悄给出错值——这正是 P10 案例的输出 `inf` 的由来。

**关键区分表（贯穿全章的核心认知）**：

| 情况 | 结果 | 会被 catch 捕获吗 |
|------|------|-------------------|
| 整数除 0（int / int） | 未定义行为，程序崩溃 | **不会**——硬件级错误，C++ 异常机制管不到 |
| 浮点除 0（double / double） | 得到 inf / nan，照常往下跑 | **不会**——静默产出错误值更危险 |
| 代码主动 `throw` | 抛出异常对象 | **会**——这才是异常处理管的范围 |

**错误示范**：新手最常见的误解是"写了 try-catch，程序遇到除零就会自动进 catch"。

```cpp
try {
    int a = 100, b = 0;
    cout << a / b << endl;   // 错！整数除0不抛C++异常，直接崩溃，catch形同虚设
} catch (...) {
    cout << "接住了" << endl; // 永远不会执行
}
```

**正确写法**：C++ 的异常要靠程序员**自己检测、自己 throw**（这正是 P11-P12 的教学动机）：

```cpp
if (b == 0) throw "Division by zero condition!";  // 先检测，再抛出
```

**人话总结**：错误不会自己变成异常，得你亲手 throw。

### 知识点 2. 标准异常（P7-P8）【熟悉】

#### ① 是什么

**一句话定义**：C++ 在 `<exception>` 头文件中预定义了一系列标准异常类（P7），它们**以父子类层次结构组织**，根类是 `std::exception`，提供公共方法 `what()` 返回异常原因描述。

**生活化比喻**：标准异常体系像医院的科室分类——急诊分诊台（`std::exception` 基类）能接待所有病人，但你也可以精确挂到骨科（`bad_alloc`）、内科（`logic_error` 家族）、外科（`runtime_error` 家族）。挂号时用大类兜底（catch 基类）不会漏诊，用细类（catch 派生类）能专病专治。

#### ② 为什么

内存分配失败、动态转换失败、下标越界……这些错误每个 C++ 程序都会遇到。如果每人每项目各造一套名字，库和用户之间就无法沟通。标准化异常类 = 全行业统一的"错误方言"，标准库组件（vector::at、new、dynamic_cast）抛出的异常用户可以直接 catch。

#### ③ 怎么用

**标准异常层次结构树（依据 P7 结构图重绘，标注触发场景）**：

```
                        std::exception            ← 所有标准 C++ 异常的父类（万流归宗）
                        │  const char* what()     ← 返回异常原因描述
   ┌──────────┬───────────────────────┬──────────────────┐
   │          │          │             │                  │
bad_alloc  bad_cast  bad_typeid  bad_exception     logic_error 家族        runtime_error 家族
new 失败   dynamic_  typeid 对   无法预期的    理论上读代码就能       理论上读代码读不

```

**三类分支记忆**：直接挂在 exception 下的 4 个（bad_* 家族，由语言设施抛出）+ logic_error 一支（程序本身的逻辑缺陷）+ runtime_error 一支（跑起来才遇到的错误）。

**标准异常全表（P8 表格原文照录）**：

| 异常 | 描述 | 所属分支 |
|------|------|----------|
| `std::exception` | 该异常是所有标准 C++ 异常的父类 | 根 |
| `std::bad_alloc` | 该异常可以通过 `new` 抛出 | 直接子类 |
| `std::bad_cast` | 该异常可以通过 `dynamic_cast` 抛出 | 直接子类 |
| `std::bad_typeid` | 该异常可以通过 `typeid` 抛出 | 直接子类 |
| `std::bad_exception` | 这在处理 C++ 程序中无法预期的异常时非常有用 | 直接子类 |
| `std::logic_error` | 理论上可以通过读取代码来检测到的异常 | logic 支 |
| `std::domain_error` | 当使用了一个无效的数学域时，会抛出该异常 | logic 支 |
| `std::invalid_argument` | 当使用了无效的参数时，会抛出该异常 | logic 支 |
| `std::length_error` | 当创建了太长的 `std::string` 时，会抛出该异常 | logic 支 |
| `std::out_of_range` | 该异常可以通过方法抛出，例如 `std::vector` 和 `std::bitset<>::operator[]()` | logic 支 |
| `std::runtime_error` | 理论上不可以通过读取代码来检测到的异常 | runtime 支 |
| `std::overflow_error` | 当发生数学上溢时，会抛出该异常 | runtime 支 |
| `std::range_error` | 当尝试存储超出范围的值时，会抛出该异常 | runtime 支 |
| `std::underflow_error` | 当发生数学下溢时，会抛出该异常 | runtime 支 |

可运行示例（含标准库组件自动抛出的场景）：

```cpp
#include <iostream>
#include <stdexcept>     // logic_error/runtime_error 家族在这个头文件
using namespace std;
int main() {
    try { throw invalid_argument("bad arg"); }
    catch (const logic_error& e)  { cout << "logic: " << e.what() << endl; }
    // 输出：logic: bad arg
    vector<int> v;
    try { cout << v.at(3) << endl; }               // 空 vector 取第 3 个
    catch (const out_of_range& e) { cout << "range: " << e.what() << endl; }
    // 输出：range: vector::_M_range_check: __n (which is 3) >= this->size() (which is 0)
    try { throw overflow_error("up"); }
    catch (const runtime_error& e) { cout << "run: " << e.what() << endl; }
    // 输出：run: up
    return 0;
}
```

注意示例中 `catch(const logic_error&)` 能接住 `invalid_argument`——**父类引用捕获子类对象**，靠的是第19章学的多态。

**人话总结**：现成的异常家族，include exception 直接用。

#### ④ 注意事项 + 错误示范

- 使用标准异常必须先引入头文件：`#include <exception>`（基类）或 `#include <stdexcept>`（logic/runtime 两支的具体类）。
- **错误示范**：以为 `new` 失败返回 nullptr。

```cpp
int* p = new int[1000000000ULL * 1024];  // 分配失败时默认抛 bad_alloc，不是返回 null
if (p == nullptr) { /* 这个判断在默认 new 下永远不会成立 */ }
```

**正确写法**：要么 try-catch `bad_alloc`，要么用不抛异常的版本 `new (std::nothrow) int[n]`（失败返回 nullptr）。
- `out_of_range` 由 `at()` 抛出；普通 `operator[]` **不做越界检查**，越界是未定义行为——想用异常兜底就用 `at()`。

**人话总结**：new 失败是抛异常，不是给 null。

## 模块二：异常处理核心三件套

### 知识点 3. try/catch 语句（P9-P11）【重点】

#### ① 是什么

**一句话定义**（P9）：try 块中放置可能抛出异常的代码，这段代码被称为**保护代码**（有可能出错的代码）；一个 try 块后面可以跟**多个 catch 块**，分别捕获不同类型的异常。

**生活化比喻**：try/catch 像机场安检通道——旅客（控制流）正常走过安检区（try 保护代码）；一旦探测器报警（throw），这名旅客立刻被引导进对应的处置室（匹配的 catch），而不是继续在廊桥里往前走（try 内后续语句不执行）。不同证件类型走不同处置窗口（多个 catch），最后还有个万能窗口（catch(...)）。

#### ② 为什么（三层追问）

- **为什么要包一段代码而不是包一行？** 因为"一次业务操作"常由多行组成，任何一行出错都意味着整段操作作废，必须整体保护。
- **为什么一个 try 配多个 catch？** 同一段保护代码在不同情境下会抛出不同异常（P9 右栏原话），出错原因不同、处理方式也不同，所以要分类处置。
- **为什么不直接把整个 main 塞一个 try？** 深层原因：catch 粒度决定了恢复能力——把出错点包得越准，能给出的针对性补救就越有效；满屏大 try 等于没有分级分诊。

#### ③ 怎么用

P9 给出的语法格式：

```cpp
try {
    // 保护代码（有可能出错的代码）
} catch (ExceptionName e1) {
    // catch 块：处理类型 1
} catch (ExceptionName e2) {
    // catch 块：处理类型 2
} catch (ExceptionName eN) {
    // catch 块：处理类型 N
}
```

**教材 P10-P11 案例逐行走读**（"这段代码有什么问题？要想代码正常运行完，如何修改？"）：

```cpp
#include <iostream>
using namespace std;
double div_(double x, double y) { return (x / y); }   // 教材原名 div，此处避免与 POSIX div 冲突
double add(double x, double y)  { return x + y; }
int main() {
    double v1 = 50, v2 = 0;                // v2 = 0，除法隐患埋下
    double result1 = div_(v1, v2);         // 50.0 / 0.0：浮点除0，不崩溃
    cout << result1 << endl;               // 输出：inf        ← 错误值悄悄扩散
    double result2 = add(v1, v2);          // 50 + 0 = 50，照常执行
    cout << result2 << endl;               // 输出：50
    return 0;
}
```

g++ 实测输出：

```
inf
50
```

状态走读：`div_(50,0)` 内部执行 IEEE 754 除法，结果为"正无穷"编码，赋给 `result1`；`cout` 按平台打印 `inf`（Linux）或 `#INF`（Windows）——**程序"正常结束"了，却带着一个错误值跑完了全程**。这就是 P10 提出的两难：没崩溃 ≠ 没问题。

P11 给出结论：**需要 div 函数里面判断除数是否为 0，如果为 0，需要抛出异常**——修复分两步：函数内加检测并 throw（下一步知识点 4），调用处加 try-catch（知识点 5）。

**try 块中一旦抛出异常，后续语句不再执行**——最小验证：

```cpp
#include <iostream>
using namespace std;
int main() {
    try {
        cout << "第1句" << endl;
        throw 42;
        cout << "第2句" << endl;      // 被跳过
    } catch (int e) {
        cout << "catch 收到 " << e << endl;
    }
    return 0;
}
// 输出：第1句
// 输出：catch 收到 42
```

**try-catch 嵌套可视化**（课件专项要求 2）——内层 catch 未匹配的异常如何向外层传播：

```cpp
#include <iostream>
using namespace std;
int main() {
    try {                                        // ┌─ 外层 try
        cout << "进入外层" << endl;
        try {                                    // │  ┌─ 内层 try
            throw 3.14;                          // │  │ 抛 double
            cout << "内层后续不执行" << endl;     // │  │ ×跳过
        } catch (int e) {                        // │  ├─ 内层 catch(int)：double≠int，不匹配
            cout << "内层接住 int" << endl;       // │  │ ×不进
        }                                        // │  └─ 内层结束，异常仍未处理
        cout << "内层try后的语句" << endl;         // │ ×异常还在逃逸，这句也不执行
    } catch (double e) {                         // ├─ 外层 catch(double)：匹配！
        cout << "外层接住 double: " << e << endl; // √ 输出这里
    }
    cout << "全部处理完，继续" << endl;            // 输出：全部处理完，继续
    return 0;
}
// 输出：进入外层
// 输出：外层接住 double: 3.14
// 输出：全部处理完，继续
```

嵌套匹配规则图示：

```
外层 try {
    ...
    内层 try { throw X; }
        catch(T1)  ← ① 先在内层的 catch 里从左到右找 X 的匹配
        catch(T2)  ← ②
    ...内层 try 之后的语句（若 ①② 都没接住则一并跳过）
    若内层全部 catch 未匹配 → 异常穿出内层 try，
        像没处理一样来到外层 catch(T3)...  ← ③ 外层继续找
}
```

**人话总结**：try 圈雷，谁炸谁停，就近找坑埋。

#### ④ 注意事项 + 错误示范

**陷阱级规则：多个 catch 的匹配顺序 = 书写顺序，自上而下一个一个试，命中即停。** 因此**子类必须在父类前面**。

**错误示范**：

```cpp
class MyException : public exception {
public:
    const char* what() const throw() override { return "my test exception"; }
};
int main() {
    try { throw MyException(); }
    catch (exception& e)    { cout << "父类先截获: " << e.what() << endl; }
    catch (MyException& e)  { cout << "子类精确处理" << endl; }  // 永远不可达
    return 0;
}
// 输出：父类先截获: my test exception
// g++ 编译期警告：exception of type 'MyException' will be caught by earlier handler for 'std::exception'
```

后果：子类 catch 变成死代码，精确处置逻辑全部失效。g++ 会给警告但不报错，VS 同样只警告——**能编译通过 ≠ 写对了**。
**正确写法**：`catch (MyException& e) {...}` 在前，`catch (exception& e) {...}` 在后，`catch (...)` 垫底。

另一个易错点：**catch 类型与 throw 表达式类型严格匹配，不发生隐式转换**：

```cpp
try { throw "boom"; }              // 抛 const char*
catch (exception& e) { /* A */ }   // 接不住：const char* 不是 exception
catch (string s)     { /* B */ }   // 也接不住：不会 char* → string 隐式转换
catch (const char*)  { /* C */ }   // 只有这里能接住
```

**人话总结**：catch 从上往下试，子类在前父类在后。

### 知识点 4. 抛出异常 throw（P12-P13）【重点】

#### ① 是什么

**一句话定义**（P12）：使用 throw 语句在代码块中的**任何地方**抛出异常；throw 的操作数可以是任意表达式，**表达式结果的类型决定了抛出的异常的类型**。

**生活化比喻**：throw 像拉动火警拉手——拉的手（抛出点）只负责"确认着火就拉"，不负责灭火；楼管中心（catch）在离你最近的控制室等着。类型决定异常类型好比拉不同编号的拉手对应"火警/燃气警/水浸警"，中心按警种处置。

#### ② 为什么（三层追问）

- **为什么要 throw？** 因为函数发现问题却没资格就地解决（不知道怎么恢复才符合业务），于是把问题"升级"出去。
- **为什么抛出点选在函数内部检测处？** 除数是不是 0，`div` 自己最清楚；让最有信息的一方负责报警，是错误处理的第一原则（P13 教学动机的本质）。
- **为什么类型由表达式决定？** 这样同一机制能承载任何错误信息：字符串（一句话说明）、int/enum（错误码）、类对象（携带上下文的富信息）。异常类型就是"警种的身份证"，catch 凭它分拣。

#### ③ 怎么用

P12 教材实例（尝试除以零时抛出异常）：

```cpp
double div_(double a, double b) {
    if (b == 0) {
        throw "Division by zero condition!";  // 抛出 const char* 类型的异常
    }
    return (a / b);        // throw 之后函数立即返回，正常路径才会走到这
}
```

P12 右下角批注："修改上述案例中的代码，尝试运行"——把 P10 案例的 `return (x/y);` 换成上面版本，main 不动，运行结果是：

```
terminate called after throwing an instance of 'char const*'
（程序异常终止，exit code 3；"后面不会执行"那句从未打印）
```

**配套代码 mycode.cpp 的 mydiv 函数**（与教材同构，注意两处拼写差异）：

```cpp
double mydiv(double v1, double v2) {
    if (v2 == 0) {
        throw "divsion by zero condition";   // 比教材少个 i（divsion）、无感叹号
    }                                          // 编译器不在乎拼写，能正常运行
    return v1 / v2;
}
```

**throw 后函数立即返回、控制权转移到调用者**——三层调用完整演示：

```cpp
#include <iostream>
using namespace std;
int level3() {
    cout << "level3 开始" << endl;
    throw 42;                    // 抛出 int，值为 42
    cout << "level3 结束" << endl;   // 永不执行
    return 0;                        // 永不执行
}
void level2() { level3(); cout << "level2 不会回来" << endl; }   // 永不执行
void level1() { level2(); cout << "level1 不会回来" << endl; }   // 永不执行
int main() {
    try {
        level1();                       // 层层深入
        cout << "main 的 cout 也跳过" << endl;   // 永不执行
    } catch (int e) {
        cout << "main 捕获到 " << e << endl;     // 输出：main 捕获到 42
    }
    return 0;
}
// 输出：level3 开始
// 输出：main 捕获到 42
```

异常传播路径流程图（throw 点 → catch 点，标注栈帧回退）：

```
调用方向 ↓                              异常传播方向 ↑（栈展开 stack unwinding）

main        [栈帧1: main]         try { level1(); ... }
  │                                   ▲
  ▼                                   │ ③ 弹出 level1 帧，回到 level2 调用点上方
level1      [栈帧2: level1]  call → level2()
  │                                   ▲
  ▼                                   │ ② 弹出 level2 帧，回到 level3 调用点上方
level2      [栈帧3: level2]  call → level3()
  │                                   ▲
  ▼                                   │ ① throw 42：level3 帧开始弹出，
level3      [栈帧4: level3]  throw 42 ┘    本帧局部对象逆序析构
                                            │
                                            ▼
                            运行时在每一层查找"当前层有无匹配 catch"：
                            level3 无 → level2 无 → level1 无 → main 有 catch(int)
                                            │
                                            ▼
                            控制权落入 main 的 catch 块，打印 42，程序继续
```

与正常 return 的本质区别：

| 维度 | 正常 return | throw 抛出 |
|------|-------------|------------|
| 回到哪里 | 回到**直接调用者**的调用点下一行 | 跳到**最近的匹配 catch**，可能跨越多层栈帧 |
| 沿途帧的处理 | 逐层正常弹栈，返回值逐层传递 | 逐层弹栈（栈展开），沿途局部对象照样析构，未匹配层的 try 后续语句全部跳过 |
| 携带什么 | 一个返回值（受函数签名约束） | 一个任意类型的异常对象 |
| 无人接收时 | —— | std::terminate，程序终止（P13 教训） |

**人话总结**：throw 一出手，函数当场撤，就近找 catch。

#### ④ 注意事项 + 常见错误示范

**P13 核心教训：只抛出不捕获，程序无法正常结束。** 上面演示的运行结果就是活证据：`terminate called after throwing an instance of 'char const*'`，进程以非 0 退出码死亡，连累 main 后半段全部业务。

错误示范 1——throw 写在"看起来会执行"但其实永远执行不到的位置之外忘了检测：

```cpp
double div_(double a, double b) {
    if (b < 0) throw "negative divisor";   // 只防了负数
    return a / b;                           // b==0 仍然溜过去算出 inf
}
```

条件写不全等于没写。抛出前把所有非法输入枚举一遍（0、负数、NaN、越界）。

错误示范 2——以为 throw 之后还能清理现场：

```cpp
void foo() {
    int* p = new int[100];
    throw 1;          // 下面 delete 永远轮不到 → 内存泄漏
    delete[] p;
}
```

正确做法是把资源交给 RAII（详见知识点 8 专题），或者 throw 前先释放。

错误示范 3——抛临时字符串常量本身没问题，但**别抛局部变量的引用/指针**：

```cpp
const char* boom() {
    static const char* ok = "safe";   // static 或直接抛字面量才安全
    return ok;
}
void wrong() {
    char buf[] = "local message";
    throw buf;      // 抛的是数组首元素地址对应的指针值，异常对象拷贝的是指针本身，
                    // 栈展开后 buf 已销毁 → catch 里拿到悬垂指针，未定义行为
}
```

**正确写法**：`throw string(buf);` 或 `throw "literal";`（字面量存于静态存储区，永久有效）。

**结合配套代码讲"注释的原因"**：mycode.cpp 的 `test01()` 里，mydiv 的 try-catch 整块被 `/* */` 注释掉了：

```cpp
void test01() {
    int num1 = 200, num2 = 0, num3;
    /*try {
        cout << mydiv(num1, num2) << endl;
    }
    catch (const char *msg) {
        cerr << msg << endl;
    }*/
    try {
        cout << add(num1, num2) << endl;
    }
    catch (exception& e) {
        cout << e.what() << endl;
    }
    cout << 1111 << endl;
}
```

被注释的原因：课堂上先用 add（自定义异常）演示主流程；mydiv 那段（`const char*` 字符串异常的捕获方式）作为**留白实验**——放开注释即可看到"另一种异常类型要用对应的 catch 接"。实测放开后输出（cerr 与 cout 混排见知识点 5 讨论）：

```
divsion by zero condition
my test exception
1111
```

**人话总结**：光抛不接，程序必挂。

### 知识点 5. 捕获异常 catch（P14-P16）【重点】

#### ① 是什么

**一句话定义**（P14）：catch 块跟在 try 块后面，用于捕获异常；想捕获哪种异常，由 catch 关键字后括号内的**异常声明**决定；括号内写省略号 `...` 则成为能处理任何异常的**万能捕获**。

**生活化比喻**：catch 像快递驿站的分拣员——指定类型 catch 是"只收京东件"（生鲜柜只收冷链件），`catch(...)` 是门口那个什么都收的大筐。分拣员按窗口排队顺序（书写顺序）逐个验单，第一眼看对眼的窗口收下，后面的窗口不再看。

#### ② 为什么（三层追问）

- **为什么要 catch？** P13 已经证明：没人接的异常等于程序死刑。catch 是给异常安排的"接球手"。
- **为什么要多种 catch 形式？** 有的错误值得精确处理（库存不足→走补货流程），有的只能兜底（未知异常→至少记录日志别闪退）。指定类型 vs `catch(...)` 正对应这两种需求。
- **深层本质**：捕获类型声明同时完成两件事——**匹配判据**（类型是否兼容）和**数据交接**（把异常对象绑定到变量 e，供 what() 等使用）。写 `catch(const char* msg)` 就是把抛出的字符串指针交接到 msg。

#### ③ 怎么用

P14 的两种基本语法：

```cpp
try {
    // 保护代码
} catch (ExceptionName e) {
    // 处理 ExceptionName 异常的代码        ← 捕获指定类型
}

try {
    // 保护代码
} catch (...) {
    // 能处理任何异常的代码                ← 万能捕获
}
```

**教材演进三部曲（P14→P15→P16），每一步都是完整可运行程序**：

第一步（P15）：给 div 加上 `catch(...)`，程序可以正常运行结束了——

```cpp
#include <iostream>
using namespace std;
double div_(double a, double b) {
    if (b == 0) throw "Division by zero condition!";
    return (a / b);
}
int main() {
    double v1 = 50, v2 = 0;
    try {
        double result1 = div_(v1, v2);
        cout << result1 << endl;        // 抛出后此行跳过
    } catch (...) {
        cout << "出错了！" << endl;      // 输出：出错了！
    }
    double result2 = v1 + v2;
    cout << result2 << endl;            // 输出：50（add 照常执行，程序活到了最后）
    return 0;
}
```

第二步（P16）：想打印刚才 throw 抛出的异常信息？——

```cpp
    try {
        double result1 = div_(v1, v2);
        cout << result1 << endl;
    } catch (const char * msg) {        // 类型与 throw 表达式严格一致
        cerr << msg << endl;            // 输出：Division by zero condition!（走 stderr）
    }
```

第三步：`cerr` 与 `cout` 的区别——

| 维度 | `cout` | `cerr` |
|------|--------|--------|
| 绑定的流 | 标准输出 stdout | 标准错误 stderr |
| 是否缓冲 | 有缓冲（攒一批再刷） | **无缓冲，即时输出** |
| 能否重定向分离 | `> file` 进文件 | `2> err.log` 单独收集 |
| 用途惯例 | 正常业务数据 | 诊断、错误信息 |

异常信息用 `cerr` 打印，保证崩溃/日志采集时错误不被缓冲吞掉，也不会污染重定向后的正式输出。

**结合配套代码 test01() 讲完整流程**（add 抛 `MyExcption` 被 `catch(exception& e)` 捕获）：

```cpp
void test01() {
    int num1 = 200, num2 = 0, num3;
    try {
        cout << add(num1, num2) << endl;   // add 内 v1=200>0 → throw myex
    }
    catch (exception& e) {                 // MyExcption is-a exception，父类引用接住
        cout << e.what() << endl;          // 多态分发到 MyExcption::what()
    }                                      // 输出：my test exception
    cout << 1111 << endl;                  // 输出：1111 —— 程序正常流转的铁证
}
```

执行流程图：

```
main/test01 帧: try { add(200, 0) }
   │
   ▼
add 帧: v1=200 > 0 成立
   │  构造局部对象 MyExcption myex（this 指向栈上 myex）
   ▼
throw myex;
   │  ① 拷贝初始化：以 myex 为模板构造一份"异常对象副本"（放在特殊存储区，
   │     生命周期直到被捕获处理完毕——所以抛栈上局部对象是安全的）
   │  ② add 帧开始栈展开：myex 析构（逆序），add 的 return 永不执行
   │  ③ 控制权回到 test01 的 try 调用点：发现 catch(exception& e)
   │     类型检查：MyExcption 能绑定到 exception& 吗？→ 公有继承，可以！
   ▼
catch 块执行：e 绑定到异常对象副本；e.what() 按虚函数表
   找到 MyExcption::what() → 返回 "my test exception"
   ▼
catch 块结束 → 异常对象销毁 → 继续执行 try-catch 之后的 cout << 1111
```

**引用捕获 vs 值捕获性能与语义对比**（课件专项 + 难点 2）：

| 维度 | `catch(exception& e)` 引用捕获 | `catch(exception e)` 值捕获 |
|------|-------------------------------|------------------------------|
| 拷贝次数 | 0 次额外拷贝 | 再多复制一次异常对象 |
| 对象切片 | 无——e 仍指向完整派生对象 | **有！** 按基类 exception 切割，派生成员全丢 |
| `e.what()` 结果 | 虚函数多态生效 → `"my test exception"` | 多态已死 → `"std::exception"` |
| 修改影响 | 直接作用于异常对象 | 改的是副本，外面看不见 |
| 推荐度 | ✅ 首选（配 const 更佳：`catch(const exception& e)`） | ❌ 几乎总是错 |

实测对比（g++ 真实输出）：

```cpp
#include <iostream>
#include <exception>
using namespace std;
class MyException : public exception {
public:
    const char* what() const throw() override { return "my test exception"; }
};
int main() {
    try { throw MyException(); }
    catch (exception e)   { cout << "值捕获: " << e.what() << endl; }
    // 输出：值捕获: std::exception            ← 被切片，多态丢失
    try { throw MyException(); }
    catch (const exception& e) { cout << "引用捕获: " << e.what() << endl; }
    // 输出：引用捕获: my test exception        ← 多态保留
    return 0;
}
```

**人话总结**：catch 是接球手，类异常务必用引用接。

#### ④ 注意事项 + 常见错误示范

- **`catch(...)` 的定位**：它是"最后的兜底"，不是"省事的偷懒"。放最前面会吞掉一切，让后面精心写的分类 catch 全部变死代码。适合场景：线程入口函数防止异常穿透线程边界、main 的最后防线统一记日志。
- **万能捕获看不到异常内容**：`catch(...)` 里没有变量，无法 `e.what()`，只能打印固定文案或 `std::current_exception()` 另存。既要兜底又要详情时，正确组合是 `catch(const exception& e)` + `catch(...)` 两层。
- **错误示范**：catch 了却不处理也不重抛，静默吞异常：

```cpp
try { riskyOp(); }
catch (...) {}        // 错：什么都不做，错误被掩埋，bug 无从追查
```

**正确写法**：至少记日志，或处理不了就 `throw;` 原样重抛给上层：

```cpp
catch (const exception& e) {
    cerr << "操作失败: " << e.what() << endl;   // 要么处理
    // throw;                                   // 要么原样重抛（无对象的重抛）
}
```

重抛演示（内层记录、外层恢复）：

```cpp
#include <iostream>
using namespace std;
int main() {
    try {
        try { throw 10; }
        catch (int n) { cout << "内层捕获 " << n << "，重抛" << endl; throw; }
        // 输出：内层捕获 10，重抛
    } catch (int n) {
        cout << "外层再次捕获 " << n << endl;    // 输出：外层再次捕获 10
    }
    return 0;
}
```

- **别忘了知识点 3 的铁律**：catch 匹配只看书写顺序，第一个能接住的接走就不再往下看。

**人话总结**：三点垫底兜全场，接住要么治要么转。

## 模块三：高级异常与辅助语法

### 知识点 6. 自定义异常（P17-P18）【重点】

#### ① 是什么

**一句话定义**（P17）：通过**继承和重载 `exception` 类**来定义新的异常——派生类重写 `what()`，返回描述该异常原因的字符串。

**生活化比喻**：`throw "字符串"` 像随手撕纸条写故障——谁都能写一句，但物业（catch）没法按纸条分类派单；自定义异常像正式报修工单——有固定表单类型（类名，供精确派单）、有详细描述（what()）、还能附照片附件（成员变量携带错误码、文件名等上下文）。

#### ② 为什么（三层追问）

- **为什么要继承 `std::exception` 而不是随便写个类？** ① 免费接入整个标准异常生态：任何写 `catch(const exception&)` 的上层代码天然能兜住你的异常；② 复用 `what()` 约定接口，所有异常都能被统一"问出一句话原因"；③ 与标准库异常共存于同一棵继承树，多 catch 排序才有章可循。
- **为什么要重写 `what()`？** 基类的 what() 只会说 "std::exception"，等于工单空白；重写后才能告诉处理者"错在哪"。
- **为什么签名是 `const char* what() const throw()`？** 三段各有含义：返回 `const char*`——异常消息不该被查看者修改；`const`——查询错误不应改变异常对象自身状态（所以 const 对象/const 引用也能调用）；`throw()`——C++98 异常规格，承诺该函数绝不抛出异常（万一实现里抛了直接 terminate）。现代等价写法是 `noexcept`。

#### ③ 怎么用

**教材 P17 案例（自定义类）** + **P18 案例（抛出与捕获）**：

```cpp
#include <iostream>
#include <exception>
using namespace std;

class MyException : public exception {           // P17：继承 exception
public:
    const char* what() const throw() {           // 重写 what()
        return "my test exception";              // 返回异常原因
    }
};

int add(int v1, int v2) {                        // P18
    if (v1 > 0) {                                // 如果 v1>0，抛出自定义异常
        MyException myex;                        // 先在栈上构造异常对象
        throw myex;                              // 再抛出（拷贝到异常存储区）
    }
    return v1 + v2;
}

int main() {
    int num1 = 100, num2 = 200;
    try {
        cout << add(num1, num2) << endl;         // add 抛出，cout 被跳过
    } catch (exception& e) {                     // 父类引用捕获 → 多态
        cout << e.what() << endl;
    }
    return 0;
}
// 输出：my test exception
```

**配套代码 mycode.cpp 的同款实现**（注意源码类名拼写是 `MyExcption`，比教材少一个字母 p→pt 的 p，属笔误但编译器不介意）：

```cpp
class MyExcption : public exception {
public:
    const char* what() const throw() {
        return "my test exception";
    }
};
double add(double v1, double v2) {
    if (v1 > 0) {                                  // 注释原文：如果v1大于0则抛出自定义异常MyException
        MyExcption myex;
        throw myex;
    }
    return v1 + v2;
}
```

`test01()` 中 `add(200, 0)` → v1>0 → 抛出 → `catch(exception& e)` 利用**多态**调用到 `MyExcption::what()`——原理同第19章"父类引用指向子类对象，虚函数按实际类型分发"。`what()` 在 exception 中本就是 virtual，所以不写 override 也多态依然生效（写上更好，见下文规范版）。

**自定义异常类设计的标准范式（带成员变量携带上下文）**：

```cpp
#include <iostream>
#include <string>
#include <exception>
using namespace std;

// 进阶版：携带错误码 + 文件名 + 行号的"富工单"
class FileError : public exception {
    string detail_;                      // 上下文信息
    int    code_;
public:
    FileError(const string& file, int line, int code)
        : code_(code) {
        detail_ = "FileError[" + to_string(code) + "] @ " + file + ":" + to_string(line);
    }
    const char* what() const noexcept override {   // 现代写法：noexcept 替代 throw()
        return detail_.c_str();                    // string 生命周期与本对象一致，安全
    }
    int code() const { return code_; }             // 自定义查询接口
};

int main() {
    try {
        throw FileError("config.ini", 42, 404);    // 抛出时就把上下文打包带走
    } catch (const FileError& fe) {
        cout << fe.what() << " code=" << fe.code() << endl;
        // 输出：FileError[404] @ config.ini:42 code=404
    } catch (const exception& e) {                 // 上层仍能按基类兜底
        cout << e.what() << endl;
    }
    return 0;
}
```

**简单 throw 字符串 vs 自定义异常类 优劣对比**：

| 维度 | `throw "错误啦"`（字符串） | 自定义异常类 |
|------|---------------------------|--------------|
| 编写成本 | 最低 | 要多写一个类 |
| 被精确捕获 | 只能 `catch(const char*)`，所有字符串异常混在一起 | 按类型精确分拣 |
| 携带结构化上下文 | 不能（只有一句话） | 成员变量随意放（错误码/路径/时间戳） |
| 融入标准体系 | 否——`catch(exception&)` 接不住它 | 是——基类引用天然兜得住 |
| 本地化/二次加工 | 拼好的字符串难以再解析 | 可按字段重新组装 |
| 适用场合 | 玩具程序、快速验证 | 正式项目一律用类 |

**人话总结**：继承 exception 重写 what，工单才有人认领。

#### ④ 注意事项 + 常见错误示范

- **错误示范 1：忘记公有继承。** `class MyException : exception`（默认 private 继承）会导致 `catch(exception&)` 编译失败——外部无法把派生对象当基类用。必须 `public exception`。
- **错误示范 2：what() 返回悬垂指针。**

```cpp
class Bad : public exception {
public:
    const char* what() const throw() {
        char buf[64];
        sprintf(buf, "value too big: %d", 999);
        return buf;             // 错！返回栈数组地址，函数返回即失效
    }
};
```

**正确写法**：返回字符串字面量（静态存储区），或把消息存进成员 string 并返回其 `c_str()`（如上 FileError）。
- **错误示范 3：签名抄歪。** `char* what()`、`const char* what()`（少了 const）都不构成对基类虚函数的重写（override），只是新增了一个函数——`catch(exception&)` 里调 e.what() 走的仍是基类版本，你的消息永远显示不出来。g++ 下配合 `override` 关键字可在编译期暴露这类错误：

```cpp
const char* what() const noexcept override { return "my test exception"; }  // 推荐写法
```

- **异常规格演进提醒**：教材 `what() const throw()` 里的 `throw()` 是 C++03 动态异常规格，C++11 起被 `noexcept` 取代并弃用（C++17 中 throw() 已不推荐出现在新代码）。老师保留老写法是为对齐教材；工程请写 `noexcept`。

**课堂练习题（P19-P22）——数组下标越界异常**

**题目（P19）**：创建一个数组，创建一个函数取数组元素，当数组下标小于 0，或者数组下标大于最大下标时抛出异常，其他正常取值。下标小于 0 → `underflow`；下标大于 n-1 → `overflow`。

**解题思路（三步）**：
1. 异常不必是类——**枚举常量就能当异常抛**：`enum index { underflow, overflow };`（underflow=0，overflow=1）。抛出类型是枚举类型 index，catch 也必须写 `catch(index e)`。
2. 函数里做两道边界检查，哪道不过就 throw 哪个枚举值；都过了才 `return arr[index]`。
3. 调用方 try 包住，catch 里用 `if (e == underflow) / else if (e == overflow)` 分辨是哪一种越界并输出对应提示。

**教材参考答案（P20 声明 + P21 main + P22 函数体，三段合一）**：

```cpp
#include <iostream>
#include <cstdlib>                   // exit 所需
using namespace std;
enum index { underflow, overflow };  // under=下标小于0，over=下标超过最大下标
int array_index(int* arr, int n, int index);

int array_index(int* arr, int n, int index) {   // P22
    if (index < 0)   throw underflow;           // 太小 → 抛枚举值
    if (index > n-1) throw overflow;            // 太大 → 抛枚举值
    return arr[index];                          // 合法才真正取值
}

int main() {                                    // P21
    int* arr = new int[10];
    for (int i = 0; i < 10; i++)
        arr[i] = i;                             // 教材此页原文写作 A[i]=i，属排版笔误
    try {
        cout << array_index(arr, 10, 5)  << endl;   // 正常 → 5
        cout << array_index(arr, 10, -1) << endl;   // 抛 underflow
        cout << array_index(arr, 10, 15) << endl;   // 永远执行不到！
    } catch (index e) {
        if (e == underflow) { cout << "index underflow!" << endl; exit(-1); }
        if (e == overflow)  { cout << "index overflow!"  << endl; exit(-1); }
    }
    return 0;
}
// 输出：5
// 输出：index underflow!   （随后 exit(-1) 直接终结进程）
```

**输出精解**：第一次调用合法打印 5；第二次 idx=-1 抛 underflow，**try 块第三条语句（idx=15）被整体跳过**——教科书级演示"抛出后后续语句不执行"；catch 里 first if 命中打印后 `exit(-1)` 终止进程，所以教材 main 根本测不到 overflow 分支。**这正引出配套代码 test02() 的改进设计：三种情况拆成三行、注释切换，一次只测一种。**

**配套代码 test02() 逐行走读**（mycode.cpp 第 51-76 行区域）：

```cpp

    int* arr = new int[5];                      // 堆上分配 5 个 int
    for (int i = 0; i < 5; i++) {
        arr[i] = i + 11;                        // 填入 11,12,13,14,15
    }
    try {
        //cout << array_index(arr, 5, -2)  << endl;   // 实验A：放开→抛 underflow
        //cout << array_index(arr, 5, 100) << endl;   // 实验B：放开→抛 overflow
        cout << array_index(arr, 5, 2) << endl;       // 当前：arr[2]=13，正常
    }
    catch (index e) {
        if (e == underflow) {
            cout << "下标太小啦！" << endl;            // 中文提示（源文件GBK编码）
        }
        else if (e == overflow) {
            cout << "下标太大啦！" << endl;
        }
    }

```

三种测试情况的预期输出（均经 g++ 实测验证）：

| 放开哪行 | 传播过程 | 输出 |
|----------|----------|------|
| 只放开 `array_index(arr,5,2)`（现状） | 无异常，正常返回 | `13` |
| 放开 `-2` 行（置首） | -2<0 → throw underflow → try 剩余语句跳过 → catch 第一分支 | `下标太小啦！` |
| 放开 `100` 行 | 100>4 → throw overflow → catch else-if 分支 | `下标太大啦！` |
| **三行全放开** | 第一行就抛 underflow，后两行全跳过 | 只有 `下标太小啦！` |

**被注释掉的两次调用的演示目的**：`arr[5,-2]` 演示 underflow 触发路径，`arr[5,100]` 演示 overflow 触发路径；互斥注释是为了让学生每次只观察一种异常的完整传播，避免"第一个异常短路后面实验"。

**隐藏陷阱**：test02 里 `new int[5]` 之后没有任何 `delete[]`——即使不抛异常这条路径也泄漏；若中途 throw，栈展开时更是直接漏掉。这正是下一个专题（RAII 与异常安全）要解决的问题。

**人话总结**：枚举当警种，越界照样抛得明明白白。

### 知识点 7. 嵌套类和局部类（P23-P30）【熟悉】

#### ① 是什么

**一句话定义**：嵌套类是定义在外围类内部的类（P23-P24）；局部类是定义在函数体内的类（P26-P27）。两者本质都是**作用域管理手段**，不是新的对象模型。

**生活化比喻**：嵌套类像公司部门内部的专用工具间——工具（InnerClass）登记在部门名下（作用域隐藏在外围类中），别的部门要用必须写全称"研发部·工具间"（`OuterClass::InnerClass` 名字限定），而且工具间钥匙不给部门经理私配（嵌套类不能访问外围类私有成员，反之亦然）。局部类像会议室白板上的临时草图——只在本次会议（函数执行期间）有意义，散会即擦（出了函数域不可见）。

#### ② 为什么

- **为什么要嵌套类？** P23 原话：外围类需要使用嵌套类对象作为底层实现，并且该嵌套类只用于外围类的实现，**同时可以对用户隐藏该底层实现**。比如链表类内部的 Node、容器内部的迭代器实现细节——藏进类里，全局命名空间不被垃圾名污染。
- **为什么规定"互相不能访问私有成员"？** 因为嵌套**仅仅是语法上的嵌入**（P23 末句），不构成 friend 关系（C++11 起才允许嵌套类访问外围类私有成员，但教材按传统规则讲授）。
- **为什么要局部类？** 把只为这一个函数服务的辅助类型限制在函数体内，用完即弃；实践中很少使用（P26 原话）。

#### ③ 怎么用

**P24 嵌套类基本语法结构**：

```cpp
class 外围类名 {            // 类体
    class 嵌套类名 {        // 类体
    };
};
```

**P27 局部类基本语法结构**：

```cpp
type funcName(parameter list) {   // 函数
    class 局部类名 {              // 类体
    };
};
```

**P25 嵌套类三条特点**（原文规则）：
1. 嵌套类不可以访问外围类的任何成员；
2. 外围类可以通过对象访问嵌套类的**公有**成员，但不能访问其保护和私有成员；
3. 嵌套类只能由外围类使用（类名对外不可见，外部使用需加名字限定）。
另有两条补充（P23）：嵌套类的成员函数**可以**在类体外定义；老版本 C++ 和部分编译器不支持嵌套类。

**局部类三条限制**（P26 原文规则）：只在定义它的局部域内可见；成员函数**必须**定义在类体中（不能类外）；不能有静态成员函数。

**教材 P28-P30 完整案例（三段拼成一个可运行程序，g++ 实测）**：

```cpp
#include <iostream>
using namespace std;

class OuterClass {                       // P28：外部类
public:
    class InnerClass {                   // 嵌套类
    public:
        void func();                     // 只声明——嵌套类成员函数可以拿到类外定义
    };
public:
    InnerClass obj;                      // 外围类持有嵌套类对象（"作为底层实现"）
    void func() {                        // 外部类的 func 方法
        cout << "OuterClass func()" << endl;
        obj.func();                      // 通过对象调用嵌套类公有成员（特点2 演示）
    }
};

void OuterClass::InnerClass::func() {    // P29：类体外定义，作用域链写全两级类名
    cout << "InnerClass func()" << endl;
}

void func() {                            // 全局函数
    class LocalClass {                   // P29：局部类
    public:
        int num;
        void setNum(int n) { num = n; }              // 成员函数必须类体内定义
        void showNum() { cout << "num=" << num << endl; }
    };
    LocalClass lc;                                   // 局部类对象只在函数内可用
    lc.setNum(111);
    lc.showNum();
}

int main() {                               // P30
    OuterClass oc1;
    oc1.func();                            // ① 走外围类转发
    cout << "---------------------" << endl;
    OuterClass::InnerClass ic1;            // ② 外部作用域使用嵌套类：必须名字限定
    ic1.func();
    cout << "---------------------" << endl;
    func();                                // ③ 局部类在全局函数内部自产自销
    return 0;
}
```

实际输出：

```
OuterClass func()
InnerClass func()
---------------------
InnerClass func()
---------------------
num=111
```

逐行走读 main 的状态变化：
- `OuterClass oc1;`：栈上构造 oc1，其成员 obj（InnerClass）随之构造（无自定义构造，仅占位）。
- `oc1.func();`：进外围类 func，打印第一行；再执行 `obj.func()`——注意此刻调用的是**嵌套类**的 func，函数体早已定义在类外（P29 那段），打印第二行后逐层返回。
- `OuterClass::InnerClass ic1;`：证明嵌套类可以在外部创建，前提是**逐级限定**；写成 `InnerClass ic1;` 直接编译报错 `'InnerClass' was not declared in this scope`。
- `ic1.func();`：独立对象自己调用，打印一行——演示嵌套类并非只能依附外围类对象存在。
- `func();`：进全局函数，局部类 LocalClass 随函数作用域诞生：lc 构造→setNum(111) 写成员→showNum 打印 `num=111`→函数返回，LocalClass 类型与 lc 同时消亡，函数外谁也引用不到。

**嵌套类 vs 局部类 对比表**：

| 维度 | 嵌套类 | 局部类 |
|------|--------|--------|
| 定义位置 | 另一个类的类体内 | 函数体内 |
| 可见范围 | 外围类作用域内直接可见；外部需 `Outer::Inner` 限定 | 仅定义它的函数体内 |
| 成员函数类外定义 | **可以**（`Outer::Inner::func()` 全链书写） | **不可以**，必须类体内定义 |
| 静态成员函数 | 可以有 | 不能有 |
| 与外围/宿主的关系 | 仅是语法嵌入，互相无私有访问权（教材规则） | 不能访问函数局部变量；只能用全局量 |
| 典型用途 | 隐藏实现细节（Node、迭代器、句柄） | 函数内一次性小工具 |
| 实用频率 | 较多 | 极少（P26：实践中很少使用） |
| 兼容性提示 | 老版本 C++/部分编译器不支持（P23） | 一直支持 |

**配套代码 test03() 逐行走读**（mycode.cpp 第 3-47 行，结构与教材案例完全一致，仅两处文案差异）：

```cpp

    OuterClass oc1;
    oc1.func();                                   // 打印 Outerclass func()（源码此处大小写为 Outerclass，
                                                  // 与教材 P28 的 OuterClass 略有出入，纯显示文案）
```

Test002.cpp 的 main 当前只放开 `test03()`（`//test01(); //test02();` 处于注释），所以整套工程的默认输出就是上面五行（分隔线为星号版）。

**人话总结**：类里藏类要写全名，函数里造类用完即焚。

#### ④ 注意事项 + 常见错误示范

**错误示范 1：外部直接裸用嵌套类名。**

### 专题 A. 异常传播流程图与拷贝/移动语义（专项 1）

知识点 4 已给出四层调用的传播图。此处补全**异常对象生命周期**视角：

```
throw expr;
   │
   ├─ 阶段1 构造异常对象：以 expr 为初值，在"异常存储区"生成对象（静态/特殊区，
   │        不受任何栈帧支配）。expr 若是栈上局部对象（如 add 里的 myex），
   │        拷贝/移动发生在 throw 瞬间——随后 myex 随栈展开销毁，副本仍存活。
   │        ⇒ 这就是"throw 局部对象是安全的"的原因。
   ├─ 阶段2 栈展开（stack unwinding）：从抛出帧开始逐层弹出，
   │        每帧内已构造完成的局部对象按构造逆序调析构；
   │        每到一个帧，先检查该帧 try 对应的 catch 列表能否匹配。
   ├─ 阶段3 移交：找到匹配 catch → 用它声明的形式绑定异常对象：
   │        catch(T e) 再拷贝一次（且有切片风险）；
   │        catch(T&/const T&) 直接绑定到异常存储区的对象，零额外拷贝；
   │        catch(...) 不绑定任何东西。
   └─ 阶段4 销毁：catch 块（及重新抛出链）执行完毕，异常对象析构释放。
       若一路到顶都没人匹配 → std::terminate()（P13 结局）。
```

**与正常 return 的区别对照表**见知识点 4；一句话记忆：return 是"坐电梯逐层回"，throw 是"消防滑索直接落到最近的接应平台"。

**抛对象切片陷阱延伸**：`throw derivedObj;` 时异常存储区按 **static 类型** 建对象——

```cpp
MyException me;
throw me;              // OK：异常对象类型 = MyException（表达式类型决定，P12）
exception& ref = me;
throw ref;             // 危险：ref 的 static 类型是 exception → 异常对象被切片！
```

第二条抛出去的就是 exception 而非 MyException，catch(MyException&) 再也接不住。这也是"宁可 `throw MyException()` 就地构造，别抛基类引用"的理由。

### 专题 B. RAII 与异常安全（专项 5）

**RAII（Resource Acquisition Is Initialization，资源获取即初始化）**：把资源的生命周期绑到对象生命周期上——构造函数拿资源，析构函数还资源。由于**栈展开保证沿途局部对象一定被析构**（专题 A 阶段 2），异常再怎么飞，资源也会被对象析构自动归还。这就是异常安全的基石。

**错误代码：new 之后 throw 导致内存泄漏**（g++ 实测可复现）：

```cpp
#include <iostream>
#include <memory>
using namespace std;
void badWay() {
    int* p = new int[100];      // 裸指针持资源：不受栈展开管辖
    throw 1;                    // p 还没等到 delete 就被"扔下"
    delete[] p;                 // 永远执行不到 → 100 个 int 泄漏
}
void goodWay() {
    unique_ptr<int[]> p(new int[100]);   // 智能指针持资源：栈展开时 ~unique_ptr 自动 delete[]
    throw 1;
}
int main() {
    try { badWay(); }  catch (int) { cout << "badWay: 泄漏了 100 个 int" << endl; }
    try { goodWay(); } catch (int) { cout << "goodWay: unique_ptr 自动释放" << endl; }
    return 0;
}
// 输出：badWay: 泄漏了 100 个 int
// 输出：goodWay: unique_ptr 自动释放
```

**手动 try-catch 清理 vs RAII 守卫 对比**：

| 维度 | 手动在 catch 里善后 | RAII（智能指针/lock_guard） |
|------|---------------------|------------------------------|
| 写法 | `try{...}catch(...){ delete p; unlock(); throw; }` 每条异常路径都要写 | 构造即获取，离开作用域即释放 |
| 多出口正确性 | return/break/异常混合时极易漏一条路径 | 所有离开方式统一走析构，天然安全 |
| 重抛纪律 | catch 里善后完必须 `throw;` 否则异常被吞 | 无需操心 |
| 代码体量 | 侵入业务逻辑 | 一行声明，意图清晰 |
| 典型代表 | 老式 C 风格包装 | `unique_ptr`、`shared_ptr`、`lock_guard`、fstream |

**异常安全三级保证（标准库容器的承诺，专项补充 2）**：

| 等级 | 承诺 | 标准库例子 |
|------|------|-----------|
| 无异常保证 nothrow | 操作绝不抛（或不在此讨论） | 析构函数、swap（多数实现）、`is_nothrow_*` trait |
| 强保证 strong | 抛了就**完全回滚**，像没发生过（事务语义） | `vector::push_back`（扩容失败时原容器不变）、`map::insert` |
| 基本保证 basic | 抛了也无泄漏、对象仍处于**合法但未定义具体值**的状态 | `vector::erase`、部分 `insert` 场景 |

文档里 STL 函数都会标注 noexcept 或异常行为，后续学容器时先查这条承诺，再决定要不要包 try。

**assert 与异常的区别（专项补充 3）**：

| 维度 | `assert(expr)` 宏 | 异常 throw/catch |
|------|-------------------|------------------|
| 定位 | 调试期自检："这种事**不该**发生"（程序员的合同） | 运行期恢复："这种事**可能发生**"（环境的现实） |
| Release 行为 | 定义 NDEBUG 后整体消失，零开销 | 始终存在 |
| 触发后果 | abort 立即终止，弹断言框 | 可被捕获，程序继续流转 |
| 可否重定向处理 | 不可 | 可以，分层分类 |
| 典型用法 | 内部不变量、参数契约（demo/调试） | 文件打不开、网络超时、余额不足 |

配套小例（Windows Debug 实测弹出 `Assertion failed! ... Expression: b != 0` 后终止，exit 3）：

```cpp
#include <iostream>
#include <cassert>
using namespace std;
int divide(int a, int b) {
    assert(b != 0);       // 调试期防线；Release(NDEBUG) 下这行直接消失
    return a / b;
}
int main() {
    cout << divide(10, 2) << endl;   // 输出：5
    divide(10, 0);                   // Debug：断言弹窗终止；Release：变成未定义行为！
    cout << "不会到这里（Debug）" << endl;
    return 0;
}
```

注意反面教训：**发布版里 assert 蒸发了**，若把"必须发生的校验"只写在 assert 里，Release 下就裸奔了——生产校验必须用 if+throw。

**人话总结**：资源交给对象管，异常来了自然还。

### 专题 C. 栈展开机制详解与析构函数禁忌（专项 6）

**栈展开（unwinding）中析构顺序演示**——构造 A→B→C，异常从最深帧抛出，析构必然 C→B→A（逆序）：

```cpp
#include <iostream>
using namespace std;
struct Trace {
    const char* name;
    Trace(const char* n) : name(n) { cout << "构造 " << name << endl; }
    ~Trace() noexcept { cout << "析构 " << name << endl; }
};
void level3() {
    Trace c("C层局部对象");
    cout << "level3 抛出前" << endl;
    throw 1;
    cout << "level3 抛出后（永不执行）" << endl;
}
void level2() { Trace b("B层局部对象"); level3(); cout << "level2 不会执行" << endl; }
void level1() { Trace a("A层局部对象"); level2(); cout << "level1 不会执行" << endl; }
int main() {
    try { level1(); }
    catch (int) { cout << "main 捕获异常" << endl; }
    cout << "程序继续" << endl;
    return 0;
}
```

g++ 实测输出（一字不差）：

```
构造 A层局部对象
构造 B层局部对象
构造 C层局部对象
level3 抛出前
析构 C层局部对象
析构 B层局部对象
析构 A层局部对象
main 捕获异常
程序继续
```

执行流程图：

```
main ─ try{ level1() }
  │ 构造A
  level1 ─ level2()
    │ 构造B
    level2 ─ level3()
      │ 构造C
      level3 ─ throw 1;
        │        └─ 展开开始：析构C ─
        │   无匹配catch → 继续展开：析构B ─┤ 逆序三连
        │   无匹配catch → 继续展开：析构A ─┘
        ▼
  main 的 catch(int) 命中 → 打印"main 捕获异常"
        │ 异常对象销毁
        ▼
  继续执行 catch 之后的 cout << "程序继续"
```

**为什么析构函数绝不能抛异常？** 栈展开正在进行时，某帧析构又抛新异常 → **同一时刻有两个异常在飞**，C++ 标准直接规定调用 `std::terminate()`，程序原地暴毙，原来的异常反而彻底没人处理。C++11 起析构函数**隐式 noexcept**，抛了连挣扎的机会都不给。

实测（g++ 编译期即警告，运行 exit 3）：

```cpp
#include <iostream>
using namespace std;
struct Bad {
    ~Bad() { throw "error in destructor"; }   // 析构里抛异常
};
int main() {
    try {
        Bad b;
        throw 42;        // 展开中销毁 b → ~Bad 又抛 → terminate
    } catch (int) { cout << "捕获 42" << endl; }   // 永远到不了
    return 0;
}
// 编译警告：throw will always call terminate() [-Wterminate]
// 运行输出：terminate called after throwing an instance of 'char const*'
```

**正确写法**：善后动作内部消化——

```cpp
~Connection() noexcept {          // 明确承诺不抛
    try { this->close(); }        // close 可能抛
    catch (...) { /* 记日志或忽略：析构是善后，不能再惹事 */ }
}
```

记忆口诀：**析构是善后，不能再惹事。**

**人话总结**：退场顺序倒着来，半路闹事全场埋。

## 2. 本章最难两个点，放慢重讲

### 难点 1：异常传播与栈展开机制

拆成五帧慢动作（对应专题 A/C 的图，这里换"退票"比喻逐帧过）：

1. **throw 瞬间**：运行时先在"异常存储区"给表达式做一份拷贝（像把登机牌拍照存档）——这份档案不归任何栈帧管，后面随便你销毁原票。
2. **本帧开始退票**：抛出函数内的局部对象按出生逆序办退房手续（调析构）。level3 里的 Trace c 最先析构。
3. **每退一层先看门口有没有指定收件人**：该层若有 try 且其 catch 列表存在能匹配的类型 → 就地交接，退票停止；没有 → 继续往外退。
4. **退到 catch 命中层**：按 catch 声明形式交接（引用绑定零拷贝 / 值接收再拷一次且可能切片）。
5. **退到顶没人接**：terminate。整个过程 try 之后的所有未执行语句一律作废，这就是"转移控制权"的字面意思。

配套练习：给专题 C 的 Trace 程序在 level2 里加一个 `try { level3(); } catch (double) {}`——预测输出？答：int 异常对 catch(double) 不匹配（不做数值隐式转换），B 层照样析构外逃，最终仍由 main 的 catch(int) 接住；但若改成 `catch (int)`，则 B 层就截胡，main 收不到。亲手改一遍最能固化理解。

### 难点 2：catch 块的类型匹配规则

匹配算法一句话：**从第一个 catch 开始，自上而下问"is-a 兼容吗"，第一个说是的接管，其余看都不看。**

- `catch(T 值)` / `catch(T& 引用)` / `catch(const T&)`：兼容条件 = throw 的动态类型 is-a T，或能标准转换（int→long 这类整型提升允许；char*→string 不允许，因为需要用户定义的隐式转换）。
- 派生类 catch 写在基类 catch 之后 = 死代码（编译器 warning 见知识点 3·④ 实录）。
- `catch(...)` 与一切兼容 → 永远最后写；写中间会腰斩后面所有 catch。
- 想区分"我的错"和"世界的错"：`catch(MyErr&) {...} catch(const exception& e) { log(e); } catch(...) { reportUnknown(); }` 三层漏斗。
- 引用捕获是唯一推荐姿势（值捕获 = 多拷贝 + 切片双杀，实测证据在知识点 5·③）。

## 3. 【常见陷阱专题】三大最易错点

### 陷阱 1：catch 块顺序错误导致子类异常永远无法被捕获

```cpp
// ❌ 错误写法
try { throw MyException(); }
catch (exception& e)   { cout << "父类先截获: " << e.what() << endl; }
catch (MyException& e) { cout << "子类精确处理" << endl; }        // 永远不可达
// 输出：父类先截获: my test exception （g++ 同时给出 will be caught by earlier handler 警告）

// ✅ 正确写法
try { throw MyException(); }
catch (MyException& e) { /* 专属处置 */ }
catch (exception& e)   { /* 通用兜底 */ }
```

**如何记住**：catch 像 if-else 链，精确匹配放前面，通配放最后。

### 陷阱 2：throw 抛出临时对象后在 catch 中按值接收导致切片

```cpp
// ❌ 错误写法
try { throw MyException(); }
catch (exception e) { cout << e.what() << endl; }   // 值拷贝切成 exception 基类子对象
// 输出：std::exception                        ← 自定义消息丢了

// ✅ 正确写法
catch (const exception& e) { cout << e.what() << endl; }
// 输出：my test exception                     ← 引用保多态
```

**如何记住**：catch 永远用引用或 const 引用，不用值。

### 陷阱 3：析构函数中抛出异常导致程序 terminate

```cpp
// ❌ 错误写法
struct Bad { ~Bad() { throw "error"; } };
int main() { try { Bad b; throw 42; } catch (int) {} }
// 编译警告：throw will always call terminate() [-Wterminate]
// 运行：terminate called ... exit code 3 —— 连 42 都没人接得住

// ✅ 正确写法
struct Good {
    ~Good() noexcept {                      // 承诺不抛
        try { cleanup(); } catch (...) { /* 内部消化/记日志 */ }
    }
};
```

**如何记住**：析构是善后，不能再惹事。

## 4. 新手最常问的 5 个问题

**Q1：throw 和 return 有什么区别？为什么不直接用返回值表示错误？**
A：return 只能回给直接调用者，且只有一个通道（正常值）；多层调用链里错误要手工逐层传递判断，代码被 if(err) 淹没，还可能被忘记检查。throw 可以跨越任意层直接落到最近的匹配 catch，正常值通道留给业务，错误走专线，还自动完成沿途析构。代价是控制流跳跃性强，滥用会让程序难以追踪——所以约定：**可预期的常规失败（如 map::find 找不到）用返回值，异常情况才用异常**。

**Q2：catch(...) 万能捕获是不是应该到处用？什么时候合适？**
A：不是。它接住一切但也看不到异常内容（没有 e.what()），到处用等于把所有故障压成同一句"出错了"。合适的场合：线程函数入口（绝不让异常穿透线程边界）、main/事件循环的最后防线（统一记日志再决定退出）、确实"无论什么错处理方式都一样"的粗粒度恢复点。否则请优先 `catch(const exception&)` 拿到信息。

**Q3：自定义异常为什么要继承 std::exception 而不是自己随便写个类？**
A：① 上层只要写 `catch(const exception&)` 就能兜住你和标准库的所有异常，生态互通；② what() 是全行业统一的"说清错因"接口；③ 将来你想细分捕获时，你的类和标准异常在同一棵树上，排序规则统一。随便写的类对上层而言是陌生人，catch(exception&) 接不住它。

**Q4：嵌套类和普通类有什么区别？什么时候需要用嵌套类？**
A：语法能力几乎相同，差别在**作用域**：嵌套类的名字藏在外围类里，对外要用 `Outer::Inner` 才能提到。用途：当某个类纯粹是外围类的实现零件、不希望污染全局命名空间时——链表里的 Node、容器里的迭代器辅助结构、状态机里的状态类等。它对隐藏实现细节非常顺手。

**Q5：异常处理和 if 判断错误哪个更好？性能差别大吗？**
A：分工不同不是替代关系。高频、可预期、调用方必然要处理的失败（查找未命中）用返回值+if；低频、跨层、需要立刻脱离正常流程的异常（磁盘满、网络断、参数非法）用异常。性能上现代实现多为"零成本抽象"（landing pad 表）：**不抛时几乎无开销，抛出时才付栈展开的昂贵代价**（搜索+析构，比一次函数调用贵几个数量级）。所以铁律：不要用异常当普通控制流（别拿 throw 当 goto 用），也别指望它在每秒百万次的热路径里报错。

## 5. 课件类型专项补充

### 5.1 异常规格（Exception Specification）的演进

| 时代 | 写法 | 语义 | 现状 |
|------|------|------|------|
| C++98/03 | `void f() throw(A, B);` | 只允许抛 A/B，别的会被转成 bad_exception（实现常直接 terminate） | **已废弃**：运行时检查、开销大、表达力差、几乎没人用对 |
| C++98/03 | `void f() throw();` | 承诺绝不抛 | 保留但弃用 |
| C++11 | `void f() noexcept;` | 承诺绝不抛，违反直接 terminate（编译期可知） | **现行标准**；`noexcept` 还是运算符可用于查询 |
| C++17 | noexcept 进入**类型系统** | `void()noexcept` 与 `void()` 是不同类型，参与重载/特化匹配 | 泛型库据此优化（vector 扩容移动是否 noexcept 决定用 move 还是 copy） |

为什么动态规格被抛弃而 noexcept 留下：前者是运行期检查（慢且行为混乱），后者是编译期契约（快，且能让 std::move、allocator、容器策略做出更好的静态决策）。**教材 P17 的 `what() const throw()` 的现代替代方案就是 `what() const noexcept override`**——本笔记所有新写示例均已采用，并在知识点 6 的富上下文异常类里给出两者并存展示。

### 5.2 标准库容器的异常安全承诺

三级保证已在专题 B 列出。补充查阅方法：cppreference 每个容器函数条目都有"Exception safety"小节，例如 `vector::push_back` 注明强保证（分配失败抛 bad_alloc 时容器不变），`at()` 注明越界抛 `std::out_of_range`。养成习惯：**学 STL 每个容器先看异常承诺，再决定 try 包在哪一层。**

### 5.3 assert 与异常的区别

对照表见专题 B 末。一句话裁决：**assert 防的是"程序员写错代码"（Debug 抓现行，Release 隐身），异常处理的是"世界不如你所愿"（任何构建都在线）。生产校验逻辑永远不要只依赖 assert。**

| 2 | `catch(exception e)` 后 e.what() 显示 `std::exception` | 值接收发生对象切片，派生子对象被削掉 | `catch(const exception& e)` | 丢失多态与自定义信息 |
| 3 | 析构函数里 throw 后程序直接暴毙 | 栈展开中双异常在飞 → std::terminate | 析构内 try-catch 内部消化 + `noexcept` | 原异常也没人处理，进程崩溃 |
| 4 | `throw "err";` 用 `catch(exception&)` 接不住而 terminate | 类型严格匹配：const char* 与 exception 无继承关系 | `catch(const char* msg)` 或改抛异常类 | 程序无法正常结束（P13 同款） |
| 5 | 以为写了 try-catch 就能接住整数除 0 | 硬件级错误不是 C++ 异常 | 先 `if(b==0) throw ...` 自己检测 | catch 形同虚设，程序崩溃 |
| 6 | 浮点除 0 没崩溃就以为没问题 | IEEE 754 给出 inf/nan 静默扩散 | 检测分母为 0 主动抛出 | 错误值流入后续计算，脏数据难查 |
| 7 | `catch(...)` 放最前 | 它与一切类型兼容，吞掉全部异常 | `...` 只放最后 | 后面所有 catch 变死代码 |
| 8 | throw 后还写清理语句 | 抛出即离开本函数，后续不执行 | 清理交给 RAII 对象析构 | 裸 new 的资源泄漏 |
| 9 | `char buf[64]; return buf;` 式 what() | 返回栈数组地址，出函数即悬垂 | 字面量或成员 string 的 c_str() | 未定义行为，乱码/崩溃 |
| 10 | `char* what()` 或忘写 const | 不构成重写，只是新增函数 | `const char* what() const noexcept override` | 派生消息永远显示不出来 |
| 11 | 外部裸写 `InnerClass ic1;` | 嵌套类名藏在外围类作用域 | `OuterClass::InnerClass ic1;` | 编译错误 not declared |
| 12 | 局部类成员函数写到类外 `void L::f(){}` | 局部类出了函数就不存在 | 全部类体内实现 | 编译错误 |
| 13 | 只 throw 不 catch 就跑演示 | 无人接球 | 每个 throw 配对应层 catch 或上层兜底 | terminate（P13 教学正身） |
| 14 | `new` 失败判 nullptr | 默认 operator new 抛 bad_alloc | try-catch bad_alloc 或 `new(nothrow)` | 判断永假，错误处理缺失 |
| 15 | 用异常做常规控制流（循环里抛） | 抛出路径要走栈展开，开销巨大 | 常规失败用返回值 | 性能雪崩 + 可读性崩坏 |

## 附录 A：教材作业参考答案（P32-P33 原文）

**(1) 什么叫异常处理?**
答：异常处理是一种程序定义的错误，它对程序的逻辑错误进行设防，并对运行异常加以控制。在 C++ 中，异常处理是对所能预料的运行错误进行处理的一套实现机制。

**(2) C++ 的异常处理机制有何优点?**
答：C++ 的异常处理机制使得异常的引发和处理不必在同一函数中。C++ 异常处理的目的是在异常发生时，尽可能地减小破坏，周密地善后，而不影响其他部分程序的运行。这样底层的函数可以着重解决具体问题，而不必过多地考虑对异常的处理。上层调用者可以在适当的位置设计对不同类型异常的处理，这在大型程序中是非常必要的。
