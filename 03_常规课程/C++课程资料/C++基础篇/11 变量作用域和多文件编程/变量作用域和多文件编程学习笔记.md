## 三、模块一：作用域概念 + typedef声明（《11.1》P1–P7）

### 知识点 1　作用域的概念（《11.1变量作用域》P1–P5）【了解】

#### ① 是什么

**一句话定义**（课件 P4 原文）：C++ 中的一个**变量或常量在程序中都有一定的作用范围，称之为作用域（scope）**。

**生活化比喻**：作用域就像**工牌权限**。你在 A 栋刷工牌能进所有楼层，但在 B 栋你的工牌根本不认识你——不是牌子消失了，而是**那个空间不认这个名字**。变量的"名字能被谁读到"，就是它的权限范围。

补充一层（同页课件）：**变量定义的作用是给一段指定的内存空间起名，方便操作这段内存**，相当于"给某块内存起了个别名"。语法：

```cpp
数据类型 变量名 = 值;    // 例如 int age = 20;
```

并且（P5）基本变量类型有 `int`、`float`、`char`、`double` 等，**变量类型不同占有内存的字节数不同**——这也是"给内存起名"时必须先说清类型的根本原因：类型决定了这块内存有多大、里面的比特该怎么解读。

#### ② 为什么（追问 3 层）

1. **为什么不设计成"所有变量全程序可见"？** 因为几百个变量共用一张全局名单，重名冲突会让程序根本无法编写。
2. **为什么"限制可见范围"就能解决冲突？** 因为不同函数、不同 `{}` 是相互独立的命名区域，同名 `i` 在两个循环里互不干扰。
3. **为什么还要区分生命周期？** 因为可见性解决"能不能写这个名字"，而生命周期解决"这块内存还在不在"。二者共同决定变量的行为，缺一不可——这正是模块二三类变量的分类依据。

**价值总结**：作用域机制同时解决三件事——**避免命名冲突、控制可见性（封装）、约束内存回收时机**。

#### ③ 怎么用

作用域在 C++ 中以**一对花括号 `{}` 为一个边界**（块作用域），层层嵌套：内层可看外层，外层看不到内层。

```cpp
#include <iostream>
using namespace std;

int main() {
    int outer = 1;                     // 块1：main 的作用域
    {
        int inner = 2;                 // 块2：内层新作用域
        cout << outer + inner << endl; // 内层可以读外层变量
    }                                  // 块2 结束，inner 到此为止
    // cout << inner;                  // 错误！inner 不在作用域内，编译不过
    cout << "outer still alive:" << outer << endl;
    return 0;
}
// 输出：
// 3
// outer still alive:1
```

**人话总结**：作用域就是"这个名字在这儿好不好使"。

#### ④ 注意事项 / 常见错误示范

```cpp
// ❌ 错误示范 1：以为出了 {} 变量还能用
for (int i = 0; i < 3; i++) { /* ... */ }
cout << i;              // 编译错误：'i' was not declared in this scope

// ❌ 错误示范 2：以为"看得见"等于"还活着"
// 全局变量在整个文件都看得见；但函数返回其局部变量的指针后，
// 名字可能还能间接访问（悬垂指针），内存却已回收 —— 未定义行为
int* bad() { int x = 10; return &x; }   // x 出函数即销毁，指针失效
// ✅ 正确写法：需要跨函数存活的数据，交给 static、全局变量或动态内存(new)
```

> ⚠️ **教材排版提醒**：本课件 P4/P9/P11/P21 的示例代码里出现了中文全角符号（`；`、`（）`、`“”`）。这些是排版笔误，**照抄到源文件里一定编译失败**，务必改成半角 `;` `()` `""`。

### 知识点 2　typedef 声明（《11.1变量作用域》P6–P7）【了解】

#### ① 是什么

**一句话定义**（课件 P6）：`typedef` 用来**为复杂的声明定义简单的别名**，它与宏定义有些差异；它本身是一种**存储类关键字**，因此**不能与 `auto`、`extern`、`mutable`、`static`、`register` 出现在同一个表达式（声明式）中**。

**生活化比喻**：`typedef` 是给类型**办张副卡**。主卡（`int`）还在、额度不变，只是多了一个名字（`abc`）能刷同一张卡。它**不产生新类型**，也不产生新内存。

课件 P6 的四条性质（原文要点）：

1. `typedef` 可以声明各种类型名，但**不能用来定义变量**；
2. 用 `typedef` 只是对已经存在的类型**增加一个类型名**，**不能创造新的类型**；
3. 当在不同源文件中用到同一类型数据（尤其是像数组、指针、结构体、共用体等类型数据）时，常用 `typedef` 声明一些数据类型，以**提高编程效率**；
4. `typedef` 有利于程序的**通用与移植**。有时程序会依赖于硬件特性，用 `typedef` 便于移植。

#### ② 为什么（追问 3 层）

1. **为什么要给类型起别名？** 复杂类型名太长太绕（函数指针、模板、结构体）。
2. **为什么绕就要改名？** 因为可读性直接影响维护成本，`FuncPtr f;` 比 `void (*f)(int,int);` 好读十倍。
3. **为什么改名还有利于移植？** 因为换平台时只需修改 `typedef` 那一行（如 `typedef long long Int64;`），业务代码一行不动。

#### ③ 怎么用

课件 P7 语法：

```cpp
typedef int abc;     // 给 int 起别名 abc
abc   num = 1;       // 等价于 int num = 1; 创建了一个 int 类型变量并赋值 1
```

下面是可直接运行的完整版，覆盖"简化复杂类型"与"跨文件共享类型"两大典型场景：

```cpp
#include <iostream>
#include <string>
using namespace std;

typedef int abc;                          // 课件 P7 原始例子
typedef unsigned char Byte;               // 场景1：语义化短名
typedef void (*FuncPtr)(int, int);        // 场景2：函数指针（最难记的一类）
struct Student { int id; string name; };  // 场景3：结构体省掉重复书写
typedef Student Stu;

void add(int a, int b) { cout << a + b << endl; }

int main() {
    abc x = 7;                            // x 的类型就是 int
    Byte b = 'A';                         // unsigned char
    FuncPtr f = add;                      // 用别名声明函数指针，清爽
    f(3, 4);
    Stu s{1001, "Zhang"};                 // C++ 里 struct 名本身即类型名
    cout << x << " " << (int)b << " " << s.id << " " << s.name << endl;
    return 0;
}
// 输出：
// 7
// 7 65 1001 Zhang
```

**行为发生在编译期**：`typedef` 是纯粹的**类型别名替换**，编译器在语义分析阶段就把 `abc` 归一成 `int`，生成的机器码里没有任何 `abc` 的痕迹，**零运行时开销**。

#### ④ C 语言写法 vs C++ 写法（专项要求）

| 维度 | C 语言写法 | C++ 写法 | C++ 的改进 |
|------|-----------|----------|-----------|
| 定义别名 | `typedef int abc;` | 同左（兼容）＋ `using abc = int;`（C++11） | `using` 方向更直观："abc 就是 int" |
| 结构体别名 | `typedef struct S {...} S;`（必须双写） | `struct S {...};` 直接可用 | C++ 中 `struct` 名自动成为类型名，不再强制 `typedef` |
| 模板别名 | ❌ 不支持 | `template<class T> using Vec = std::vector<T>;` | `using` 可与模板结合，`typedef` 不行 |
| 宏伪装别名 | `#define ABC int`（纯文本替换，易出错） | `typedef` / `using` 有类型检查 | 作用域可控、能被调试器识别 |

```cpp
#include <iostream>
using namespace std;

using abc   = int;   // C++11 起推荐写法，与 typedef int abc; 完全等价
using MyInt = int;   // 读作 "MyInt 是 int"

int main() {
    MyInt y = 9;
    abc   z = y + 1;
    cout << z << endl;
    return 0;
}
// 输出：
// 10
```

**`using` 的三点优势**：① 赋值式语法符合直觉，复杂声明不再"内外反转"；② 支持模板别名（alias template）；③ 在 IDE 里更容易被正确解析和跳转。现代 C++ 项目中新代码普遍首选 `using`。

**常见错误示范**：

```cpp
// ❌ 错误 1：想用 typedef 造一个"新类型"（做单位检查）
typedef int Meter;
typedef int Second;
void f(Meter m);
f(Second{3});         // 能编译通过！Meter 和 Second 是同一个类型 int
                      // typedef 不提供类型安全，只是别名

// ❌ 错误 2：typedef 与存储类关键字混用（课件 P6 明确禁止）
static typedef int abc;   // 编译错误：typedef 不能与 static 同现

// ❌ 错误 3：拿 typedef 去定义变量
typedef int cnt = 5;      // 编译错误：typedef 只声明类型，不创建对象
```

**人话总结**：typedef 是给类型办副卡，不多占一字节。


## 四、模块二：局部/全局/静态变量 + C++存储类（《11.1》P8–P21）

> 本模块是全章的重头戏（两个【重点】+ 两个【熟悉】），也是面试出题率最高的区域。学之前先把这张总表放在手边：

| 对比项 | 局部变量（auto） | 全局变量 | 静态局部变量（static） |
|--------|-----------------|----------|----------------------|
| 定义位置 | 函数体内 / `{}` 内 | 所有函数体外 | 函数体内，加 `static` |
| 作用域 | 所在块（`{}`）内 | 声明处 → 文件末尾 | 所在函数内（**不变！**） |
| 生命周期 | 进入块 → 离开块 | 整个程序运行期 | 整个程序运行期 |
| 存储位置 | 栈区（stack） | 静态存储区 | 静态存储区 |
| 未初始化默认值 | 不确定（垃圾值） | 零初始化 | 零初始化 |
| 初始化次数 | 每次进入都执行 | 程序启动前一次 | **仅第一次经过时一次** |
| 跨函数共享 | ❌ | ✅（本文件内；配 `extern` 可跨文件） | ❌（只有本函数能用） |
| 链接性 | 无 | 外部链接 | 名字不进外部符号表 |

### 知识点 3　局部变量（《11.1变量作用域》P8–P9）【重点】

#### ① 是什么

**一句话定义**（课件 P8 原文）：**在函数内部声明/定义的变量叫局部变量，局部变量的作用域仅限于函数内部。** 同时，在函数内部定义的变量、函数的**参数**和**返回值**、`if` 和 `for` 结构内部使用的变量等**都是局部变量**。

三条附加规则（同在 P8）：

- **当存在全局变量和局部变量同名的时候，在函数内，局部变量会覆盖全局变量**；
- **使用 `{}` 可以限制变量的作用域**；
- 课件 P9 案例中，被注释掉的 `//cout << "num = " << num << endl;` 之所以必须注释，正是因为 `num` 已在上一行的 `}` 处离开作用域。

**生活化比喻**：局部变量是**会议白板笔**。开会（进入函数）时拿出来用，散会（退出函数）就擦掉放回抽屉；下次开会是一支全新的空白笔——**不会记得上次写了什么**。

#### ② 为什么（追问 3 层）

1. **为什么函数内的变量要是局部的？** 为了函数之间互不污染，调用者不必担心被被调函数改掉自己的数据。
2. **为什么"用完即焚"是好事？** 因为栈上内存能自动回收，函数递归一万层也不会泄漏（每层的 `i` 各自独立）。
3. **为什么又要允许同名覆盖？** 因为写函数的人不应该知道外面有多少全局变量，"就近原则"让函数内部的命名自由且可预测。

#### ③ 怎么用

**示例 1：课件 P9 原案例（补全为可运行版本）**

```cpp
#include <iostream>
using namespace std;
int main() {
    cout << "测试局部变量" << endl;
    {                              // 手动加一对花括号，专门用来限制作用域
        int num = 100;             // num 是这个块内的局部变量
        cout << "num = " << num << endl;
    }                              // ← 走出这个 } ，num 就地销毁
    // cout << "num = " << num << endl;   // 若取消注释：编译错误
    return 0;                      // 'num' was not declared in this scope
}
// 输出：
// 测试局部变量
// num = 100
```

**示例 2：三层作用域嵌套 + 同名覆盖（本章第一大考点）**

```cpp
#include <iostream>
using namespace std;

int v2 = 121;                       // 全局变量（定义在所有函数之外）

int main() {
    int v2 = 100;                   // main 的局部变量，遮蔽（shadow）全局 v2
    if (1 > 0) {                    // if 块内又是新的一层作用域
        int v2 = 10;                // 再次遮蔽，此刻有三层同名 v2 同时存在
        cout << "v2 if:"    << v2    << endl;   // 就近原则 → 最内层的 10
    }                               // 内层 v2 消亡
    cout << "v2 main:"   << v2   << endl;       // 回到 main 层 → 100
    cout << "v2 global:" << ::v2 << endl;       // :: 作用域解析运算符，显式取全局
    return 0;
}
// 输出：
// v2 if:10
// v2 main:100
// v2 global:121
```

**逐行走读（按课件专项要求，逐行说明程序状态变化）**：

- 第 4 行：程序启动，全局 `v2` 在**静态区**被分配并初始化为 `121`，生命周期从现在开始直到进程结束。
- 第 6–7 行：`main` 开始执行，栈帧建立；第 7 行在**栈上新建一个 int 并写入 100**，变量名 `v2`。此时符号查找表里有两条 `v2`（内层 100、外层 121），**编译器规定名字解析取最内层**，于是此后写在 `main` 里的裸 `v2` 一律指 100。
- 第 8–9 行：进入 `if` 块，**再新建一个栈变量 `v2 = 10`**（与前两个是完全不同的三块内存）。
- 第 10 行：`cout << v2` → 名字解析命中最内层，**读出值为 10**，因为就近原则。打印 `v2 if:10`。
- 第 11 行：遇 `}`，**内层 v2 的生命周期结束**（栈指针回退，那块内存标记为可复用，值不再有意义）。
- 第 12 行：`cout << v2` → 现在最内层只剩 `main` 的那个，**读出值为 100**。打印 `v2 main:100`。
- 第 13 行：写成 `::v2`，前缀 `::` 表示"跳过所有局部层，直接到全局命名空间找"，**读出值为 121**。打印 `v2 global:121`。
- 第 14 行：`return 0`，`main` 的 `v2` 随栈帧销毁；随后运行时库回收静态区的 `::v2`，进程结束。

**关键点**：`v2 if:` 那行的 `10` 从来就没有"变回"过 100——不是赋值覆盖了谁，而是**三个独立变量恰好同名**，编译器在不同行选择了不同解释。

**示例 3：循环变量与"看不见的兄弟"**

```cpp
#include <iostream>
using namespace std;
int main() {
    for (int i = 0;  i < 3;  i++) { cout << "A:" << i << " "; }  // i 属于 for 自己引入的块
    for (int i = 10; i < 13; i++) { cout << "B:" << i << " "; }  // 又一个全新 i，合法
    cout << endl;
    // cout << i;                                                // 错误：两个 i 都已销毁
    return 0;
}
// 输出：
// A:0 A:1 A:2 B:10 B:11 B:12
```

#### ④ 注意事项 / 常见错误示范

```cpp
// ❌ 错误 1：同名覆盖导致的"逻辑串台"（最常见 bug 之一）
int total = 0;
void accumulate() {
    int total = 0;        // 手滑又写了一遍声明！
    total += 100;         // 改的是局部 total，全局 total 一直是 0
}                         // 局部 total 销毁，100 凭空蒸发
// ✅ 正确：删掉重复声明；或显式写 ::total += 100;

// ❌ 错误 2：使用未初始化的局部变量
int flag;                 // 栈上垃圾值，每次运行都可能不同
if (flag == 0) { /*...*/ }// 行为不可预测（未定义行为）
// ✅ 正确：int flag = 0;   —— 局部变量没有"编译器默认值"

// ❌ 错误 3：返回局部变量的地址/引用
int& ref() { int x = 5; return x; }   // 悬垂引用
// ✅ 正确：按值返回，或改用 static / new / 传入输出参数

// ❌ 错误 4：以为参数是"共享"的
void modify(int n) { n = 999; }       // 只改了副本
int main() { int v = 1; modify(v); cout << v << endl; }
// 输出：1                             —— 想改传引用 int& 或指针
```

**口诀**：**局部变量一出栈，人间蒸发不回头；同名先找最近层，够不着再加 `::`。**

**人话总结**：局部变量只管这一亩三分地，出了花括号就作废。

### 知识点 4　全局变量（《11.1变量作用域》P10–P11）【重点】

#### ① 是什么

**一句话定义**（课件 P10 原文）：**在函数外部声明/定义的变量叫全局变量，C++ 全局变量作用域在整个文件都有效。**

精确一点：**作用域从"声明处"开始，到"文件末尾"结束**——写在中间的全局变量，它上面的函数是看不见它的。

**生活化比喻**：全局变量是**小区公告栏**。公告一旦贴上（越过声明行），之后路过的所有人（后续函数）都能看、都能改；但也正因为人人能改，贴久了内容经常对不上账——这就是它的风险。

配套讲义 `全局和局部变量作用域及生命周期.txt` 的原文要点（正好对应本知识点）：

> 所谓全局变量，一般是指函数外部定义的（独立于函数内部，独立于代码文件的代码），……不受其影响（也就是说，全局变量的生存期一直到**程序的结束**）。如果要在**另外一个文件**中使用该另一个文件中存在的全局变量，那么可以使用 **`extern`** 关键字，这样另外一个文件就可以使用该数据了。

#### ② 为什么（追问 3 层）

1. **为什么需要全局变量？** 有些数据天然属于"整个程序的状态"（配置、计数器、日志句柄），不该在每个函数间手工传递。
2. **为什么默认只在"文件内有效"而不是"全程序有效"？** 因为默认只在**本翻译单元**可见，可以避免不同模块的同名变量互相打架；真需要跨文件时再用 `extern` 显式打开——**默认封闭、按需开放**。
3. **为什么讲师要强调"滥用风险"？** 因为任何一个函数都能悄悄改写它，导致"我在 A 函数打了断点，值却在 B 函数被改了"的排查地狱，同时破坏函数的可测试性（同样的输入可能给出不同输出）。

#### ③ 怎么用

**示例 1：课件 P11 原案例（修正全角符号后可运行）**

```cpp
#include <iostream>
using namespace std;

int num = 100;                     // 全局变量：定义在所有函数之外

void test() {                      // test 写在 num 之后，所以能直接用
    cout << "test func print num = " << num << endl;
}

int main() {
    cout << "测试全局变量" << endl;
    cout << "num = " << num << endl;
    cout << "------------------------------" << endl;
    test();
    return 0;
}
// 输出：
// 测试全局变量
// num = 100
// ------------------------------
// test func print num = 100
```

**示例 2：全局变量的"声明处才生效"规则**

```cpp
#include <iostream>
using namespace std;

void early() { /* cout << g; */ }   // ❌ 此处若写 g 编译不过：还没"出生"

int g = 5;                          // 全局变量声明处（作用域从这里才开始）

void late()  { cout << "late sees g=" << g << endl; }   // ✅ 能看见

int main() { late(); cout << "main g=" << g << endl; return 0; }
// 输出：
// late sees g=5
// main g=5
```

**示例 3：跨文件访问全局变量（对应 `extern`，也为模块三铺垫）**

`global_a.cpp`：

```cpp
#include <iostream>
using namespace std;
int total = 0;              // 【定义】真正的内存在这里分配（全程序只能有一处定义）
void addTotal();            // 供另一文件调用的函数声明
int main() {
    addTotal(); addTotal();
    cout << "a.cpp 看到的 total = " << total << endl;
    return 0;
}
```

`global_b.cpp`：

```cpp
extern int total;           // 【声明】告诉编译器：total 定义在别的文件，链接时去找
void addTotal() { total += 5; }
```

```bash
# 编译命令（两个 .cpp 一起交给编译器，才能完成链接）
g++ -std=c++11 global_a.cpp global_b.cpp -o app && ./app
```

```text
// 输出：
// a.cpp 看到的 total = 10
```

**逐行走读**：`global_a.cpp` 第 3 行的 `total` 位于静态区，初值 0；`global_b.cpp` 第 1 行的 `extern int total;` **不分配任何内存**，只是登记一个"待链接的外部符号"；两次 `addTotal()` 后静态区那块内存从 `0 → 5 → 10`；`main` 读到的正是同一块内存，因此打印 10。这印证了"全局变量存放在静态区、生命周期贯穿全程、可通过 `extern` 跨文件共享"三条结论。

**内存布局示意图（ASCII，栈区 vs 静态区）**：

```
        高地址
   ┌──────────────────────────────┐
   │  全局/静态存储区               │  ← 程序启动前完成初始化，进程结束才整体释放
   │  ┌────────┬────────┬───────┐ │
   │  │ ::v2   │  num   │ total │ │     值：121      100      0
   │  │(全局)  │(全局)  │(extern│ │     生命周期：整个程序运行期
   │  │        │ 共享)  │ 引用) │ │     链接性：外部链接（可被 extern 引用）
   │  └────────┴────────┴───────┘ │
   ├──────────────────────────────┤
   │  常量区 / 代码区（只读）        │  ← 字符串字面量、机器指令
   ├──────────────────────────────┤
   │           （空闲）             │
   ├──────────────────────────────┤
   │  栈区  ↓ 向低地址增长           │  ← 局部变量、函数参数；进出作用域自动分配/回收
   │  ┌────────────────────────┐  │
   │  │ main 栈帧: v2 = 100     │  │   生命周期：进入 main → return
   │  ├────────────────────────┤  │
   │  │ if 块:   v2 = 10        │  │   生命周期：进入 { → 遇到 }
   │  ├────────────────────────┤  │
   │  │ （未使用）↓              │  │
   │  └────────────────────────┘  │
   ├──────────────────────────────┤
   │  堆区  ↑ 向高地址增长           │  ← new / malloc 所得，程序员手动管理
   └──────────────────────────────┘
        低地址
```

#### ④ 注意事项 / 常见错误示范

**全局变量滥用风险清单**：

| 风险 | 具体表现 | 缓解做法 |
|------|---------|---------|
| 隐式耦合 | 改一个字段要翻遍全项目找谁在读 | 收拢为类的私有成员 + getter/setter |
| 难以测试 | 单元测试互相污染，必须按顺序跑 | 测试前后重置状态，或用依赖注入 |
| 并发不安全 | 多线程同时 `count++` 丢更新 | 加锁 / `std::atomic` |
| 初始化顺序不定 | 跨文件全局对象构造顺序无保证（Static Initialization Order Fiasco） | Meyers' Singleton（函数内 `static` 局部对象） |
| 命名污染 | 多个 `.cpp` 同名全局符号 → 链接冲突 | 匿名命名空间 / `static` 修饰 / 放进类里 |

```cpp
// ❌ 错误 1：在头文件里"定义"全局变量（本章第一高频事故）
// config.h
int maxUsers = 100;        // 这是定义！被 a.cpp 和 b.cpp 各 include 一次
                           // → 链接期 error: multiple definition of `maxUsers'
// ✅ 正确：头文件放声明，某一个 .cpp 放唯一一份定义
// config.h  : extern int maxUsers;
// config.cpp: int maxUsers = 100;

// ❌ 错误 2：extern 声明与定义类型不一致
// a.cpp: double price = 9.9;
// b.cpp: extern int  price;      // 能编译过，链接也能过（名字相同），
                                 // 但按 int 去读 double 的 8 字节 → 垃圾值，极难排查
// ✅ 正确：两边类型严格一致；更好做法是把声明写进公共头文件，两边都 include

// ❌ 错误 3：想在前面的函数里用后面的全局变量
void f() { cout << g; }     // error: 'g' was not declared in this scope
int g = 1;
// ✅ 正确：把全局变量声明提到文件顶部，或在函数前写 extern int g;

// ❌ 错误 4：extern 的同时还初始化
extern int v1 = 0;          // 课件 P19 这样写，但请注意：一旦加了初始化，extern 就失效，
                            // 这仍然是【定义】而非声明
// ✅ 正确：定义处写 int v1 = 0;，声明处写 extern int v1;
```

**人话总结**：全局变量是公告栏，好用但别贴满墙。

### 知识点 5　静态变量（《11.1变量作用域》P12–P13）【熟悉】

#### ① 是什么

**一句话定义**（课件 P12 原文压缩）：静态存储区的变量在**程序刚开始的时候就完成初始化，也是整个程序生命周期的唯一一次初始化**；静态存储区中一般存储两种变量——**`static` 变量和全局变量**。当 `static` 修饰函数内的局部变量时，**作用域只在其函数内，但是生存周期为整个源程序**：即只可以在定义该变量的函数内进行使用，但是退出该函数后，该变量一直存在，但不可以进行使用。

**生活化比喻**：静态局部变量是**实验室里那台公用显微镜**。它放在实验楼（程序）的地下一层（静态区），不是谁的私人物品（只有本实验台的钥匙 = 作用域仅限本函数），但你明天回来它还在那儿、示数还是昨天调好的（生命周期全程、保留上次值）。

#### ② 为什么（追问 3 层）

1. **为什么需要"活得久但藏得深"这种变量？** 因为既要跨调用保存状态，又不希望被别的函数乱改。
2. **为什么不用全局变量代替？** 全局变量谁都能改；`static` 局部变量把状态锁在唯一的宿主函数里，等于"自带私有属性的迷你对象"。
3. **为什么"只初始化一次"这么重要？** 因为它让函数能自我记忆：计数器、缓存、单例、斐波那契备忘录、ID 发号器全都靠这一条。

#### ③ 怎么用

**示例 1：课件 P13 原案例（修正 `mian`→`main`、全角分号后完整可运行）**

```cpp
#include <iostream>
using namespace std;

int num = 1;                    // 全局 num，初值 1

int func() {
    static int num = 5;         // 首次进入函数时 num 初始化；后面再进入函数时 num 不会被初始化
    return num--;               // 后置--：先返回当前值，再把 num 减 1
}

int main() {
    for (; num <= 5; num++) {   // 用的是全局 num（func 内的 num 看不见）
        cout << num << "---" << func() << endl;
    }
    return 0;
}
// 输出：
// 1---5
// 2---4
// 3---3
// 4---2
// 5---1
```

**逐行走读（重点看两个同名 `num` 各自的命运）**：

| 时刻 | 全局 `::num` | 静态区 `func::num` | 本轮输出 | 说明 |
|------|-------------|-------------------|---------|------|
| 程序启动 | 1 | **5**（初值在编译期就烧进可执行文件的静态数据段，加载时就位） | — | 静态区一次性初始化 |
| 循环第 1 轮判断/打印 | 1 | 5 | `1---5` | `func` 返回 5，随后静态 num 变为 4 |
| `num++` 之后 | 2 | 4 | — | 自增的是**全局** num |
| 循环第 2 轮 | 2 | 4 → 3 | `2---4` | 静态 num **没有**被重置回 5 |
| 第 3 / 4 / 5 轮 | 3→4→5 | 3→2→1，最后 0 | `3---3` `4---2` `5---1` | 两个 num 同步递减，故数值恰好相等 |
| 循环退出判断 | 6 | 0 | — | `6 <= 5` 为假，退出 |

这个例子的精妙之处在于：**左边一列走的是全局变量，右边一列走的是静态局部变量**，两者同名却毫无关系；而 `func::num` 之所以能一路 5→4→3→2→1，全靠"只初始化一次"。

**示例 2：课件 P17 的 static vs 普通局部（v1/v2 对照）**

```cpp
#include <iostream>
using namespace std;

void func() {
    static int v1 = 0;          // 静态区，只初始化一次，跨调用保值
    int          v2 = 0;        // 栈，每次进来都被重新写成 0
    v1++;
    v2++;
    cout << "v1=" << v1 << "  v2=" << v2 << endl;
}

int main() { func(); func(); func(); return 0; }   // 多调用几次 func 函数
// 输出：
// v1=1  v2=1
// v1=2  v2=1
// v1=3  v2=1
```

**`v2` 永远等于 1**，是"每次调用重新初始化 + 加一次"的必然结果；**`v1` 单调递增**，是"只初始化一次 + 保值"的必然结果。这两行输出之差，就是 `static` 关键字的全部含义。

**示例 3：实战——发号器（ID Generator）**

```cpp
#include <iostream>
using namespace std;

int nextId() {
    static int id = 1000;       // 只有本函数能碰它，外部无从篡改
    return id++;                // 每次调用返回一个更大的编号
}

int main() {
    cout << nextId() << " " << nextId() << " " << nextId() << endl;
    return 0;
}
// 输出：
// 1000 1001 1002
```

**`static` 变量存储位置示意（静态区放大图）**：

```
   全局/静态存储区（程序启动时整体就绪，进程结束时整体回收）
   ┌──────────────────────────────┬──────────┬──────────────┬──────────────┐
   │ 变量                          │  初值     │  作用域        │  生命周期      │
   ├──────────────────────────────┼──────────┼──────────────┼──────────────┤
   │ ::num      （全局变量）         │    1     │ 本文件全部      │ 全程           │
   │ func::num  （static 局部）★    │    5     │ 仅 func 内 ★   │ 全程 ★         │
   │ func::v1   （static 局部）     │    0     │ 仅 func 内     │ 全程           │
   │ nextId::id （static 局部）     │ 1000     │ 仅 nextId 内   │ 全程           │
   └──────────────────────────────┴──────────┴──────────────┴──────────────┘
        ★ = 关键反差：内存一直都在，名字却只在函数内好使
   --------------------------------------------------------------
   栈区（每次调用 func 新开一个栈帧）
   ┌──────────────────────────────┐
   │ func 栈帧: v2 (=0，每次重写)   │  ← 出函数即销毁
   └──────────────────────────────┘
```

**关于线程安全（课件未提，但必须知道的现代 C++ 事实）**：C++11 起，`static` 局部变量的**初始化**由标准保证线程安全（magic statics），并发首次调用只有一个线程执行初始化，其余线程等待。但**"读改写"操作（如 `id++`）依然不安全**——安全性只覆盖初始化那一刻。

#### ④ 注意事项 / 常见错误示范

```cpp
// ❌ 错误 1：以为每次调用都会重新初始化
int counter() { static int n = 0; return ++n; }
// 有人据此认为连续调用得到 1,1,1 —— 实际得到 1,2,3
// ✅ 认知纠正：初始化只在第一次经过该行时执行

// ❌ 错误 2：想"重置" static 却没有入口
void resetCounter() { /* 无法访问 counter() 里的 n！ */ }
// ✅ 正确：提供显式接口
int counter(bool reset = false) {
    static int n = 0;
    if (reset) n = 0;            // 需要重置时手动赋值
    return ++n;
}

// ❌ 错误 3：把 static 理解成"扩大了作用域"
static int hidden = 1;
void other() { cout << hidden; }   // 能访问，但原因是"它在同一文件的全局区"，
                                   // 不是因为 static —— static 只会【缩小】链接可见性
// ✅ 认知纠正：函数外的 static = 限制到本文件（内部链接）；函数内的 static = 延长生命周期

// ❌ 错误 4：多线程下把 static 局部当裸计数器用
// 多个线程同时 value = counter();  结果丢失更新（数据竞争，未定义行为）
// ✅ 正确：std::atomic<int> 或加 std::mutex

// ❌ 错误 5：static 修饰数组时想当然
static int buf[10];   // OK，整个数组在静态区，长度固定
// 但别指望它能像 vector 一样自动扩容 —— 静态区大小在编译期就定了
```

**口诀（务必背下来）**：**static 记三特——特久（生命周期贯穿全程）、特独（只初始化一次）、特小（作用域一点都不变大）。**

**人话总结**：static 让变量活得久，但没让它管得宽。

### 知识点 6　C++ 存储类（《11.1变量作用域》P14–P21）【熟悉】

#### ① 是什么

**一句话定义**（课件 P14 原文）：**存储类用于定义 C++ 程序中变量和函数的生命周期和可见性。寿命是指变量保持活动的时间段，可见性是指可访问变量的程序的模块。**

课件列出 **五种类型的存储类，可以在 C++ 程序中使用**：

| # | 中文名 | 关键字 | 一句话职责 |
|---|--------|--------|-----------|
| 1 | 自动 Automatic | `auto` | 局部变量的默认存储类（栈，进出块生死）；C++11 后含义改为类型推导 |
| 2 | 寄存器 Register | `register` | 建议编译器把变量存入寄存器（C++17 起移除） |
| 3 | 静态 Static | `static` | 延长生命周期至全程 / 收紧链接性 |
| 4 | 外部 External | `extern` | 声明"这个符号在别的文件定义"，跨文件共享 |
| 5 | 可变 Mutable | `mutable` | 允许 `const` 成员函数修改的"例外成员" |

**生活化比喻**：存储类是变量的**用工编制**。同样一个人（一块内存），可以是"临时工"（`auto`，项目结束就走）、"编外专家"（`mutable`，制度说不许动但他有特批）、"长期合同工但只属本科室"（`static`）、"借调人员，本地只留联系方式"（`extern`）。

#### ② 为什么（追问 3 层）

1. **为什么要把存储策略做成关键字？** 因为同一份"名字=内存"的语法，需要表达完全不同的时间和可见性语义。
2. **为什么要四种以上？** 因为性能优化（`register`）、模块复用（`extern`）、状态驻留（`static`）、常量语义例外（`mutable`）是四类互不相干的需求。
3. **为什么 `auto` 的含义后来彻底变了？** 因为泛型编程时代"我不想写超长类型名"的需求远大于"我要指定存储类"，委员会判定后者可以废弃、前者价值巨大。

#### ③ 逐个怎么用

##### (1) `auto` 自动存储类（P16）

课件原文：**`auto` 是所有局部变量的默认存储类，`auto` 关键字自动应用于所有局部变量**；上面的例子定义了两个具有相同存储类的变量，**`auto` 只能在函数中使用**。

```cpp
#include <iostream>
using namespace std;
int main() {
    {
        auto int v1;          // C++11 之前合法：显式声明"自动存储类"
        float v2 = 99.1f;     // 同样默认是 auto，无需写出来
        v1 = 5;
        cout << v1 << " " << v2 << endl;
    }
    return 0;
}
// 输出（C++03 编译器）：5 99.1
// ⚠️ 注意：这段代码在 C++11 及以后【编译不过】——见下方"含义改变"
```

**⚠️ `auto` 的含义大转折（本章必考的时代分水岭）**：

| 标准 | `auto` 的含义 | 例子 |
|------|--------------|------|
| C++98/03 | **存储类说明符**：与 `register/static/extern` 并列，表示"自动存储期"，且几乎从不手写（因为是默认值） | `auto int x;` |
| C++11 起 | **类型自动推导**：与存储类彻底无关，编译器根据初始化表达式推断类型 | `auto x = 3.14;`（推导为 double） |
| C++11 起 | 原来的存储类用法被**移除**，`auto int x;` 变成语法错误 | 'auto' type specifier cannot be combined with another type specifier |

```cpp
#include <iostream>
#include <vector>
using namespace std;
int main() {
    auto pi = 3.14;                        // 推导为 double（编译期确定，运行期零开销）
    vector<int> v{1, 2, 3};
    for (auto x : v) cout << x << " ";     // 替代冗长的 iterator 类型名
    cout << endl;
    auto it = v.begin();                   // 推导为迭代器类型
    cout << "size=" << v.size() << " *it=" << *it << " pi=" << pi << endl;
    return 0;
}
// 输出：
// 1 2 3
// size=3 *it=1 pi=3.14
```

**结论**：看到老教材里的 `auto int v1;`，请翻译成"这是一个普通的局部变量"。今天写代码，`auto` 只用于类型推导。

##### (2) `static` 静态存储类（P17）

课件原文：**静态变量只初始化一次，直到程序结束；它保留可在多个函数之间调用的值；静态变量由编译器提供的一个默认值：0。** 示例即知识点 5 的 `v1/v2` 案例（见上文示例 2）。

补充 `static` 的**第三种用途（作用于函数/全局变量时限制链接性）**：

```cpp
#include <iostream>
using namespace std;

static void helper() { cout << "helper 只在本文件可见" << endl; }
static int  secret   = 42;              // 内部链接：别的文件即使写 extern 也拿不到

int main() { helper(); cout << secret << endl; return 0; }
// 输出：
// helper 只在本文件可见
// 42
```

| `static` 出现的位置 | 效果 | 生命周期 | 作用域 | 链接性 |
|--------------------|------|---------|--------|--------|
| 函数内的局部变量 | 保值、只初始化一次 | 全程（**延长**） | 仍限本函数 | 无 |
| 文件作用域的变量/函数 | 隐藏，仅本文件可见 | 全程 | 本文件 | **内部链接**（**收紧**） |
| 类的成员变量 | 属于类而非对象，全类共享一份 | 全程 | 类作用域 | 视定义位置 |
| 类的成员函数 | 无 `this`，只能通过类访问静态成员 | — | 类作用域 | — |

##### (3) `register` 注册存储类（P18）

课件原文：**寄存器变量在寄存器中分配存储器而不是 RAM，其大小与寄存器大小相同，比其他变量具有更快的访问速度。建议仅使用寄存器变量进行快速访问，例如在计数器中。** 语法 `register int count = 0;`。**注意：不能得到寄存器变量的地址。**

```cpp
#include <iostream>
using namespace std;
int main() {
    register int count = 0;        // "建议"编译器放进 CPU 寄存器（也可能被无视）
    for (count = 0; count < 5; count++) cout << count << " ";
    cout << "\n";
    // cout << &count;             // 早期规范禁止：不能对 register 变量取地址
    return 0;
}
// 输出：
// 0 1 2 3 4
```

**⚠️ 演进与废弃情况（专项要求）**：

| 阶段 | `register` 的地位 |
|------|------------------|
| C 语言 | 有效建议，编译器可采纳或忽略；不能对其取地址 |
| C++98/03 | 同上，保留关键字 |
| C++11 | 语义已弱化为"与普通局部变量相同"，但仍可写；对 `register` 参数取地址被禁止 |
| **C++17** | **`register` 作为存储类说明符被彻底移除**，`register int x;` 直接编译错误 |
| C++17 之后 | 仅作为**保留关键字**存在（不能用作标识符） |

```cpp
// C++17 起的错误示范
register int x = 1;      // error: 'register' storage class specifier is deprecated
                         //        and incompatible with C++17（clang 直接报错）
// ✅ 正确做法：什么都不写，把优化交给编译器
int x = 1;               // 现代 GCC/Clang/MSVC 的寄存器分配器远比人工提示聪明
```

**结论**：教学资料里保留 `register` 是为了讲清历史；**新代码一律不要用**，需要热点优化时交给 `-O2`。

##### (4) `extern` 外部存储类（P19）

课件原文：**`extern` 变量对所有程序都可见。如果两个或多个文件共享相同的变量或函数，则使用它。** 课件写法：`extern int v1 = 0;`（注意：带初始化即变成定义，见知识点 4 错误示范 4）。

真正标准的用法（完整两文件示例，与知识点 4 示例 3 同源）：

```cpp
// ---------- file data_def.cpp ----------
#include <iostream>
using namespace std;
int sharedValue = 7;          // 【唯一】定义：分配内存
void showFromElsewhere();     // 前置声明

int main() {
    showFromElsewhere();
    cout << "here: " << sharedValue << endl;
    return 0;
}
```

```cpp
// ---------- file data_use.cpp ----------
extern int sharedValue;       // 【声明】：不分配内存，链接期去别处找
using namespace std;
void showFromElsewhere() { cout << "there: " << sharedValue << endl; }
```

```bash
g++ -std=c++11 data_def.cpp data_use.cpp -o extapp && ./extapp
```
```text
// 输出：
// there: 7
// here: 7
```

**C 与 C++ 的差异**：C 里 `extern` 主要解决跨 `.c` 共享；C++ 额外承担两件事——① `extern "C"` 关闭名称改编（name mangling），让 C++ 能链接 C 库；② `static`/匿名命名空间提供了更好的"文件内私有"手段，`extern` 的使用应更加克制。

```cpp
// 让 C++ 正确调用 C 编译的目标文件（工业项目必备写法）
#ifdef __cplusplus
extern "C" {
#endif
    int c_library_add(int a, int b);   // 这份 .h 同时能被 C 和 C++ include
#ifdef __cplusplus
}
#endif
```

**`extern` 的三个易错点**：① 声明与定义类型不一致（静默错误）；② 在头文件里写 `extern int x = 0;`（变成定义，可能被多文件重复携带）；③ 忘了把对应 `.cpp` 加入编译（`undefined reference to 'sharedValue'`）。

##### (5) `mutable` 可变存储类（课件 P14 列举，正文未展开）

**一句话定义**：`mutable` 只能修饰**类的非 static、非 const 数据成员**，含义是"**即使在 `const` 成员函数里也允许被修改**"——它是常量正确性的一个官方逃生口。

```cpp
#include <iostream>
using namespace std;

class Student {
private:
    int             age;
    mutable int     accessCount;     // "统计/缓存"性质的例外成员
public:
    Student() : age(20), accessCount(0) {}
    void showAge() const {           // const 成员函数：承诺不改对象状态
        // age++;                    // ❌ 编译错误：const 函数不能修改普通成员
        accessCount++;               // ✅ 正确：mutable 成员破例允许
        cout << "age=" << age << ", 被访问次数=" << accessCount << endl;
    }
};

int main() {
    Student s;
    s.showAge(); s.showAge(); s.showAge();
    return 0;
}
// 输出：
// age=20, 被访问次数=1
// age=20, 被访问次数=2
// age=20, 被访问次数=3
```

**为什么需要它**：`showAge()` 逻辑上不改变学生年龄，所以标了 `const`；但"记录被调用几次"属于**观测副作用**，不是对象的业务状态。若没有 `mutable`，就只能把计数塞进全局变量（回到滥用的老路）。典型用途：**惰性缓存、互斥锁成员、访问计数、日志标志**。

**限制与错误示范**：

```cpp
mutable int  x;              // ❌ 编译错误：mutable 只能用于类成员，不能修饰局部/全局变量
const mutable int y = 1;     // ❌ 不能同时 const + mutable
static mutable int z;        // ❌ 不能修饰 static 成员（static 成员本就独立于对象）
```

#### ④ 五种存储类总览速查（本知识点核心表格）

| 存储类 | 出现位置 | 是否分配内存 | 生命周期 | 作用域 | 链接性 | 现代状态 |
|--------|---------|-------------|---------|--------|--------|---------|
| `auto`（旧） | 函数内 | 是（栈） | 块 | 块 | 无 | C++11 起含义改为类型推导 |
| `auto`（新） | 函数内 | 是（栈） | 块 | 块 | 无 | C++11 主流特性 |
| `register` | 函数内/参数 | 通常否（寄存器） | 块 | 块 | 无 | **C++17 移除** |
| `static`（局部） | 函数内 | 是（静态区） | 全程 | 本函数 | 无 | 有效，常用 |
| `static`（文件级） | 函数外 | 是（静态区） | 全程 | 本文件 | 内部链接 | 有效（推荐匿名命名空间替代） |
| `extern` | 任意作用域 | **否**（仅声明） | 全程（在他处） | 声明处起 | 外部链接 | 有效，跨文件必需 |
| `mutable` | 类成员 | 随对象 | 随对象 | 类 | — | 有效，配合 const 成员函数 |

**课堂练习（课件 P20–P21）：利用全局变量统计函数被调用次数**

```cpp
#include <iostream>
using namespace std;

int count = 0;                 // 全局变量，跨函数共享状态
void func() { count++; }       // 每次调用把全局计数加 1

int main() {
    for (int i = 0; i < 100; i++) { func(); }   // i 是 for 的局部变量
    cout << "func函数被调用次数：" << count << endl;
    return 0;
}
// 输出：
// func函数被调用次数：100
```

**进阶思考**：如果把 `count` 改成 `func()` 内的 `static int count`，还需要全局变量吗？答案是不需要——但那样 `main` 就读不到 `count` 了，必须额外提供 `getCount()` 接口。这正是"全局（共享方便但失控）vs static 局部（受控但要开口子）"的经典权衡。

**人话总结**：存储类管的是"活多久、谁能看、去哪找"。


## 五、模块三：多文件编程具体步骤（《11.2》P1–P8）

### 知识点 7　为什么要多文件编程（《11.2多文件编程》P1–P5）【了解】

#### ① 是什么

**一句话定义**（课件 P4 原文）：**为了方便分工或后期的维护，分散代码应遵循一个基本原则：实现相同功能的代码应存储在一个文件中。**

**生活化比喻**：单文件写到底，好比**全家所有东西塞进一个衣柜**——找袜子要翻半小时，请朋友来帮忙整理（协作开发）根本无从下手。多文件编程就是给衣服分区：上衣一格、裤子一格，**每个格子（模块）只负责一类物品，内部怎么调整都不影响别的格子**。

课件 P4 给出的文件后缀分类（务必记牢）：

| 后缀 | 类别 | 说明（课件原文要点） |
|------|------|---------------------|
| `.h` | **头文件** | 放声明：函数原型、类定义、宏、`extern` 声明、`typedef`/`using` |
| `.hpp` | **头文件** | header plus plus 的缩写，**混杂着 .h 的声明和 .cpp 的定义**，OpenCV 采用此风格（模板实现必须在头文件中，故常见 `.hpp`） |
| `.cpp` | **源文件** | Windows 平台的源文件后缀 |
| `.cc` | **源文件** | Unix/Linux 平台的源文件后缀（Google C++ Style 即用 `.cc`） |

（补充同类：`.cxx`/`.C` 亦属源文件；`.hh` 属头文件。配套工程的 `Test001.vcxproj.filters` 里可以看到 VS 的实际归类：头文件过滤器收 `h;hh;hpp;hxx;h++;hm;inl;inc;ipp;xsd`，源文件过滤器收 `cpp;c;cc;cxx;c++;cppm;ixx;def;...`。）

课件 P5 的另一层动机——**版权与保密**：

> 又或者是有一天，你写出了很牛的功能代码，出于版权和保密考虑，大多是已经编译好的二进制文件，**可能仅包含 .h 文件**。

也就是说：商业库交付形态通常是"**公开的头文件（说明书）+ 编译好的 `.lib/.dll/.a/.so`（黑盒）**"。会用 `.h` 就是能用第三方库的前提。

课件 P5 的最小三文件骨架（含原稿拼写瑕疵 `"sudent.h"`，正确应为 `"student.h"`）：

```cpp
// 1.student.h
void printInfo();

// 2.student.cpp
#include "student.h"        // 课件原文此处写作 "sudent.h"（拼写笔误）
// printInfo 定义

// 3.main.cpp
#include "student.h"
int main(){ /* ... */ }
```

#### ② 为什么（追问 3 层）

1. **为什么要拆文件？** 单个 `.cpp` 上千行时，人脑装不下、编译器重编慢、多人协作必冲突。
2. **为什么按"功能相同放一个文件"来拆？** 因为这样**修改的影响面被限制在单个文件**，评审、测试、定位 bug 都以模块为单位。
3. **为什么必须是 `.h` + `.cpp` 这种配对形式，而不是 `.cpp` 之间直接互相 include？** 因为 `.cpp` 是编译单元、彼此独立编译；`.h` 只是"接口契约"，可以被无限次复制而不产生重复符号（前提是加防护）。**声明可多次，定义只能一份**——这条 ODR（One Definition Rule）是整个多文件体系的承重墙。

#### ③ 怎么用（内容放置决策表）

| 要放的东西 | 放哪里 | 原因 |
|-----------|--------|------|
| 函数原型、类声明 | `.h` | 让别人能调用，但不暴露实现 |
| 函数实现、类的非 inline 成员函数 | `.cpp` | 保证全程序只有一份定义 |
| 宏常量、`constexpr`、`typedef`/`using` | `.h` | 需要在多处共享的编译期信息 |
| `extern` 变量声明 | `.h` | 声明可以有多个 |
| 全局变量的定义（`int x = 1;`） | **恰好一个** `.cpp` | 定义只能有一份 |
| 模板函数的实现 | `.h`/`.hpp` | 编译器需在使用点看到完整定义才能实例化 |
| 只想本文件用的小工具函数 | `.cpp` + `static`/匿名命名空间 | 不污染对外接口 |

**人话总结**：拆文件就是把"契约"和"干活"分开。

#### ④ 注意事项 / 常见错误示范

```cpp
// ❌ 错误 1：把所有实现塞进 .h（除模板/inline 外）
// util.h
int add(int a, int b) { return a + b; }    // 这是定义
// 被 a.cpp 与 b.cpp 各 include 一次 → link error: multiple definition of `add'
// ✅ 正确：util.h 写原型，util.cpp 写实现；或显式加 inline 关键字

// ❌ 错误 2：.cpp 里没有 include 自己的 .h
// student.cpp 直接写 void printInfo(){...}，却没 #include "student.h"
// → 头文件签名一旦改动，.cpp 编译不出错，链接时才炸；失去"接口自洽"检查
// ✅ 正确：每个 xxx.cpp 第一行 include "xxx.h"（也是 include 顺序规范的第一条）

// ❌ 错误 3：A.h include B.h，B.h 又 include A.h（循环依赖）
// → 靠宏守卫会表现为诡异的"某某类型未声明"
// ✅ 正确：前向声明（class B;）打断环，或抽出共同基类放到第三个头文件
```

#### ③ 怎么用：完整可运行的多文件工程

以下代码是本机实测可编译版本（`g++ -std=c++11 main.cpp student.cpp teacher.cpp -o app`），结构与 VS 工程一致。

**`student.h` —— 声明层（对外契约）**

```cpp
#pragma once                  // 防护机制二：编译器指令，本文件只编译一次
#ifndef _STUDENT_H_           // 防护机制一：传统宏守卫兜底（编译器不认识 pragma 时生效）
#define _STUDENT_H_           // 宏名必须全项目独一无二，惯例用"文件名大写 + 下划线"

// 只写原型，不写函数体：这就是"声明"
void printInfo();             // 打印学生信息
void printName();             // 打印学生姓名
int  getAge();                // 返回学生年龄

#endif // !_STUDENT_H_        // 宏守卫结束
```

**`student.cpp` —— 实现层（真正干活）**

```cpp
#include "student.h"          // 自包含：先 include 自己的头，让编译器校验签名一致
#include <iostream>           // 实现需要的标准库，由实现自己 include
using namespace std;

void printInfo() { cout << "student info" << endl; }
void printName() { cout << "student name" << endl; }
int  getAge()    { return 20; }
```

**`teacher.h` / `teacher.cpp` —— 第二个模块（证明可无限扩展）**

```cpp
// teacher.h
#pragma once
#ifndef _TEACHER_H_
#define _TEACHER_H_
void teachClass();
#endif // !_TEACHER_H_
```

```cpp
// teacher.cpp
#include "teacher.h"
#include <iostream>
using namespace std;
void teachClass() { cout << "teacher is teaching" << endl; }
```

**`main.cpp`（对应工程中的 `Test001.cpp`）—— 使用层**

```cpp
#include <iostream>
#include "student.h"          // 双引号：自定义头文件，先找本项目目录
#include "teacher.h"
using namespace std;

int main() {
    printInfo();              // 只依赖 .h 里的声明即可调用
    printName();
    cout << getAge() << endl;
    teachClass();
    return 0;
}
```

**编译与运行**：


```text
// teacher is teaching
```

**逐行走读整个构建过程（专项要求：说明每步状态变化）**：

| 阶段 | 发生了什么 | `printInfo` 这个名字此时的状态 |
|------|-----------|------------------------------|
| 预处理 `main.cpp` | `#include "student.h"` 把 3 行声明**文本复制**进 main.cpp；`#pragma once`/`#ifndef` 在这一阶段判定是否展开 | main.cpp 里有了原型 → 编译器知道"有这函数，无参，返回 void" |
| 编译 `main.cpp` | 生成 `main.o`。遇到 `printInfo()` 调用但找不到函数体 → 在 `main.o` 里登记一条**未决符号引用** `U printInfo` | 未决（Unresolved） |
| 预处理+编译 `student.cpp` | `#include "student.h"` 展开声明（一致性自检）；生成 `student.o`，导出**强符号** `T printInfo` | 已定义 |
| 编译 `teacher.cpp` | 生成 `teacher.o`，导出 `T teachClass` | — |
| **链接** | 链接器把所有 `.o` 的符号表合并，把 `main.o` 的 `U printInfo` 指向 `student.o` 的 `T printInfo`，回填真实地址 | 解析完成 |
| 运行 | CPU 跳到 `student.o` 那段机器码执行，`cout` 输出 `student info` | — |

如果漏掉 `student.cpp` 没参与编译，链接阶段就会报：

```text
/tmp/ccXXXX.o: in function `main': main.cpp:(.text+0x15): undefined reference to `printInfo()'
collect2.exe: error: ld returned 1 exit status
```

——**"编译过了 ≠ 能跑"**，这是多文件编程最反直觉、也最重要的一课。

## 六、模块四：include 区别 + 防止头文件重复包含（《11.2》P9–P16）

### 知识点 9　`#include<>` 和 `#include""` 的区别（《11.2多文件编程》P9）【熟悉】

#### ① 是什么

**一句话定义**（课件 P9）：

- **`#include <>` 引用的是编译器的类库路径里面的头文件**，一般用于引用**标准头文件**，如 `stdio.h`、`string.h` 等；
- **`#include ""` 引用的是项目相对路径中的头文件**，一般用于引用**自定义的头文件**。如果使用 `#include ""`，**首先会在当前项目所在文件夹下寻找**是否有对应的头文件，**如果没有，还是会到编译器自带头文件目录中查找**。

课件给的例子：使用 `#include "stdio.h"`，如果项目中不包含 `stdio.h` 这个头文件，则还是会定位到标准头文件中查找 `stdio.h` 这个文件。

**生活化比喻**：`<>` 是**打 114 查号台问公家单位**（系统目录，直连权威源）；`""` 是**先在自家小区群里问一句，没人知道再打 114**（先本地、后系统）。

#### ② 为什么（追问 3 层）

1. **为什么要两套搜索策略？** 因为"系统的"和"我自己的"是两个信任域，需要不同查找顺序。
2. **为什么 `""` 要先查本地？** 因为你要确保编译用的是**你自己那份**（可能是打过补丁的第三方头），而不是安装目录里那份旧的。
3. **为什么 `""` 找不到还要退回系统路径？** 因为语言设计要保持向后兼容——历史上大量代码用 `#include "stdio.h"`，若硬性失败会摧毁无数既有工程。

#### ③ 怎么用（对比表格 + 搜索顺序图）

| 对比维度 | `#include <header>` | `#include "header"` |
|---------|--------------------|--------------------|
| 搜索起点 | 编译器预设的**系统/类库路径**（`-I`、`INCLUDE` 环境变量） | **当前文件所在目录 / 项目目录** |
| 找不到时 | 直接报错 | **再回落到系统路径继续找** |
| 典型用途 | 标准库、第三方 SDK 头 | 自己项目的 `.h` |
| 能否被本地同名文件劫持 | 一般不会（除非显式加了 `-I.`） | **会**（本地优先） |
| 语义暗示 | "这是公共 API" | "这是我私有的接口" |
| 探测开销 | 少一次本地目录探测 | 多一次本地探测（可忽略） |
| 示例 | `#include <iostream>`、`#include <stdio.h>` | `#include "student.h"` |

```
        #include <iostream>            #include "student.h"
               │                              │
               ▼                              ▼
      ┌────────────────┐            ┌──────────────────────┐
      │ 系统/类库搜索路径 │            │ ① 当前项目/当前文件目录  │
      │ (C:\...\include)│            └─────────┬────────────┘
      └───────┬────────┘                   找到了? ── 否 ──┐
          找到了?                            │             │

             │                        └───────┬────────┘

      │ such file or    │

```

**演示代码（同一个文件，两种写法命运不同）**：

```cpp

#include <cstdio>         // C 标准库的 C++ 包装（推荐这种而非 stdio.h）
#include "student.h"      // 自定义头：先找当前项目目录
```

**行为差异实测（同一个自定义头，两种写法的命运）**：

项目目录下存在自定义文件 `my_head.h`（内容只有一行注释）。在 `main.cpp` 中分别改写第 3 行后编译：

| main.cpp 里写的是 | g++ 结果 |
|------------------|---------|
| `#include "my_head.h"` | ✅ 编译通过 —— 在**当前项目目录**就找到了 |
| `#include <my_head.h>` | ❌ `fatal error: my_head.h: No such file or directory` —— 只查系统类库路径 |

反过来验证课件 P9 举的 `stdio.h` 例子：

| main.cpp 里写的是 | g++ 结果 |
|------------------|---------|
| `#include <stdio.h>` | ✅ 通过（走系统路径） |
| `#include "stdio.h"` | ✅ 同样通过 —— 项目目录没有 stdio.h，于是**回落到系统路径**找到它 |

两张表合起来就是完整规则：**`<>` 只有一条路；`""` 有两条路，本地优先、系统兜底。**

**行为发生在预处理阶段**：`#include` 既不是编译期也不是运行期，而是**编译之前的预处理**——它做的纯粹是"文件内容原地粘贴"，粘贴后才进入编译。**每一处 `#include` 都会真的粘贴一遍**，这就自然引出了下一个知识点：重复包含。

**人话总结**：尖括号找系统，双引号先找自己。

### 知识点 10　防止头文件重复包含（《11.2多文件编程》P10–P14）【重点】

#### ① 是什么

**一句话定义**：当一个头文件被多条 `#include` 路径重复展开时，其中的**定义**会被复制多份，从而触发重定义错误；**头文件保护（include guard）**就是在预处理阶段拦截这种重复展开的机制。

课件 P10 直接给出**三种方案**（也正是配套 txt 作业 `说一说避免重复引用的方法有哪些？.txt` 的标准答案）：

> 1. 使用宏定义避免重复引入
> 2. 使用 `#pragma once` 避免重复引入
> 3. 用 `_Pragma` 操作符

**生活化比喻**：头文件保护是**小区门禁刷卡**。第一次刷卡（首次 include）门开、登记在册；同一张卡再刷（第二次 include）系统显示"该业主已入场"，直接不放行——**内容不会被抬进来第二遍**。

#### ② 为什么（追问 3 层）

1. **为什么会重复包含？** 因为 `#include` 是文本复制，而依赖天然形成网状：`main.cpp → student.h`，同时 `main.cpp → teacher.h → student.h`，`student.h` 就被粘贴了两次。
2. **为什么粘贴两次就出事？** 因为粘贴的是**定义**（函数体、变量、类），而 C++ 的 ODR 要求一个非 inline 实体在全程序中只能有一个定义。
3. **为什么宏守卫能拦住？** 因为 `#ifndef` 的判断发生在**预处理**阶段——第二次展开时宏已被定义，整段内容被预处理器直接跳过，编译器压根看不到重复定义。

#### ③ 先看事故：不加防护会怎样

```cpp
// ---------- common.h（无任何防护）----------
void helper();
int shared = 1;            // ← 定义（全局变量）写在头文件里，是灾难源头

// ---------- main.cpp ----------
#include <iostream>
#include "common.h"
#include "common.h"        // 手滑 include 了两次（现实中常因间接依赖而发生）
int main() { helper(); std::cout << shared << std::endl; }
```

g++ 实际报错（本机复现）：

```text
In file included from main.cpp:3:
common.h:2:5: error: redefinition of 'int shared'
 int shared = 1;
     ^~~~~~
In file included from main.cpp:2:
common.h:2:5: note: 'int shared' previously defined here
```

同理，头文件里写 `inline void f(){}` 被 include 两次，会得到 `error: redefinition of 'void f()'`。

> 📌 **严谨补充（课件未细说，但值得掌握）**：并非所有重复展开都报错。**单纯的声明**（`void helper();`）重复 N 次是合法的；类定义重复则会报 `redefinition of 'class X'`；而如果两个**不同的 `.cpp`** 各自 include 同一份含定义的 `.h`，那是**链接期**的 `multiple definition`，不是编译期错误。理解"编译期重复 vs 链接期重复"的分界，才算真懂这个问题。

#### ④ 三种防护机制逐一详解

##### 机制 1｜传统宏守卫（Include Guard）—— 课件 P11

课件模板：

```cpp
#ifndef _NAME_H
#define _NAME_H
//头文件内容
#endif
```

课件对**原理**的原文说明：`_NAME_H` 是宏的名称；**注意：设置的宏名必须是独一无二的，不要和项目中其他宏的名称相同。** 当程序中**第一次** `#include` 该文件时，由于 `_NAME_H` 尚未定义，所以会**定义 `_NAME_H` 并执行"头文件内容"部分的代码**；当发生**多次** `#include` 时，因为前面已经定义了 `_NAME_H`，所以**不会再重复执行"头文件内容"部分的代码**。

逐行拆解每一行的作用：

| 行 | 指令 | 作用 | 首次 include | 第二次 include |
|----|------|------|-------------|---------------|
| 1 | `#ifndef _STUDENT_H_` | "if not defined"：若宏未定义则为真 | 真 → 进入 | 假 → 跳过 |
| 2 | `#define _STUDENT_H_` | 把这个独一无二的宏定义为"存在" | 打上烙印 | （被跳过） |
| 3..n | 头文件正文 | 声明/定义本体 | 展开给编译器 | **整段丢弃** |
| n+1 | `#endif` | 闭合条件块 | 收尾 | 收尾 |

**完整可运行示例（含两次 include，编译通过）**：

```cpp
// ---------- guarded.h ----------
#ifndef _STUDENT_H_          // 若 _STUDENT_H_ 未定义（说明是第一次进来）
#define _STUDENT_H_          // 立刻定义它，留下"我来过"的凭证
// ↓↓↓ 头文件内容：本段在后续任何重复 include 中都会被预处理直接跳过 ↓↓↓
void printInfo();            // 函数声明
int  shared = 1;             // ⚠️ 即便有宏守卫，也不该在头文件里放定义（见注意事项）
// ↑↑↑ 头文件内容 ↑↑↑
#endif // !_STUDENT_H_       // 结束条件编译；尾部注释是 VS 自动生成风格
```

```cpp
// ---------- main.cpp ----------
#include <iostream>
#include "guarded.h"
#include "guarded.h"          // 第二次 include：宏已定义 → 整段被跳过 → 不再是重定义
using namespace std;
int main() { cout << "guarded ok, shared=" << shared << endl; return 0; }
// 输出：
// guarded ok, shared=1
```

**宏命名规范（工业实践）**：

| 规范 | 示例 | 说明 |
|------|------|------|
| 全大写 + 下划线 | `STUDENT_H` | 最常见，避免与小写宏冲突 |
| 前导下划线版 | `_STUDENT_H_` | 课件所用风格（VS 默认）；严格说 `_` 开头是保留标识符，宜谨慎 |
| 带项目/命名空间前缀 | `MYPROJ_MODEL_STUDENT_H_` | **大型项目首选**，杜绝跨模块同名撞车 |
| 路径派生 | `SRC_UTIL_STUDENT_H` | CMake 等工具的常见自动生成法 |

##### 机制 2｜`#pragma once` —— 课件 P12

用法：把 `#pragma once` **放在文件开头位置**即可，无需宏、无需 `#endif`。

课件对优劣的原文要点（四条，逐条理解）：

1. `#ifndef` 是通过定义独一无二的宏来避免重复引入的，意味着**每次引入头文件都要进行识别，所以效率不高**；
2. 但考虑到 **C 和 C++ 都支持宏定义**，所以项目中使用 `#ifndef` 规避可能出现的"头文件重复引入"问题，**不会影响项目的可移植性**；
3. 和 `ifndef` 相比，**`#pragma once` 不涉及宏定义，当编译器遇到它时就会立刻知道当前文件只引入一次，所以效率很高**；
4. 但**并不是每个版本的编译器都能识别 `#pragma once`**，老版本的编译器有些是不支持该指令（**执行时会发出警告，但编译会继续进行**），即**兼容性不是很好**；除此之外，**`#pragma once` 只能作用于某个具体的文件，而无法像 `#ifndef` 那样仅作用于指定的一段代码**。

课件结语：目前几乎所有常见的编译器都支持 `#pragma once` 指令，甚至于 **VS 2017 新建头文件时就会自带该指令**。可以这么说，在 C/C++ 中，`#pragma once` 是一个**非标准但却逐渐被很多编译器支持的指令**。

```cpp
// ---------- student.h ----------
#pragma once                 // 编译器指令：本文件在本次编译中最多展开一次
void printInfo();            // 干净利落，没有宏、没有 #endif
int  getAge();
```

**原理差异**：`#pragma once` 由编译器基于**文件身份（inode / 完整路径 / 内容指纹）**在展开前就短路，连读文件都可以省；宏守卫则必须**读完文件、解析到 `#ifndef` 才知道要跳过**。所以在大型工程反复 include 同一头文件时，`#pragma once` 有实打实的编译速度优势。

##### 机制 3｜`_Pragma` 操作符 —— 课件 P13

用法（课件原文）：`_Pragma("once")`，**放在文件开头位置**。

课件说明：**C99 标准中新增加了一个和 `#pragma` 指令类似的 `_Pragma` 操作符**，其可以看做是 `#pragma` 的**增强版**，不仅可以实现 `#pragma` 所有的功能，更重要的是，**`_Pragma` 还能和宏搭配使用**。

```cpp
// ---------- student.h ----------
_Pragma("once")              // 等价于 #pragma once，但它是【运算符】而非【指令】
void printInfo();
```

**"能和宏搭配"到底强在哪**（这是 `#pragma` 做不到的）：

```cpp
#include <iostream>
using namespace std;

#define DO_PRAGMA(x) _Pragma(#x)                     // # 是字符串化运算符
#define QUIET_UNUSED DO_PRAGMA(GCC diagnostic ignored "-Wunused-variable")

QUIET_UNUSED                                          // 通过宏间接发出的 pragma 指令
int main() {
    int unused_here = 1;                              // 该行告警已被上面的宏关闭
    cout << "no warning printed" << endl;
    return 0;
}
// 输出：
// no warning printed
// 说明：若把 #pragma GCC diagnostic ... 直接塞进 #define，编译器不会展开它
```

**代价**：`_Pragma` 可读性差、写法绕，日常很少单独用它做头文件保护；它的价值在于**元编程/宏库**场景。

##### 机制 4（最佳实践）｜`#pragma once` + 宏守卫 结合 —— 课件 P14

课件原文：**考虑到编译效率和可移植性，`#pragma once` 和 `#ifndef` 经常被结合使用来避免头文件被重复引入。**

```cpp
#pragma once
#ifndef _NAME_H
#define _NAME_H
//头文件内容
#endif
```

课件对**双层防护收益**的解释：

- 当编译器**可以识别 `#pragma once`** 时，则整个文件**仅被编译一次**（走快速通道，宏部分形同冗余保险）；
- 如果编译器**不识别 `#pragma once`** 指令，此时**仍有 `#ifndef` 在发挥作用**（保底可移植）。

**这正是配套 `Test001/student.h` 采用的写法**（原样摘录，去掉试验性注释块）：

```cpp
#pragma once

#ifndef _STU_
#define _STU_
void printInfo();
void printName();
int  getAge();
#endif // !_STU_
```

**三种机制横向对比表（本章最重要的一张表）**：

| 维度 | ① 宏守卫 `#ifndef` | ② `#pragma once` | ③ `_Pragma("once")` | ④ 组合（①+②） |
|------|-------------------|-----------------|--------------------|--------------|
| 生效阶段 | 预处理 | 编译器（展开前） | 编译器（展开前） | 两者叠加 |
| 是否标准 | ✅ C/C++ 标准 | ❌ 非标准（但普及） | ✅ C99 起为标准操作符 | ✅ 至少一半标准 |
| 兼容性 | 所有编译器/所有年代 | 老编译器警告但仍继续编译 | 需支持 `_Pragma` | 最好 |
| 编译效率 | 较低（须读入并识别宏） | **高**（文件级短路） | 高 | **最高** |
| 代码整洁度 | 3 行样板 + 必须记住 `#endif` | 1 行 | 1 行 | 4 行 |
| 作用粒度 | **可只保护一段代码** | 只能整个文件 | 只能整个文件 | 两者都有 |
| 宏名冲突风险 | 有（须全项目唯一） | 无 | 无 | 有（但可控） |
| 同一文件经两条路径/映射盘进入 | ✅ 仍能正确判重 | ❌ 可能被当作两个文件各展开一次 | 同左 | ✅ 由宏守卫兜底 |
| 与宏配合 | — | — | ✅ 唯一能做到 | — |
| 推荐场合 | 极致可移植 / 分段保护 | 日常新项目 | 宏库/元编程 | **工业项目默认** |

**完整端到端演示（含"报错 → 加防护 → 通过"全过程，菱形依赖）**：

```cpp
// ========== 目录结构 ==========
// person.h   student.h   student.cpp   main.cpp

// ---------- person.h ----------
#ifndef _PERSON_H_
#define _PERSON_H_
class Person {
public:
    int age;
    Person(int a) : age(a) {}
};
#endif // !_PERSON_H_

// ---------- student.h（间接依赖 person.h，构成菱形包含）----------
#pragma once
#ifndef _STUDENT_H_
#define _STUDENT_H_
#include "person.h"          // 路径 A：student.h → person.h
class Student : public Person {
public:
    Student(int a) : Person(a) {}
    void who() const;
};
#endif // !_STUDENT_H_

// ---------- student.cpp ----------
#include "student.h"
#include <iostream>
void Student::who() const { std::cout << "Student, age=" << age << std::endl; }

// ---------- main.cpp ----------
#include "person.h"          // 路径 B：main.cpp → person.h（与 A 汇合，形成重复 include）
#include "student.h"
int main() { Student s(20); s.who(); return 0; }
```

```bash
g++ -std=c++11 main.cpp student.cpp -o guardapp && ./guardapp
```

```text
// Student, age=20

// 若删除 person.h 的 #ifndef/#define/#endif 三行，立即变红：
// person.h:6:7: error: redefinition of 'class Person'
```

这个例子刻意制造了**菱形依赖**（`main → person.h` 且 `main → student.h → person.h`），也就是真实项目中最常见的"我没写两次 include，怎么也重定义了"的场景——**宏守卫的价值正是在这种间接路径上体现出来的**。

#### ⑤ 注意事项 / 常见错误示范

```cpp
// ❌ 错误 1：宏名不够独特（两个不同头文件用了同一个宏名）
// utils.h  : #ifndef _NAME_H / #define _NAME_H / ...
// logger.h : #ifndef _NAME_H / #define _NAME_H / ...   ← 撞名！
// 后果：先 include utils.h 的文件里，logger.h 会被当成"已展开"而整体消失，
//       表现为诡异的 "undeclared identifier"，排查极其痛苦。
// ✅ 正确：宏名带上路径/项目前缀，如 MYPROJ_UTILS_LOGGING_H_

// ❌ 错误 2：把 #define 写在了 ifndef 之前
#define _STUDENT_H_          // 一上来就打上了烙印
#ifndef _STUDENT_H_          // 永远为假 → 整个头文件永远不展开
#define _STUDENT_H_
void printInfo();
#endif
// 后果：printInfo 从未声明 → 使用处 error: 'printInfo' was not declared

// ❌ 错误 3：#endif 与 #ifndef 数量不匹配 / 少了 #endif
// 后果：error: unterminated #ifndef，或后续 include 的文件被整段吞进条件块

// ❌ 错误 4：把 #endif 塞进函数体中间
#ifndef _X_H_
#define _X_H_
inline int f() {
#endif                       // ← 千万别这样（除非你非常清楚自己在做什么）
// 后果：预处理是文本级的，函数体被劈开后极易产生语法错误

// ❌ 错误 5：#pragma once 拼错
// #pragma one        ← 少个 c，编译器只给一个 unknown pragma 警告，
//                       于是你以为有防护，其实完全没有 → 重复定义照旧
// ✅ 正确：写完防护一定要做一次"双 include 压力测试"确认真的挡住了

// ❌ 错误 6：以为宏守卫能防止"链接期"的重复定义
// 头文件里写 int g = 1; 就算加了 #ifndef，只要它被两个不同 .cpp include，
// 仍是 two translation units each define g → multiple definition（链接错误）
// ✅ 正确：头文件里只放 extern 声明；定义集中在唯一一个 .cpp
```

**记忆口诀**：

- **头文件进门要刷卡，刷过就不再进**；
- **`pragma once` 快但不标准，`ifndef` 慢但走到哪都好使，两个一起上最稳**；
- **宏名不唯一，队友两行泪**。

**人话总结**：给头文件装个门禁，重复来的直接被挡在门外。

### 7.3 两个课后思考题（配套 txt 参考答案）

#### Q1：简述全局变量和局部变量的作用域及生命周期（`全局和局部变量作用域及生命周期.txt`）

> **全局变量**：一般是指函数外部定义的（独立于函数内部，独立于代码文件的代码）。**作用域**为从声明处到文件末尾，整个文件内所有函数均可使用；若要在**另外一个文件**中使用该另一个文件中存在的全局变量，那么可以使用 **`extern`** 关键字，这样另外一个文件就可以使用该数据了。**生命周期**不受函数调用的影响（也就是说，全局变量的生存期一直到**程序的结束**），存放在静态存储区。
>
> **局部变量**：在一个函数内部定义（即在函数的"局部"作用域中）。其存储类别默认为 **`auto`（自动）**，含义是**进入函数时自动生成、离开函数时自动消失**（存放在栈区），因此每次调用都是一份全新的变量；关键字 `auto` 只是显式说出这层默认含义，**没有必要写为 auto**。所以局部变量的**作用域限于定义它的函数（乃至更内层的 `{}`）**，**生命周期仅为该次函数调用期间**。

#### Q2：说一说避免重复引用（包含）的方法有哪些？（`说一说避免重复引用的方法有哪些？.txt`）

> 1. 使用**宏定义**避免重复引入（`#ifndef / #define / #endif` 宏守卫）；
> 2. 使用 **`#pragma once`** 避免重复引入；
> 3. 用 **`_Pragma`** 操作符（`_Pragma("once")`）。
>
> （加分项：生产项目常把 1 与 2 **组合使用**，兼顾编译效率与可移植性。）

## 九、第三阶段：难点慢讲 + 常见陷阱专题

### 9.1 难点慢讲 A：五种存储类修饰符的差异（对应提示词"补 2"）

把 `auto/register/static/extern/mutable` 混成一锅粥，是因为大家试图用"一个维度"去记"四个维度"。正确方法是**每次只问四个问题，逐个回答**。

**四问模板**：① 内存在哪？② 什么时候生、什么时候死？③ 谁能用名字访问它？④ 别的文件能找到它吗？

**Step 1：先立一个"什么都不写"的基准**

```cpp
void f() { int a = 1; }   // a：栈区 / 进函数生死 / 仅 f 可见 / 别的文件找不到
```
这就是 `auto`（旧语义）的样子——**默认状态，无需书写**。

**Step 2：只改"存活时间"→ 加 `static`**

```cpp
#include <iostream>
using namespace std;
void f() { static int a = 1; a++; cout << a << " "; }
int main() { f(); f(); f(); cout << endl; return 0; }
// 输出：2 3 4      （不是 2 2 2！）
```
差异：**内存搬到了静态区，初始化只发生一次**。作用域一个字都没变。
👉 记忆锚点：**`static` 换的是"住处和寿命"，不换"门牌号权限"。**

**Step 3：只改"谁能找到"→ 加 `extern`**

```cpp
// A.cpp: int g = 1;        → 定义，独占一份内存
// B.cpp: extern int g;     → 声明，不占内存，只是"挂号"
```
差异：**符号的可发现范围扩大到全程序**。生命周期和作用域都由"定义处"决定。
👉 记忆锚点：**`extern` 不创建任何东西，它只是一张"名片"。**

**Step 4：只改"物理位置"→ `register`（历史）**

```cpp
register int i;   // 请求放寄存器；C++17 起此写法非法
```
差异：**只影响性能建议，不影响语义**（生命周期、作用域、链接性全同 `auto`）。正因如此，它被优化器淘汰。

**Step 5：处理"例外"→ `mutable`**

```cpp
class S { int x; mutable int y; public: void show() const { y++; } };
```
差异：**不参与生命周期/链接的游戏，只为 `const` 成员函数开一个后门**。

**终极对照表（把五个放进同一坐标系）**

| 四问 | `auto`(旧) | `register` | `static`(局部) | `extern` | `mutable` |
|------|-----------|-----------|---------------|---------|-----------|
| ① 内存位置 | 栈 | 寄存器 | **静态区** | 取决于定义处（通常静态区） | 随所属对象 |
| ② 生命周期 | 块 | 块 | **全程** | 全程 | 随对象 |
| ③ 作用域 | 块 | 块 | 块（**不变**） | 声明处→文件末 | 类 |
| ④ 链接性 | 无 | 无 | 无（函数内）／内部（文件级） | **外部** | — |
| 是否分配内存 | 是 | 通常否 | 是 | **否** | 是（计入对象大小） |
| 初始化时机 | 每次经过 | 每次经过 | **仅第一次** | 程序启动前 | 随对象构造 |
| 现代状态 | 含义已变 | C++17 移除 | 有效 | 有效 | 有效 |
| 一句话 | 默认 | 过时 | 活得久、藏得深 | 打个招呼 | const 的逃生口 |

**练手法则**：拿到任何一段代码，用四问逐项口头作答，答不出来就是没懂。

### 9.2 难点慢讲 B：宏守卫的工作原理（对应提示词"补 2"，放慢到每一拍）

宏守卫的关键在于它是**纯文本层面的条件编译**，你必须想象自己是预处理器，正在**逐行朗读文件**。

**场景设定**：`a.cpp` 写了两次 include：

```cpp
#include "point.h"     // 第 1 次
#include "point.h"     // 第 2 次（现实中常因间接依赖而发生）
```

`point.h`：

```cpp
#ifndef POINT_H_              // L1
#define POINT_H_              // L2
struct Point { int x, y; };   // L3
#endif                        // L4
```

**第一次 include：预处理器逐拍动作**

| 拍 | 预处理器看到 | 内部状态变化 | 决策 |
|----|-------------|-------------|------|
| 1 | `#include "point.h"` | 记下"要去读 point.h" | 开始插入文件内容 |
| 2 | L1 `#ifndef POINT_H_` | 查宏表：**POINT_H_ 不存在** | 条件为**真** → 进入分支 |
| 3 | L2 `#define POINT_H_` | **宏表新增 POINT_H_**（关键副作用！） | 记录状态 |
| 4 | L3 `struct Point{...}` | 无条件跟随（仍在真分支内） | **保留文本，交给编译器** |
| 5 | L4 `#endif` | 退出条件块 | 恢复正常 |
| 结果 | 传给编译器的内容 = `struct Point { int x, y; };` | 宏表里多了 POINT_H_ | ✅ 类定义被看到 1 次 |

**第二次 include：逐拍动作**

| 拍 | 预处理器看到 | 内部状态变化 | 决策 |
|----|-------------|-------------|------|
| 1 | `#include "point.h"` | 再次读入同一文件 | 开始 |
| 2 | L1 `#ifndef POINT_H_` | 查宏表：**POINT_H_ 已存在** | 条件为**假** → 进入"跳过模式" |
| 3 | L2 `#define POINT_H_` | 跳过模式下只识别 `#if/#ifdef/#ifndef/#elif/#else/#endif` 结构，其他指令**一律忽略** | 不执行 |
| 4 | L3 `struct Point{...}` | **整行被丢弃，绝不传递给编译器** | 不执行 |
| 5 | L4 `#endif` | 退出跳过模式 | 恢复 |
| 结果 | 传给编译器的内容 = **空** | 宏表不变 | ✅ 编译器根本没看见第二份定义 |

**三个由此推出的深层结论**：

1. **"跳过模式"意味着中间内容连语法都不检查** —— 所以你可以在被跳过的段落里写乱码，只要不含条件块结构就照样能编译。这也解释了为什么宏守卫失效时报的往往是"莫名语法错误"：你以为被挡住了，其实没有。
2. **宏表是"整个翻译单元共享"的** —— 一个 `.cpp` 及其所有 include 共用一张宏表。所以宏名撞车 = 两个头文件互相屏蔽（第十二节易错点速查卡第 4 行的来源）。
3. **`#pragma once` 拦得更早** —— 它在"要不要读这个文件"这一步就短路了（基于文件身份），而宏守卫必须"读完才知道要丢"。这就是课件 P12 所说"效率不高 vs 效率很高"的确切含义。

**一张图看懂三层拦截点**：

```
   #include "point.h"
          │
          ▼
   ┌─────────────────────────┐
   │ 拦截点 ①  #pragma once    │  ← 编译器：这个文件我已展开过 → 连读都不读  【最快】
   └───────────┬─────────────┘
               │ 未命中 / 不认识该指令
               ▼
   ┌─────────────────────────┐
   │ 读入文件全文（磁盘 IO）    │
   └───────────┬─────────────┘
               ▼
   ┌─────────────────────────┐
   │ 拦截点 ②  #ifndef 宏守卫   │  ← 预处理器：宏已定义 → 整段丢弃，不给编译器 【次快】
   └───────────┬─────────────┘
               │ 首次
               ▼
   ┌─────────────────────────┐
   │ 交给编译器 → 生成目标码    │
   └───────────┬─────────────┘
               ▼
   ┌─────────────────────────┐
   │ 拦截点 ③  链接器           │  ← 注意：链接器【不去重定义】，只会报错。
   │                          │     所以"重复定义"必须在前两层挡住！
   └─────────────────────────┘
```

### 9.3 【常见陷阱专题】三个最易错点（对应提示词"补 3"）

#### 陷阱 1｜全局变量同名覆盖

| 项目 | 内容 |
|------|------|
| **错误现象** | 局部与全局同名时，以为用的是全局变量，实际改的是局部变量 |
| **错误原因** | 不理解"就近原则"：名字解析总是命中**最内层**作用域 |
| **后果** | 全局值始终不变、函数间状态无法共享；bug 隐蔽且**不报错**（静默逻辑错误，比编译错误可怕得多） |
| **正确写法** | 用 `::全局变量名` 显式访问；或者干脆**避免同名**（最好的写法） |
| **为什么对** | `::` 前缀显式指定"从全局命名空间开始查找"，绕过所有局部层 |
| **如何记住** | **县官不如现管，局部优先** |

```cpp
#include <iostream>
using namespace std;
int total = 0;
void addBad()   { int total = 0; total += 100; }   // ❌ 声明了新局部，全局纹丝不动
void addGood()  { total += 100; }                  // ✅ 直接改全局
void addExplicit() { ::total += 100; }             // ✅ 显式限定，意图最清晰
int main() {
    addBad();      cout << total << " ";           // 0
    addGood();     cout << total << " ";           // 100
    addExplicit(); cout << total << endl;          // 200
    return 0;
}
// 输出：
// 0 100 200
```

**防御技巧**：开启编译警告 `-Wshadow`（GCC/Clang）或 MSVC `/Wall`，让"遮蔽"当场暴露：

```bash
g++ -std=c++11 -Wshadow shadow.cpp -o s
# warning: declaration of 'total' shadows a global declaration [-Wshadow]
```

#### 陷阱 2｜头文件重复包含导致重复定义

| 项目 | 内容 |
|------|------|
| **错误现象** | 多个 `.cpp` 各自 include 同一头文件且无防护 → `redefinition of ...`（编译期）或 `multiple definition of ...`（链接期） |
| **错误原因** | `#include` 是文本复制，每处 include 都会把定义完整粘贴一份；ODR 要求定义只能有一份 |
| **后果** | 编译/链接直接失败；或（更坏）你以为加了防护但宏名撞车，某个头文件被整体屏蔽 → `undeclared identifier` |
| **正确写法** | `#ifndef/#define/#endif` 宏守卫，或 `#pragma once`，工业项目**两者叠加** |
| **为什么对** | 预处理阶段第二次展开时条件为假，整段内容被丢弃，编译器从来看不到第二份定义 |
| **如何记住** | **头文件进门要刷卡，刷过就不再进** |

**根因常常不在"写了两次 include"，而在头文件里放了定义**：

```cpp
// ❌ 治标不治本：加了宏守卫，但头文件里仍有定义
// db.h
#pragma once
#ifndef DB_H_
#define DB_H_
int g_connCount = 0;      // 单一翻译单元内不再重复，但……
#endif

// a.cpp: #include "db.h"
// b.cpp: #include "db.h"
// → 两个 .o 各有一份 g_connCount 的定义 → 链接期 multiple definition（宏守卫救不了！）

// ✅ 根治：头文件只放声明
// db.h  : extern int g_connCount;
// db.cpp: int g_connCount = 0;      // 全工程唯一一份定义
```

**判别口诀**：**宏守卫管"同一个文件里被粘两次"，`extern` 管"不同文件各粘一次"。两个问题要两把钥匙。**

#### 陷阱 3｜static 局部变量误用于多线程 / 误以为会重置

| 项目 | 内容 |
|------|------|
| **错误现象** | 以为每次调用函数 `static` 变量都会重新初始化；或在多线程下裸用 `static` 计数 |
| **错误原因** | 把 `static` 误解为"只是持久一点点的普通变量"，忽略了它**位于静态区、被所有调用共享同一块内存** |
| **后果** | 状态残留导致 bug（第二次调用结果不对）；并发下丢失更新、数据竞争（未定义行为） |
| **正确写法** | 明确"只初始化一次"；需要重置时提供显式接口；需要并发安全时用 `std::atomic` 或 `std::mutex` |
| **为什么对** | 静态区生命周期贯穿全程，那块内存只有一份；初始化只在第一次经过时执行（C++11 起该"第一次"本身是线程安全的） |
| **如何记住** | **static 记三特——特久（活得久）、特独（只初始化一次）、特小（作用域不变）** |

```cpp
#include <iostream>
using namespace std;

int naiveReset() {                    // ❌ 期望"每次从 0 开始"
    static int n = 0;
    return ++n;                       // 实际上 n 一路涨
}
int explicitApi(bool reset = false) { // ✅ 提供重置入口
    static int n = 0;
    if (reset) n = 0;
    return ++n;
}

int main() {
    cout << naiveReset() << naiveReset() << naiveReset() << " | ";
    explicitApi(true);                 // 先清零（返回值 1 被丢弃）
    cout << explicitApi() << explicitApi() << endl;
    return 0;
}
// 输出：
// 123 | 12
```

**多线程补充（务必知情）**：

```cpp
#include <atomic>
#include <thread>
#include <vector>
#include <iostream>
using namespace std;

atomic<int> g_count(0);               // ✅ 原子类型，自增不会丢更新

void worker() { for (int i = 0; i < 100000; i++) g_count.fetch_add(1); }

int main() {
    vector<thread> ts;
    for (int i = 0; i < 4; i++) ts.push_back(thread(worker));
    for (size_t i = 0; i < ts.size(); i++) ts[i].join();
    cout << g_count.load() << endl;
    return 0;
}
// 输出：
// 400000
// 编译：g++ -std=c++11 -pthread x.cpp
// 若换成裸 static int 并 ++，结果将小于 400000（丢失更新）
```

### 9.4 面试高频考点（8 题，附标准答案要点与答题思路）

| # | 考题 | 标准答案要点 | 答题思路 |
|---|------|-------------|---------|
| 1 | `static` 局部变量和普通局部变量的区别？ | 存储区（静态区 vs 栈）、生命周期（全程 vs 块）、初始化次数（一次 vs 每次）、默认值（0 vs 不确定）；**作用域相同** | 先亮"三维度"框架，最后强调"作用域不变"这个反直觉点，加分 |
| 2 | `static` 有哪几种用法？ | ①修饰局部变量延长生命周期；②修饰全局变量/函数 → 内部链接，仅本文件可见；③类成员 → 属于类，全类共享一份，无 `this` | 分"C++ 基础篇三种"来答，体现体系感 |
| 3 | `extern` 的作用是什么？ | 声明符号在别处定义，扩展可见性至跨文件；不分配内存；配合链接器符号解析。`extern "C"` 用于关闭名称改编以链接 C 库 | 一句话定义 + 编译链接机制 + `extern "C"` 延伸 |
| 4 | `extern` 声明与定义不一致会怎样？ | 类型不一致时**可能编译和链接都通过**（符号名相同即可），但按错误类型解读内存 → 垃圾值/崩溃，属未定义行为 | 举 `double price` vs `extern int price` 的例子最有说服力 |
| 5 | `#pragma once` 和 `#ifndef` 哪个更好？ | 各有取舍：`pragma once` 快、简洁但非标准、兼容性稍差、只作用于整文件；`ifndef` 标准、可移植、可分段保护但需读入文件且宏名须唯一。工程上常**两者结合** | 不要选边站，给出"评价维度 + 组合方案"才是满分答案 |
| 6 | 头文件中能不能放函数定义？ | 原则上不放。放定义会导致多次 include 或多 `.cpp` include 时重复定义。例外：`inline` 函数、模板函数、`constexpr` 函数可以（也应该）放头文件 | 先说规则，再说三类例外，体现对 ODR 的理解 |
| 7 | 全局变量的初始化顺序问题？ | 同一翻译单元内按定义顺序初始化；**跨翻译单元的顺序未定义**（Static Initialization Order Fiasco），解决方案是把全局对象改为函数内 `static` 局部对象（Meyers' Singleton） | 这题区分"背过书"和"写过工程"，务必准备一个解决方案 |
| 8 | `typedef` 和 `#define` 有什么区别？ | `typedef` 是编译期的类型别名，有类型检查、受作用域约束、不能拼接；`#define` 是预处理阶段的文本替换，无类型检查、宏名全文件有效、可参与字符串化拼接。C++11 起还可用 `using` | 顺带提 `using` 支持模板别名，展示新知识 |

**追加两题（进阶）**：

- **`mutable` 到底解决什么问题？** 答：解决"逻辑常量 vs 位模式常量"的矛盾——`const` 成员函数承诺不改变对象的**业务状态**，但缓存、锁、计数器这类**观测副作用**需要可变，`mutable` 就是这个官方逃生口。
- **`register` 现在还能用吗？** 答：C++17 起作为存储类说明符已被移除，写它会编译错误；它当初也无法强制变量真的进寄存器（只是建议），现代编译器优化远胜人工提示。

### 10.1 三类变量一表通

### 10.2 五种存储类

| 关键字 | 一句话 | 现代状态 |
|--------|--------|---------|
| `auto` | 局部默认（旧）/类型推导（C++11 新） | 只用"类型推导"义 |
| `register` | 建议进寄存器，不能取地址 | **C++17 移除** |
| `static` | 活得久 + 藏得深 | 有效 |
| `extern` | 别处定义，我来声明 | 有效（跨文件必需） |
| `mutable` | const 成员函数的例外 | 有效（只能修饰类成员） |

### 10.3 多文件三件套

```
xxx.h    →  声明 + 防护（#pragma once + #ifndef XXX_H_ ... #endif）
xxx.cpp  →  #include "xxx.h" + 实现（唯一一份定义）
main.cpp →  #include "xxx.h" + 调用；所有 .cpp 一起编译链接
```

### 10.4 include 与防重复

| 写法 | 搜索顺序 | 用于 |
|------|---------|------|
| `#include <iostream>` | 系统路径 | 标准库/第三方 SDK |
| `#include "student.h"` | 项目目录 → 系统路径 | 自定义头 |

三种防重复：`#ifndef/#define/#endif`（标准）｜`#pragma once`（快、非标准）｜`_Pragma("once")`（可与宏搭配）→ **生产用前两者组合**。

### 10.5 四类报错指纹速判

| 报错 | 真实含义 | 第一反应 |
|------|---------|---------|
| `'x' was not declared in this scope` | 名字不在作用域 / 没 include | 检查声明位置与 `#include` |
| `redefinition of '...'`（编译期） | 同一翻译单元里被粘了两份定义 | 给头文件加宏守卫 |
| `multiple definition of '...'`（链接期） | 不同 `.cpp` 各带一份定义 | 头文件改 `extern` 声明，定义留一处 |

## 十三、新手最常问的 5 个问题（Q&A）

**Q1：既然全局变量跨函数共享很方便，为什么大家都劝我少用？**
A：因为"共享方便"的另一面是"责任不明"。任何函数都能改它，出问题时你得把所有函数都排查一遍；单元测试也没法独立跑（前一个用例改了状态，后一个就挂了）。折中做法：**能用参数/返回值传递的就别用全局；确实需要全局状态时，把它封进类的私有成员，通过接口访问**——这样至少能定位到"谁改了它"。

**Q2：`static` 局部变量和全局变量都存在静态区，那还有什么区别？**
A：区别在**作用域和链接性**，不在存储位置。二者内存都在静态区、都活到程序结束，但：全局变量在本文件所有函数可见（且可被 `extern` 拉走），`static` 局部变量**只有它那一个宿主函数能看见名字**。所以 `static` 局部 = "自带访问控制的迷你全局"，是比全局变量更克制的选择。

**Q3：我的 `student.h` 明明只 include 了一次，为什么还报 redefinition？**
A：九成是**间接重复包含**。你的 `main.cpp` 可能同时 include 了 `a.h` 和 `b.h`，而 `a.h` 和 `b.h` 又各自 include 了 `student.h` —— 到编译器眼里 `student.h` 就被粘贴了两次（菱形依赖）。这正是本笔记知识点 10 端到端演示复现的场景。**结论：防护要加在被包含的头文件自己身上，而不是靠使用者自觉。**

**Q4：既然有了 `#pragma once`，为什么还要学宏守卫这么土的东西？**
A：三个理由：① 面试会问（`#pragma once` 非标准、兼容性差、只能管整个文件）；② 有些场景必须用宏守卫，例如只想保护头文件中**某一段**声明、或需要靠卫士宏判断"这个头是否已被引入"；③ 阅读真实工程时，绝大多数开源项目仍在用宏守卫。记住结论：**日常两个一起写，`#pragma once` 提效率，`#ifndef` 保下限。**

**Q5：VS 里新建了 `student.cpp`，代码没错，为什么 Build 还是报 unresolved external symbol？**
A：因为文件只在磁盘上，没进工程的编译清单（`.vcxproj` 的 `ClCompile` 列表）。VS 里要用 **"解决方案资源管理器 → 源文件 → 右键 → 添加 → 现有项"**，确认它出现在工程树中。若你是手工把文件拷进目录的，VS 不会自动识别。这也是"分开编译"模型的必然结果——**没参与编译的文件，链接器永远找不到它的符号。**

### 14.3 工业级 C++ 编码规范补充

**(1) 头文件命名与卫士宏命名**

| 规则 | 例子 |
|------|------|
| 文件名：大驼峰或全小写下划线，与类名一致 | `Student.h` / `student.h`（同一项目保持统一） |
| 卫士宏：**全大写 + 下划线**，尽量含路径信息 | `PROJECT_MODULE_STUDENT_H_` |
| 不要用保留标识符开头 | ❌ `_STUDENT_H`（`_`+大写是编译器保留的）→ ✅ `STUDENT_H_` |
| `.hpp` 用于纯头文件实现库（OpenCV 风格） | `opencv2/core.hpp` |
| 模板/inline 实现放头文件，其余一律放 `.cpp` | — |

**(2) include 顺序约定（Google / LLVM 风格通用）**

```cpp
// foo.cpp
#include "foo.h"          // 1. 自身头文件（放最前面，逼自己保证 foo.h 自包含）

#include <cstdio>         // 2. C 标准库
#include <cassert>

#include <string>         // 3. C++ 标准库
#include <vector>

#include <boost/...>      // 4. 第三方库
#include <opencv2/core.hpp>

#include "project/util/bar.h"   // 5. 本项目其他头文件（按字母序）
```

**为什么第一条必须是自身头文件**：如果 `foo.h` 依赖别的头却没自己 include，那么把它放在第一个就会立刻报错——**顺序本身就是自包含性的检测器**。

**(3) 命名空间与头文件的配合**

```cpp
// student.h
#pragma once
#ifndef MYPROJ_MODEL_STUDENT_H_
#define MYPROJ_MODEL_STUDENT_H_

namespace myproj {        // 用命名空间包一层，避免全局名字撞车
namespace model {

class Student { public: void printInfo() const; };
extern int g_total;       // 全限定名是 myproj::model::g_total

}  // namespace model
}  // namespace myproj

#endif // MYPROJ_MODEL_STUDENT_H_
```

```cpp
// student.cpp
#include "student.h"
#include <iostream>

myproj::model::Student::Student() { /* ... */ }   // 定义处用全限定名
void myproj::model::Student::printInfo() const { std::cout << "info\n"; }
```

**三条铁律**：

1. **头文件里永远不要写 `using namespace std;`**（它会顺着 include 传染给所有使用者）；
2. **头文件必须自包含**——单独用它就能编译通过，不依赖"别人先 include 了什么"；
3. **尽量减少头文件依赖**：能用前置声明（`class B;`）就不要 `#include "B.h"`，把真正的 include 推到 `.cpp` 里，可显著缩短编译时间。

**(4) 一个模块的完整文件清单模板**

```
src/
├── model/
│   ├── student.h        ← 对外接口（声明 + 防护）
│   └── student.cpp      ← 实现（唯一一份定义）
├── util/
│   ├── logger.h
│   └── logger.cpp
└── main.cpp             ← 只负责组装与流程
```

```cpp
int callCount() {                 // 版本一：只增不减
    static int n = 0;             // 只在第一次经过时初始化为 0
    return ++n;                   // 前置++：先自增再返回
}

int resetCount(bool doReset) {    // 版本二：提供重置入口
    static int n = 0;
    if (doReset) n = 0;           // 需要清零时手动赋值
    return ++n;
}

int main() {
    cout << callCount() << " " << callCount() << " " << callCount() << endl;
    cout << resetCount(true) << " " << resetCount(false) << endl;
    return 0;
}
// 输出：
// 1 2 3
// 1 2
```

**为什么普通局部变量做不到**：普通局部变量每次调用都在栈上重新创建并重新执行初始化语句，函数返回即销毁，因此永远只能得到同一个值（`1 1 1`）；而 `static` 让内存搬到静态区、初始化只发生一次，状态才得以跨调用累积。

</details>

**① 宏守卫完整模板与逐行作用**

```cpp
#ifndef MYPROJ_STUDENT_H_   // 第1行：若该卫士宏尚未定义 → 说明本头文件第一次被展开，进入分支
#define MYPROJ_STUDENT_H_   // 第2行：立即定义它，作为"我已展开过"的凭证（预处理期生效）

// 头文件内容                // 第3行起：真正的声明/定义；第二次 include 时整段被预处理器丢弃

#endif // MYPROJ_STUDENT_H_ // 末行：闭合条件块，必须与 #ifndef 一一配对，缺失即 unterminated #ifndef
```

**② 宏名必须独一无二的原因**：宏表是整个翻译单元共享的。若 `utils.h` 与 `logger.h` 都用 `_NAME_H`，先被 include 的那个会把宏打上，后者整段被判定为"已展开"而消失 → 使用者报 `undeclared identifier`，且错误信息完全不指向真正原因。

**③ 搜索顺序**：`<>` 只查编译器类库路径（`-I` / `INCLUDE`）；`""` 先查当前文件所在目录与项目目录，找不到再回落到系统路径。

**④ 两个场景**
- `#pragma once` 更优：数百个头文件互相依赖的大型工程，反复 include 同一底层头。基于文件身份在读取前就短路，省掉磁盘 IO 与宏识别，编译更快。
- `#ifndef` 更优：(a) 需要跨老版本/非主流编译器保证可移植（`#pragma once` 不认识时只给警告、防护失效）；(b) 同一物理文件需经两条不同路径（符号链接、网络映射盘）进入同一翻译单元，`#pragma once` 会误判为两个文件各展开一次，只有宏守卫能正确去重；(c) 只想保护头文件中的**某一段**代码而非整个文件。

<summary>参考答案要点（做完再看）</summary>

**1）各文件放什么**

| 文件 | 内容清单 |
|------|---------|
| `student.h` | 防护三件套 + `class Student` 声明（成员函数原型）+ `void createStudent(); void printAll(); int getTotal();` + `extern int g_studentTotal;`（**声明**） |
| `student.cpp` | `#include "student.h"` + `int g_studentTotal = 0;`（**唯一定义**）+ 所有成员函数与三个自由函数的函数体 |
| `main.cpp` | `#include <iostream>` + `#include "student.h"` + `main()` 里调用 `createStudent/printAll/getTotal` |

**2）为什么定义不能都塞头文件**：`int g_studentTotal = 0;` 是定义，被两个 `.cpp` 各 include 一次就有两份强符号 → 链接期 `multiple definition of 'g_studentTotal'`。宏守卫只能防"同一翻译单元内被粘两次"，防不了"两个翻译单元各粘一次"，所以必须"声明多处、定义一处"。

**3）防护写法（推荐组合）**

```cpp
#pragma once
#ifndef MYPROJ_MODEL_STUDENT_H_
#define MYPROJ_MODEL_STUDENT_H_
// ... 全部声明 ...
#endif // MYPROJ_MODEL_STUDENT_H_
```

**4）VS 操作步骤**（对应课件 P6–P8 五步法）：新建项目 Test001 →「头文件」文件夹右键→添加→新建项→头文件(.h)→命名 `student.h`→写声明 →「源文件」文件夹右键→添加→新建项→C++文件(.cpp)→命名 `student.cpp`→**第一行 `#include "student.h"`**→写实现 → 再加一个 `main.cpp`，`#include "student.h"` 后直接调用 → 生成解决方案。

**5）命令行编译**

```bash
g++ -std=c++11 main.cpp student.cpp -o app && ./app
```

**6）为什么 main 不必知道实现细节**：`main.cpp` 只看到 `student.h` 里的原型和类布局，编译器据此就能完成调用；函数体在 `student.o` 里，由链接器缝上地址。这正是多文件编程的核心价值——**接口与实现分离**：实现可任意重写而引用方无需重新编译（只要接口不变）、多人可并行开发、内部数据可被隐藏（private 成员），并且支持"只交付 `.h` + 二进制"的商业发布形态。

### 24.2 全章核心心法（三句话带走）

1. **三个维度永远分开问**：作用域（谁能叫它的名字）、生命周期（它什么时候生什么时候死）、链接性（别的文件能不能找到它）。所有本章问题都能被这三问拆解。
2. **`.h` 是契约，`.cpp` 是履行**：声明可以重复无数次，定义必须全程序唯一一份（ODR）。头文件保护就是为了让"重复粘贴契约"这件事无害。
3. **一切预处理问题都是文本问题**：`#include` 是复制粘贴，`#ifndef` 是条件删除，`typedef` 却发生在复制之后——分清"预处理期／编译期／运行期"，就不会被同一个语法符号迷惑。

## 附录 A｜本章知识点的"编译期 / 运行期 / 预处理期"归属总表

这是本章最容易混的一根线，单独整理成表：

| 语法现象 | 生效阶段 | 说明 |
|---------|---------|------|
| `#include <...>` / `"..."` | **预处理期** | 文本级文件插入，每处都会真的插一遍 |
| `#ifndef/#define/#endif` 宏守卫 | **预处理期** | 条件为假时内容根本不交给编译器 |
| `#pragma once` | **编译器识别（早于展开）** | 基于文件身份短路，比宏守卫更早 |
| `_Pragma("once")` | 同上 | 运算符形态，故可被宏展开产生 |
| `typedef int abc;` | **编译期** | 类型别名替换，零运行时开销 |
| `using abc = int;` | **编译期** | 同上，且支持模板别名 |
| `static` 局部变量的**初始化** | **运行期第一次经过该行** | 不是编译期！也不是每次调用 |
| `static` 局部变量的**存储分配** | 程序启动前（静态区就位） | 初值在可执行文件的静态数据段 |
| 全局变量的初始化 | 进入 `main` 之前 | 跨翻译单元顺序未定义 |
| 普通局部变量的初始化语句 | **运行期每次执行到该行** | 所以 `int v2 = 0;` 每次都重写 |
| `extern int x;` | **编译期登记引用 + 链接期解析** | 本身不产生任何内存 |
| 变量出 `{}` 销毁 | **运行期** | 栈指针回退，不调用析构以外的清理（POD 类型无操作） |

## 附录 B｜一键保存本笔记的 Python 脚本

把下面代码存成 `保存学习笔记.py`，放在任意目录运行即可。它会自动创建目标文件夹（含所有上级目录），并把这份完整笔记写入其中。

```python
# -*- coding: utf-8 -*-
# 《第11章 变量作用域和多文件编程》学习笔记 一键保存脚本
# 用法： python 保存学习笔记.py
# 功能：自动创建目标文件夹（含所有上级目录），并以二进制方式把完整笔记
#       逐字节一致地写入其中（不随操作系统改变换行符）。
import os

TARGET_DIR = r"C:\Users\freecss\Desktop\学习1\C++\C++基础篇\11 变量作用域和多文件编程"
FILE_NAME  = "变量作用域和多文件编程学习笔记.md"

NOTES = r'''这里粘贴本笔记全文（从 "# 《C++基础篇》第11章" 到最后一行）'''

def main():
    os.makedirs(TARGET_DIR, exist_ok=True)          # 递归创建目标目录，已存在则跳过
    path = os.path.join(TARGET_DIR, FILE_NAME)
    if os.path.exists(path):                        # 已有旧版笔记时不覆盖，改名加 _v3
        stem, ext = os.path.splitext(FILE_NAME)
        path = os.path.join(TARGET_DIR, stem + "_v3" + ext)
        print("检测到同名文件，改为写入：", path)
    with open(path, "wb") as f:                     # 二进制写入，保证换行符不被改写
        f.write(NOTES.encode("utf-8"))              # 统一以 UTF-8 编码落盘
    print("保存成功：%s（%d 字符）" % (path, len(NOTES)))

if __name__ == "__main__":
    main()
```

> **使用说明**：把 `NOTES = r'''...'''` 中间替换为本笔记全文即可（`r'''` 原始字符串可避免 `\n`、`\t` 被转义）。若笔记正文中出现 `'''`，改用 `r"""..."""` 包裹。脚本内置了"存在即另存 `_v3`"的保护逻辑，重复运行不会覆盖已有笔记。
