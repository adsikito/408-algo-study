通常的 C++ 学习顺序会把语言基础放在最前面，输入输出只当附带一提。本方案把输入输出提到最前，理由是**它不是知识点，而是失分点**。

### 0.1 一个已经存在的具体隐患

`资料\03_算法集训\12_单调栈\例题代码\P5788.cpp` 的题面约束为 **n ≤ 3×10⁶**，原代码如下：

```cpp
#include<iostream>
#include<cstdio>
#include<stack>
using namespace std;
int n;//n<=100
int a[3000005];
stack<int>s;//a[i]
int ans[3000005];//ans[i]就是a[i]右边第一个比a[i]大的数
int main()
{
  cin>>n;
  for(int i=1;i<=n;i++)
  {
    cin>>a[i];
  }
  // ... 后续单调栈逻辑
}
```

三个问题：

| 序 | 问题 | 后果 |
|----|------|------|
| 1 | 使用 `cin>>` 读入 3×10⁶ 个整数，**未关闭流同步** | 实测 2569 至 4694 毫秒，多数 OJ 的时限在 1000 毫秒左右，**极可能超时** |
| 2 | 注释写 `//n<=100`，与题面的 3×10⁶ 不一致 | 注释误导，若按此开数组则会 RE |
| 3 | 数组开到 3000005，与 n 上界刚好匹配 | 本身无错，但边界偏紧，遇到 n 略大于 3×10⁶ 的加强数据会越界 |

**修正后的代码**（只改输入部分，算法逻辑不动）：

```cpp
// g++ -std=c++17 -O2
#include <bits/stdc++.h>
using namespace std;

const int MAXN = 3000000 + 5;   // 边界：按题面上界 +5 冗余，防止加强数据越界
int n;
int a[MAXN];
int ans[MAXN];
stack<int> s;

int main() {
    // 修正一：关闭流同步并解绑，使 cin 的读入速度超过 scanf
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    // 修正二：改回 cin 读入，与上面两行保持一致，全程不混用两套接口
    cin >> n;
    for (int i = 1; i <= n; ++i) cin >> a[i];

    // 单调栈主体逻辑保持不变：从右往左扫，递减栈
    for (int i = n; i >= 1; --i) {
        while (!s.empty() && a[s.top()] <= a[i]) s.pop();
        ans[i] = s.empty() ? 0 : s.top();
        s.push(i);
    }
    for (int i = 1; i <= n; ++i) cout << ans[i] << " \n"[i == n];
    return 0;
}
```

> **【注意】** 上面这份修正**全程使用 `cin` / `cout` 一套接口**，没有混用 `scanf`。
> 因为第一步已经关闭了流同步，此时若再混用 `scanf`，读入顺序会错乱——见 B-1 的易错说明。
> 要么全用一套，要么就别关同步，两者不可兼得。

> **【重点】** 这个修正**不改变任何算法逻辑**，只改输入方式与数组边界。
> 换句话说，这道题原本算法是对的，但会因为输入方式而拿不到分。

## 三、知识点逐讲

### B-1　`cin` / `cout` 与 `scanf` / `printf` 的选择　`P0`　熟练　`[未学]`

> **【重点】** 关闭同步后的 `cin` **比 `scanf` 快约 2 倍**。因此「`cin` 一定比 `scanf` 慢」是过时结论。

**是什么**：C++ 有两套输入输出。一套是 C++ 的 `cin` / `cout`，靠运算符 `>>` 与 `<<` 操作；另一套是继承自 C 的 `scanf` / `printf`，靠格式字符串操作。

**为什么**：默认情况下 `cin` 慢，是因为 C++ 标准要求它**与 C 标准流保持同步**——每读一个字符都要与 `stdin` 缓冲区保持一致，这样两套接口可以混用。这个同步带来了额外开销。但**同步可以关闭**（见 B-2），关闭后 `cin` 反而比 `scanf` 快。

**怎么用**——选择规则：

| 场景 | 选择 | 理由 |
|------|------|------|
| 数据量小（小于 10⁵） | 随意，按习惯 | 差异在毫秒级，不影响结果 |
| 数据量大（10⁵ 以上） | **`cin` 加关闭同步** | 实测最优，且写法比 `scanf` 简洁 |
| 需要格式化输出（对齐、宽度、精度） | `printf` | `printf` 的格式串更直接 |
| 字符串整体读入（含空格） | `getline` | `scanf("%s")` 遇空格即停 |
| 已用 `scanf` 且不想改 | 保持 `scanf` | 不要在同一程序里混用两套 |

> **【易错】** **不要混用**。一旦调用了 `ios::sync_with_stdio(false)`，`cin` / `cout` 的缓冲区与 C 标准流分离，此时混用 `cin` 与 `scanf` 会导致**读入顺序错乱**——数据被另一套缓冲区吞掉。
>
> 判断依据：一个程序里只选一套。要么全用 `cin` / `cout`，要么全用 `scanf` / `printf`。若必须混用，就不要关闭同步。

> **【类比】** 两套接口的同步关系像两个人共用一本记事本。
> 保持同步，等于两人每次动笔前都互相确认一下（安全但慢）；
> 关闭同步，等于各写各的本子（快，但不能互相看）。

**关联**

- `[后续]` 见 B-2 `ios::sync_with_stdio(false)`。它是让 `cin` 变快的开关，是本知识点的直接延伸。
- `[并列]` 见 B-4 手写快读。三者是同一问题的三个层次的解法。
- `[易混]` 见 B-6 格式化输出。`printf` 的格式串能力是 `cout` 需要借助 `iomanip` 才能达到的。

### B-2　`ios::sync_with_stdio(false)` 与 `cin.tie(nullptr)`　`P0`　熟练　`[未学]`

> **【重点】** 这两行是赛场代码的标配，写在 `main` 函数开头第一句。**只需一行，就能让 `cin` 从最慢变成比 `scanf` 快两倍。**

**是什么**：两个函数调用，各自关闭一项默认开销。

```cpp
ios::sync_with_stdio(false);   // 关闭：C++ 流与 C 标准流的同步
cin.tie(nullptr);              // 解绑：cin 与 cout 的绑定关系
```

**为什么**：

- **同步开销**：C++ 默认要求 `cin` 与 `stdin` 保持一致，以便两套接口混用。这使 `cin` 每次读入都要额外检查。关闭后 `cin` 直接使用自己的缓冲区。
- **绑定开销**：`cin` 默认绑定到 `cout`，意思是「每次从 `cin` 读入之前，先把 `cout` 的缓冲区刷新一遍」。这是为了让交互式程序能正常提示用户输入。但在竞赛中，程序与测试数据之间没有交互，这个刷新纯粹是浪费——尤其当 `cout` 里积压了大量未输出的内容时。

**怎么用**：

```cpp
// g++ -std=c++17 -O2
#include <bits/stdc++.h>
using namespace std;

int main() {
    // 这两行必须写在 main 开头，且在第一次输入输出之前
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    int n;
    cin >> n;
    long long sum = 0LL;          // 边界：累加可能溢出 int，必须用 long long
    for (int i = 0; i < n; ++i) {
        int x;
        cin >> x;
        sum += x;
    }
    cout << sum << "\n";          // 用 "\n" 而不是 endl，见 B-3
    return 0;
}
```

**实测效果**（本地实测，环境见本章第四节）：

| 写法 | 读入 3×10⁶ 个整数耗时 |
|------|--------------------|
| `cin` 默认（保持同步） | 2569 毫秒 |
| `cin` 关闭同步并解绑 | **591 毫秒** |
| `scanf` | 1448 毫秒 |

**关闭同步使 `cin` 快了约 4.3 倍，并且超过了 `scanf` 约 2.4 倍。**

> **【易错】** 三个常见错误：
>
> 1. **位置写错**。写在循环里或在第一次 `cin` 之后才写，无效。
> 2. **写了之后仍混用 `scanf`**。此时读入顺序会错乱，见 B-1 的易错说明。
> 3. **忘记 `cin.tie(nullptr)`**。只关同步、不解绑，能拿到大部分收益，但在输出量大时仍会被 `cout` 的刷新拖慢。

> **【补充】** 关于 `#include <bits/stdc++.h>`：
> **它不是标准 C++ 头文件，而是 GCC 的扩展**。在洛谷、Codeforces 等使用 Linux g++ 的评测机上可正常使用；
> 但在 MSVC 上不存在，且**部分 MinGW-W64 版本的 `bits/stdc++.h` 会拉入 `filesystem` 头文件导致编译失败**。
>
> 本节实测过程中就遇到了这一情况：本地 MinGW-W64 g++ 8.1.0 编译 `bits/stdc++.h` 时报出
> `std::filesystem::path` 相关的数十条错误。**改用显式头文件后编译通过，五组测试用例全部正确**。
>
> **结论**：本地调试时建议使用显式头文件，或确认本地工具链版本；
> 提交到 Linux 评测机时再用 `bits/stdc++.h` 节省篇幅。
> 判断依据是**能否在本地编译通过**，而不是「别人都用」。

> **【记忆】** 关同步，解绑定，写在 main 第一行。

**关联**

- `[前置]` 见 B-1。需要先理解两套接口的同步关系，才知道这一行在关掉什么。
- `[后续]` 见 B-3。关闭同步后，`endl` 的刷新开销反而更突出，必须一起改。
- `[组合]` 与 B-3 组合使用，才构成完整的输入输出优化方案。

### B-3　`"\n"` 与 `endl` 的区别　`P0`　熟练　`[未学]`

> **【重点】** `endl` 会**强制刷新缓冲区**，`"\n"` 只换行。本次实测中两者相差 **约 32 倍**，是本模块中代价最大的一个写法差异。

**是什么**：

| 写法 | 行为 |
|------|------|
| `"\n"` | 只是插入一个换行符，内容留在缓冲区 |
| `std::endl` | 插入换行符**并且**调用 `flush()`，强制把缓冲区内容写到输出设备 |

**为什么**：强制刷新意味着每一次 `endl` 都要真正与磁盘或管道交互一次。在 10⁶ 行输出中，这就是 10⁶ 次系统调用级别的开销。而 `"\n"` 让缓冲区自己攒够再一次性写出，开销大幅降低。

**怎么用**：

```cpp
// 正确：输出量大时一律使用 "\n"
for (int i = 0; i < n; ++i) {
    cout << ans[i] << "\n";       // 只换行，不刷新
}

// 不推荐：在循环内使用 endl
for (int i = 0; i < n; ++i) {
    cout << ans[i] << endl;        // 每次都强制刷新，输出量越大代价越高
}
```

**实测效果**（本地实测，输出 10⁶ 行）：

| 写法 | 轮 1 | 轮 2 |
|------|------|------|
| `endl` | 8494 毫秒 | 6139 毫秒 |
| `"\n"` | 332 毫秒 | **193 毫秒** |

**两者相差约 26 至 32 倍。**

> **【易错】** 常见的两种错误认知：
>
> 1. **「`endl` 更规范」**。在**工程代码**中，`endl` 有其意义（比如崩溃前确保日志落盘）。但在竞赛里，程序结束时会自动刷新，手动刷新毫无收益。
> 2. **「只差一点点」**。单看 10⁶ 行差 6 秒，这已经超过多数题目的总时限。

> **【规律】** 判断标准很简单：**只要在循环里，就用 `"\n"`**。
> 循环之外的少量输出用哪个都无所谓。

> **【类比】** 缓冲区像快递打包。`"\n"` 是「把包裹放进箱子继续装」；
> `endl` 是「每放一件就叫一次快递取走」。后者每次输出都触发一次刷新，实测慢约 32 倍。

**关联**

- `[前置]` 见 B-2。关闭同步后，`cout` 的缓冲行为更独立，`endl` 的刷新代价更明显。
- `[并列]` 见 B-5 手写快写。输出量极大时，手写快写是比 `"\n"` 更进一步的方案。
- `[同构]` 与 B-2 中「`cin.tie` 导致读入前刷新 `cout`」是同一个机制的两个表现。

### B-4　手写快读　`P1`　会用　`[未学]`

> **【重点】** 手写快读只比「关闭同步的 `cin`」快约 **13%**，边际收益有限。**先把 B-2 做好，再考虑快读。**

**是什么**：用 `getchar()` 逐字符读取并手动解析整数，绕开 `cin` 与 `scanf` 的全部格式化开销。

**为什么**：`cin` 与 `scanf` 都要解析格式串、处理各种类型分支。手写快读只处理整数这一种情况，代码路径最短。但正因为它只快一点，**优先级低于 B-2**。

**怎么用**：

```cpp
// g++ -std=c++17 -O2
#include <cstdio>

// 快读：逐字符解析整数，支持负数
static inline int read_int() {
    int x = 0, f = 1;
    char c = (char)getchar();
    // 跳过非数字字符；遇到负号则记录符号
    while (c < '0' || c > '9') {
        if (c == '-') f = -1;
        c = (char)getchar();
    }
    // 逐位累加
    while (c >= '0' && c <= '9') {
        x = x * 10 + (c - '0');
        c = (char)getchar();
    }
    return x * f;
}

int main() {
    int n = read_int();
    long long sum = 0LL;
    for (int i = 0; i < n; ++i) sum += read_int();   // 边界：用 long long 防溢出
    printf("%lld\n", sum);
    return 0;
}
```

**实测效果**：

| 写法 | 读入 3×10⁶ 个整数耗时 |
|------|--------------------|
| `cin` 关闭同步并解绑 | 591 毫秒 |
| 手写快读 | **523 毫秒** |

差距约 13%。

> **【易错】** 四个常见缺陷：
>
> 1. **不支持负数**。只用 `c >= '0' && c <= '9'` 判断，遇到 `-` 会死循环。
> 2. **不处理文件末尾**。`getchar()` 在读到 EOF 时返回 `-1`，若循环条件未考虑会死循环。多组数据题必须处理。
> 3. **写成非 `inline` 的函数**。函数调用开销会吃掉部分收益，应加 `inline`。
> 4. **对小数与字符串束手无策**。快读只适合整数；输入含浮点数或字符串时不要用。

> **【补充】** 手写快读的收益取决于编译器与 OJ。在部分 OJ 上，关闭同步的 `cin` 已经足够快，
> 快读带来的 13% 没有意义。**判断依据是：先提交关闭同步的版本，若确实超时再上快读。**

**关联**

- `[前置]` 见 B-2。必须先做关闭同步，快读才有意义。
- `[后续]` 见 B-5 手写快写。两者成对出现。
- `[并列]` 见 B-1。三者是「读入速度」这条线上的三个层次。

### B-5　手写快写　`P2`　会用　`[未学]`

> **【重点】** 快写的适用场景比快读**窄得多**。只有在输出量极大（10⁶ 行以上）且用 `"\n"` 仍超时才需要。

**是什么**：用 `putchar()` 逐字符输出整数，替代 `cout` 或 `printf`。

**为什么**：与快读同理，绕开格式化开销。但输出的瓶颈通常不在格式化，而在实际的写出次数——而这一点由缓冲区决定，不是由 `printf` 与 `putchar` 的差别决定。因此收益远小于快读。

**怎么用**：

```cpp
// g++ -std=c++17 -O2
#include <cstdio>

// 快写：逐字符输出非负整数
static inline void write_int(int x) {
    if (x == 0) { putchar('0'); return; }
    if (x < 0) { putchar('-'); x = -x; }     // 边界：处理负数
    char buf[12];                            // int 最多 10 位，12 足够
    int len = 0;
    while (x > 0) {
        buf[len++] = (char)('0' + x % 10);   // 逐位取出，此时是逆序
        x /= 10;
    }
    while (len--) putchar(buf[len]);         // 逆序输出得到正序
}
```

> **【补充】** 实际赛场上，**先把 B-2 与 B-3 做到位**（关闭同步、用 `"\n"`），
> 绝大多数题目已经足够。手写快写的收益不明显，且代码更长更易错。
> 建议仅在明确遇到输出瓶颈时使用。

**关联**

- `[前置]` 见 B-3。先确认已经用 `"\n"` 替代 `endl`。
- `[并列]` 见 B-4 手写快读。两者成对，但快写的必要性远低于快读。

### B-6　格式化输出与浮点精度控制　`P0`　熟练　`[未学]`

> **【重点】** 浮点题的常见失分不是算法错，而是**输出格式不符**。`%f` 默认输出 6 位小数，而题目可能要求 2 位、9 位或不限位数。

**是什么**：控制输出的小数位数、字段宽度、对齐方式。

**为什么**：多数 OJ 使用精确比对，输出格式只要差一位小数就是 WA。而题目要求的精度各不相同。

**怎么用**——两种写法对照：

| 需求 | `printf` 写法 | `cout` 写法 |
|------|-------------|-----------|
| 保留 2 位小数 | `printf("%.2f\n", x);` | `cout << fixed << setprecision(2) << x << "\n";` |
| 保留 9 位小数 | `printf("%.9f\n", x);` | `cout << fixed << setprecision(9) << x << "\n";` |
| 有效数字 6 位（非小数位） | `printf("%g\n", x);` | `cout << setprecision(6) << x << "\n";` |
| 左对齐宽度 8 | `printf("%-8d|", x);` | `cout << left << setw(8) << x << "|";` |
| 补前导零 | `printf("%05d\n", x);` | `cout << setfill('0') << setw(5) << x << "\n";` |
| 输出 `long long` | `printf("%lld\n", x);` | `cout << x << "\n";` |

```cpp
// g++ -std=c++17 -O2
#include <bits/stdc++.h>
using namespace std;

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    double x = 3.14159265358979;
    printf("%.2f\n", x);    // 3.14
    printf("%.9f\n", x);    // 3.141592654

    cout << fixed << setprecision(2) << x << "\n";   // 3.14
    cout << fixed << setprecision(9) << x << "\n";   // 3.141592654
    return 0;
}
```

> **【易错】** 五个高频陷阱：
>
> 1. **`cout` 忘记加 `fixed`**。`setprecision(2)` 单独使用是「2 位**有效数字**」而不是「2 位小数」，
>    例如 `3.14159` 会输出 `3.1`，不是 `3.14`。**`fixed` 与 `setprecision` 必须成对使用。**
> 2. **`cout` 的格式状态会持续**。`fixed` 与 `setprecision` 一旦设置，对其后所有输出生效，
>    不会自动复位。
> 3. **`printf` 的 `%f` 与 `%lf`**。`printf` 中 `float` 会自动提升为 `double`，写作 `%f` 即可；
>    但 `scanf` 读 `double` **必须**写 `%lf`，写 `%f` 会读错。
> 4. **精度不足导致 WA**。题目要求误差小于 10⁻⁶ 时，至少输出 9 位小数比较安全。
> 5. **`endl` 与 `setprecision` 混用**。这类浮点输出往往在循环外，用 `endl` 影响不大，
>    但仍建议统一用 `"\n"`。

> **【补充】** 部分题目会明确要求「误差不超过 10⁻⁶」，此时输出 6 位小数是不够的，
> 应输出 9 位或更多。**判断依据是看题目给的精度要求，不是凭习惯写 2 位。**

**关联**

- `[前置]` 见 B-1。`printf` 与 `cout` 两套写法的选择。
- `[并列]` 见 B-3。同属输出格式与性能这一组。
- `[易混]` 见 B-7 多组数据输入。多组数据题往往同时要求严格的输出格式。

### B-7　多组数据输入的写法　`P0`　熟练　`[未学]`

> **【重点】** 多组数据题**必须处理文件末尾**。用 `scanf` 返回值或 `cin` 的流状态判断，不能靠读取组数。

**是什么**：一道题包含多组测试数据，但**不告诉你有几组**，读到输入结束为止。

**为什么**：这是蓝桥杯与 CCF 的常见出题形式。若靠 `while(true)` 加输出判断，容易死循环或多输出一次。

**怎么用**——三种标准写法：

```cpp
// 写法一：scanf 判断返回值（推荐）
// scanf 在成功读入时返回成功赋值的项数，读到 EOF 返回 -1
int a, b;
while (scanf("%d%d", &a, &b) != EOF) {
    printf("%d\n", a + b);
}

// 写法二：cin 直接作条件
// 流对象在求值时会隐式转换为 bool，读到 EOF 或出错时为 false
int a, b;
while (cin >> a >> b) {
    cout << a + b << "\n";
}

// 写法三：题目给出组数 T
int T;
scanf("%d", &T);
while (T--) {
    int a, b;
    scanf("%d%d", &a, &b);
    printf("%d\n", a + b);
}
```

> **【易错】** 五个常见问题：
>
> 1. **漏掉文件末尾判断**。写成 `while (1) { scanf(...); ... }`，读到末尾后 `a`、`b` 保持上一轮的值，
>    导致最后多输出一组，或无限循环。
> 2. **每组数据忘记重置状态**。若使用了栈、队列、数组计数器，**每组数据开始前必须清空**。
>    多组数据题的经典错误是「第一组对、后面全错」，几乎都是状态未清空。
> 3. **输出格式不对**。有的题目要求组间空行、组末不空行，需要仔细读题。
> 4. **快读未处理 EOF**。用 B-4 的快读时，`getchar()` 返回 `-1` 的循环条件必须补上。
> 5. **读入顺序与输出顺序错位**。混用两套接口时更易发生（见 B-1）。

> **【记忆】** 多组数据的两个必做动作：**判末尾，清状态**。

**关联**

- `[前置]` 见 B-1。需要知道两套接口各自的结束判断方式。
- `[后续]` 见 B-8 `freopen`。多组数据题的本地测试需要重定向。
- `[组合]` 与 B-9 调试宏组合，可在本地反复测试多组数据。

### B-8　`freopen` 重定向与本地调试　`P1`　会用　`[未学]`

> **【重点】** 本地用 `freopen` 从文件读入，省去每次手动粘贴测试数据。**但提交前必须注释掉，否则会 RE 或 WA。**

**是什么**：把标准输入输出重定向到文件。

**为什么**：竞赛题的测试数据往往很长，手动粘贴到终端既慢又容易漏字符。重定向到文件后可以反复运行。

**怎么用**：

```cpp
// g++ -std=c++17 -O2
#include <bits/stdc++.h>
using namespace std;

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    // 本地调试用：从 in.txt 读入。提交前必须注释掉下面一行
    freopen("in.txt", "r", stdin);
    // 也可重定向输出，便于与答案逐行比对
    // freopen("out.txt", "w", stdout);

    int n;
    cin >> n;
    cout << n << "\n";
    return 0;
}
```

> **【易错】** 三个常见事故：
>
> 1. **忘记注释掉就提交**。OJ 上没有 `in.txt`，`freopen` 会失败，导致读到空输入，直接 RE 或 WA。
>    **这是新手最常见的失分原因之一。**
> 2. **文件名大小写不符**。Windows 不区分大小写，多数 OJ 的评测环境区分，本地通过不代表提交通过。
> 3. **重定向后忘记删除输出文件**。反复运行会覆盖，若需要保存多次结果应换文件名。

> **【补充】** 更安全的做法是用 B-9 的条件编译宏，
> 让 `freopen` **只在本地编译时生效**，从根本上杜绝忘记注释的问题。

**关联**

- `[前置]` 见 B-7。多组数据题的本地测试依赖重定向。
- `[后续]` 见 B-9。条件编译宏是解决「忘记注释」的正解。
- `[组合]` 与 B-9 组合是最推荐的本地调试方案。

### B-9　编译期调试宏　`P1`　熟练　`[未学]`

> **【重点】** 用条件编译区分「本地」与「提交」两种状态，**从根本上消除忘记注释 `freopen` 的风险**。

**是什么**：利用 `#ifdef` 与 `#ifndef`，让同一份代码在本地编译与 OJ 编译时走不同分支。

**为什么**：B-8 的手动注释方式依赖人的记性，而人在紧张比赛中最容易忘记。条件编译把这个动作交给编译器。

**怎么用**：

```cpp
// g++ -std=c++17 -O2 -DLOCAL
#include <bits/stdc++.h>
using namespace std;

// 仅当定义了 LOCAL 时才生效的调试块
#ifdef LOCAL
#define DEBUG_MODE 1
#else
#define DEBUG_MODE 0
#endif

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    // 本地编译时自动重定向，提交时自动跳过
    if (DEBUG_MODE) {
        freopen("in.txt", "r", stdin);
        // freopen("out.txt", "w", stdout);
    }

    int n;
    cin >> n;
    cout << n << "\n";
    return 0;
}
```

**本地编译命令**（定义 `LOCAL`）：

```bash
g++ -std=c++17 -O2 -DLOCAL -o main main.cpp && ./main
```

**提交时**：直接复制源码，不需要任何修改——`LOCAL` 未定义，调试块自动失效。

> **【易错】** 三个注意点：
>
> 1. **提交时连编译命令一起复制**。部分 OJ 允许自定义编译参数，若无脑粘贴 `-DLOCAL`，
>    等于把本地调试分支带上了评测机。**只复制源码，不复制编译命令。**
> 2. **调试输出未加条件**。若调试用的 `cerr` 或 `cout` 没包在条件编译里，提交后会污染输出。
>    建议统一用 `cerr` 输出调试信息（`cerr` 不影响标准输出，且不会被判题读取）。
> 3. **宏名冲突**。`LOCAL` 在某些评测环境可能已被占用，改用更特异的名称如 `LOCAL_DEBUG`。

> **【补充】** 配套的调试输出宏，可进一步减少代码量：

```cpp
// 仅本地生效的调试输出
#ifdef LOCAL
#define dbg(x) cerr << #x << " = " << (x) << "\n"
#else
#define dbg(x) ((void)0)   // 提交后展开为空，零开销
#endif
```

使用方式：`dbg(n); dbg(sum);`——本地会输出变量名与值，提交后完全消失。

**关联**

- `[前置]` 见 B-8。宏解决的是 `freopen` 忘记注释的问题。
- `[并列]` 见 F 模块的编译选项与对拍。三者同属竞赛工程化。
- `[组合]` 与 B-8 组合构成推荐的本地调试方案。

1. **优先做 B-2**。加两行代码，`cin` 从 2569 毫秒降到 591 毫秒，收益最大且零风险。

3. **手写快读是备选**。只快 13%，且代码更长更易错。**先提交关闭同步的版本，确实超时再上快读。**

## 六、本章总结

### 6.1 核心内容（一页纸）

**必背两行代码**（写在 `main` 函数开头，第一次输入输出之前）：

```cpp
ios::sync_with_stdio(false);   // 关闭同步
cin.tie(nullptr);              // 解绑
```

**必改一处写法**：循环内所有 `endl` 换成 `"\n"`。

**选择规则**：

| 场景 | 写法 |
|------|------|
| 数据量小于 10⁵ | 任意，按习惯 |
| 数据量 10⁵ 以上 | `cin` + 关闭同步，或 `scanf` |
| 需要格式化输出 | `printf` |
| 字符串整体读入 | `getline` |
| 浮点输出 | `printf("%.Nf")` 或 `cout << fixed << setprecision(N)` |
| 多组数据 | `while (scanf(...) != EOF)` 或 `while (cin >> ...)` |
| 本地调试 | 条件编译宏包住 `freopen` |

**四条铁律**：

1. **同程序不混用两套接口**。关了同步还混用，读入顺序会错。
2. **循环内不用 `endl`**。32 倍差距。
3. **多组数据必判末尾、必清状态**。
4. **`freopen` 必须用条件编译包裹**，不靠手动注释。

**三条实测结论**：

1. 关闭同步使 `cin` 从 2569 毫秒降到 591 毫秒，**快 4.3 倍**，且**超过 `scanf` 2.4 倍**。
2. `endl` 输出 10⁶ 行耗时 6139 毫秒，`"\n"` 只需 193 毫秒，**相差约 32 倍**。
3. 手写快读只比关闭同步的 `cin` 快 **13%**，优先级排在最后。

**一处已修正的隐患**：`资料\03_算法集训\12_单调栈\例题代码\P5788.cpp` 的输入方式。
该题 n ≤ 3×10⁶，原代码用 `cin` 且未关闭同步，改法见本章第零节。

### P5788 修正代码的用例验证

| 序 | 输入 | 期望输出 | 实际输出 | 结果 |
|----|------|---------|---------|------|
| 1 | `5` / `3 1 4 5 2` | `3 3 4 0 0` | `3 3 4 0 0` | 通过 |
| 2 | `1` / `7` | `0` | `0` | 通过（单元素边界） |
| 3 | `3` / `1 2 3` | `2 3 0` | `2 3 0` | 通过（严格递增） |
| 4 | `3` / `3 2 1` | `0 0 0` | `0 0 0` | 通过（严格递减） |
| 5 | `3` / `1 1 1` | `0 0 0` | `0 0 0` | 通过（等值边界，验证弹出条件用 `<=`） |

> **【要点】** 用例 5 是关键。弹出条件写 `<=` 还是 `<`，只在有相等元素时才体现差异。
> 写 `<` 会让相等元素互相挡住，输出错误答案。**这是单调栈题最容易错的一处**，
