### F-1　比赛代码模板　`P0`　熟练　`[未学]`

> **【重点】** 模板的价值不是省几行字，而是**把「容易忘的固定动作」变成永远不会忘**：
> 关同步、开大数组、定义常量、准备调试开关。**目标是形成肌肉记忆。**

**是什么**：一份固定开头的代码骨架，每次比赛直接从它开始。

**为什么**：三个具体收益 ——
1. **省开局时间**：不用每次想「要不要关同步」。**而这恰好是模块 B 统计出的最大缺口**
   （`ios::sync_with_stdio` 全库仅 1 次）。
2. **避免遗忘**：常量、数组大小、调试宏一次性就位。
3. **统一风格**：自己读自己的代码更快。

**怎么用**：

1. 保存为本地文件，比赛开始第一件事就是粘贴它。
2. **只在必要时增加内容**，保持骨架短小（超过 30 行就失去了「扫一眼确认」的价值）。
3. 模板里**必须包含**：关同步、常用头文件、常量、调试开关。
4. **不要把整份题解塞进模板**。模板是骨架，不是解题。

```cpp
// g++ -std=c++17 -O2
// ============================================================
// 竞赛代码模板（模块 F-1）
// 用法：比赛开始先粘贴此骨架，再写题目主体
// ============================================================

#include <bits/stdc++.h>      // 注意：GCC 扩展，本机 MinGW g++ 8.1.0 编译失败，见下方【注意】
using namespace std;

// ---- 常量区：全部编译期确定 ----
const int MAXN = 100000 + 10;         // 数组大小：题面上限 + 余量（模块 A-4）
const int MOD  = 1000000007;          // 取模常量
const int INF  = 0x3f3f3f3f;          // 无穷大（模块 A-10）

// ---- 全局数组区：避免在 main 内开大数组 ----
// int a[MAXN];

// ---- 调试开关：本地编译加 -DLOCAL 才输出，提交时不加则全部消失 ----
#ifdef LOCAL
  #define DBG(fmt, ...) fprintf(stderr, "[%s:%d] " fmt "\n", __FILE__, __LINE__, ##__VA_ARGS__)
  #define ASSERT(cond) do { if (!(cond)) { fprintf(stderr, "断言失败：%s（第 %d 行）\n", #cond, __LINE__); exit(1); } } while (0)
#else
  #define DBG(fmt, ...)      // 展开为空，零开销
  #define ASSERT(cond)       // 提交版本不做断言，避免无谓开销
#endif

int main() {
    // ---- 输入输出性能开关：模块 B 的核心结论，必须写 ----
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    int n;
    if (!(cin >> n)) return 0;        // 边界：读入失败直接结束（多组数据时安全）

    DBG("n = %d", n);                  // 本地可见，提交时消失
    ASSERT(n > 0);                     // 违反假设立即报错，而不是带着错误继续算

    // ---- 题目主体写在这里 ----

    return 0;
}
```

> **【注意】** 关于 `#include <bits/stdc++.h>`：
> 它是 **GCC 扩展**，Linux 上的 OJ（绝大多数）支持，
> 但**本机 MinGW-W64 g++ 8.1.0 编译失败**（会拉入 `filesystem` 头，报数十条 `std::filesystem::path` 错误）。
>
> | 环境 | `bits/stdc++.h` |
> |------|----------------|
> | Linux + GCC（多数 OJ） | 可用，推荐（省去逐个 include） |
> | Windows + MinGW g++ 8.1.0 | **不可用**，改用显式头文件 |
> | MSVC | 不可用 |
>
> **两条路应对**：
> 1. **本地用显式头文件，提交时换成 `bits/stdc++.h`**（需每次记得改，不推荐）。
> 2. **本地与提交都用显式头文件**（推荐，一致性更好）。见下方显式版本。

显式头文件版本（本地与提交通用）：


> **【易错】** 四处：
> 1. **模板太长** —— 超过 30 行后，比赛时不会再逐行确认，反而可能带着错误模板开始。
> 2. **忘记关闭同步** —— 这是模块 B 统计出的头号缺口（全库仅 1 次）。
> 3. **模板里放了 `freopen` 却没注释** —— 提交后读写失败，直接 RE 或 WA。
> 4. **模板里固定了 `MAXN`，但不适用于当前题** —— 每题都要按题面上限调整，
>    不可盲目沿用（这是「开小」类 RE 的常见来源）。

> **【类比】** 比赛模板像**工具箱**：上场前把常用工具按固定位置摆好，
> 用的时候不用找。工具箱里不该有正在修的那台机器的零件（那是题目主体）。

> **【记忆】** **模板只放三样：开关、常量、调试宏。** 不放算法。

### F-2　调试技巧　`P0`　熟练　`[未学]`

> **【重点】** 三条纪律：
> **能用断言就用断言；调试输出必须可一键关闭；永远不要靠「改代码试一下」来定位。**

**是什么**：在代码中加入自我检查与中间输出，快速定位错误位置。

**为什么**：竞赛的调试成本极高 —— 看不到测试数据、拿不到出错用例、时间有限。
**唯一可行的手段就是让自己的程序主动报告状态。**

**怎么用**：

1. **断言（`assert` / 自定义 `ASSERT`）**：检查「本应成立的前提」。违反时立即终止并打印位置。
2. **调试输出（`DBG`）**：用条件编译宏，本地开、提交关（模块 A-11）。
3. **输出到 `stderr`**：不与标准输出混淆，便于在终端区分。
4. **二分调试法**：在程序中间输出中间结果，判断错误发生在它之前还是之后。

```cpp
// g++ -std=c++17 -O2 -DLOCAL
#include <cstdio>
#include <vector>
#include <algorithm>
using namespace std;

#ifdef LOCAL
  #define DBG(fmt, ...) fprintf(stderr, "[%s:%d] " fmt "\n", __FILE__, __LINE__, ##__VA_ARGS__)
  #define ASSERT(cond) do { if (!(cond)) { \
        fprintf(stderr, "断言失败：%s（%s:%d）\n", #cond, __FILE__, __LINE__); exit(1); } } while (0)
#else
  #define DBG(fmt, ...)
  #define ASSERT(cond)
#endif

int main() {
    int n = 5;
    vector<int> a = {3, 1, 4, 1, 5};

    // 1. 断言检查前提：数组大小与访问下标的关系
    ASSERT((int)a.size() == n);                  // 前提：a 的长度就是 n
    ASSERT(n > 0);                               // 前提：n 为正

    // 2. 二分调试法：在关键位置输出中间状态
    DBG("输入数组：");
    for (int i = 0; i < n; i++) fprintf(stderr, "%d ", a[i]);
    fprintf(stderr, "\n");

    long long sum = 0;
    for (int i = 0; i < n; i++) {
        sum += a[i];
        DBG("i=%d a[i]=%d 累计和=%lld", i, a[i], sum);   // 每步可见
    }
    ASSERT(sum == 14);                           // 断言最终结果（已知答案时）

    // 3. 断言用于检查「不该发生的状态」
    vector<int> b = {5, 4, 3, 2, 1};
    sort(b.begin(), b.end());
    for (int i = 1; i < (int)b.size(); i++) {
        // 排序后必须非递减 —— 如果这里失败，说明排序或比较器有问题
        ASSERT(b[i - 1] <= b[i]);
    }
    DBG("排序检查通过");

    // 4. 边界断言：数组越界的「事前」检查
    int idx = 3;
    ASSERT(0 <= idx && idx < (int)a.size());     // 访问前先断言
    DBG("a[%d] = %d", idx, a[idx]);

    // 5. 常用技巧：把「期望值」与「实际值」一起打印
    int expected = 14, actual = (int)sum;
    if (expected != actual)
        DBG("不一致！期望 %d，实际 %d", expected, actual);

    printf("sum = %lld\n", sum);                 // 只有标准输出会进入评测
    return 0;
}
```

> **【规律】** **`stderr` 是调试输出的正确去处。**
> 若用 `printf` 调试，一旦忘记删除，多余输出会直接导致 WA。
> 写到 `stderr` 的输出**不会进入评测结果**，安全得多（但仍建议用 `DBG` 配合条件编译）。

> **【易错】** 五处：
> 1. **提交版本里保留 `assert`** —— 某些 OJ 的 `assert` 有开销，且断言失败会 RE。
>    **模板里已把 `ASSERT` 在非 `LOCAL` 下定义为空。**
> 2. **用 `printf` 调试后忘记删除** —— 多余输出导致 WA。**用 `DBG` 或 `stderr`。**
> 3. **`assert` 里写有副作用的表达式** —— 如 `assert(x++)`。
>    在非 `LOCAL` 版本里被定义为空，副作用就消失了，行为不一致。
> 4. **只打印结果不打印输入** —— 定位时无法复现这一步。
> 5. **对浮点数用 `==` 断言** —— 浮点误差导致假失败。用 `fabs(a-b) < 1e-9`。

> **【类比】** 断言像**电路的保险丝**：正常情况下毫无影响，
> 一旦电流异常就立刻断开，让你知道问题出在这里，而不是几公里外的电机烧了。

> **【记忆】** **`stderr` 输出，`DBG` 控制，断言写前提；提交前不留输出。**

- `[后续]` 见 F-3 对拍（对拍出差异后，靠等价于断言的手段定位）。

### F-3　对拍　`P0`　熟练　`[未学]`

> **【重点】** 对拍是**最有价值的一项自查能力**，现有代码中完全缺失。
> 一句话概括：**用「一定正确但慢」的程序，验证「可能错但快」的程序，在大量小数据上找反例。**

**是什么**：三个程序 + 一个循环脚本。

| 组件 | 作用 | 要求 |
|------|------|------|
| **数据生成器** | 按题目约束随机生成小规模输入 | 覆盖边界（小值、等值、极值） |
| **暴力程序** | 直接按题意写，不优化 | **必须明显正确**，慢不要紧 |
| **待测程序** | 你的解法 | 要验证的对象 |
| **比对脚本** | 循环生成 → 跑两个程序 → 比输出 | 一直跑到出现差异为止 |

**为什么**：这是**唯一能自动化发现反例**的手段。
人想测试用例时，倾向于想到「正常情况」；随机生成器会撞上你没想到的边界。

**关键设计：为什么要用小数据**
1. 暴力程序在小数据上才能跑得快（O(n²) 在 n ≤ 10 时毫无压力）。
2. 小数据更容易人工看懂出了什么问题。
3. **n 小的时候，边界更容易被撞到**（如 n = 1、全部相同、全是负数）。

**怎么用**：

1. 建三个文件：`gen.cpp`（生成器）、`brute.cpp`（暴力）、`mine.cpp`（待测）。
2. 写循环脚本（`bash` 或 `python`）。
3. **先让暴力程序与待测程序在样例上一致**，否则对拍毫无意义。
4. 出现差异后：保存数据 → 人工比对输出 → 定位错误 → 修完再跑。

**数据生成器（需覆盖边界）**

```cpp
// g++ -std=c++17 -O2 -o gen gen.cpp
// 生成器：为「求数组区间和」类题目生成小规模测试数据
#include <bits/stdc++.h>
using namespace std;

int main(int argc, char *argv[]) {
    int seed = atoi(argv[1]);            // 用命令行参数做种子，保证可复现
    srand(seed);

    int n = rand() % 10 + 1;             // 边界：n 从 1 开始（覆盖 n=1）
    int q = rand() % 5  + 1;             // 查询次数

    printf("%d %d\n", n, q);
    for (int i = 0; i < n; i++) {
        // 边界：取值范围包含负数与 0，也包含极值
        int mode = rand() % 3;
        int x;
        if (mode == 0) x = rand() % 3 - 1;            // 小范围，含 -1 0 1
        else if (mode == 1) x = rand() % 100;         // 普通正数
        else x = (rand() % 2 ? 1 : -1) * (rand() % 1000000000);  // 极值
        printf("%d%c", x, i + 1 == n ? '\n' : ' ');
    }
    for (int i = 0; i < q; i++) {
        int l = rand() % n + 1, r = rand() % n + 1;
        if (l > r) swap(l, r);           // 保证区间合法
        printf("%d %d\n", l, r);
    }
    return 0;
}
```

**暴力程序（明显正确，慢无所谓）**

```cpp
// g++ -std=c++17 -O2 -o brute brute.cpp
#include <bits/stdc++.h>
using namespace std;

int main() {
    int n, q;
    scanf("%d %d", &n, &q);
    vector<long long> a(n + 1);
    for (int i = 1; i <= n; i++) scanf("%lld", &a[i]);
    while (q--) {
        int l, r;
        scanf("%d %d", &l, &r);
        long long s = 0;
        for (int i = l; i <= r; i++) s += a[i];   // 暴力累加，O(n) 每次
        printf("%lld\n", s);
    }
    return 0;
}
```

**待测程序（前缀和优化版，要验证的对象）**

```cpp
// g++ -std=c++17 -O2 -o mine mine.cpp
#include <bits/stdc++.h>
using namespace std;

const int MAXN = 100000 + 10;
long long pre[MAXN];

int main() {
    int n, q;
    scanf("%d %d", &n, &q);
    for (int i = 1; i <= n; i++) {
        long long x; scanf("%lld", &x);
        pre[i] = pre[i - 1] + x;         // 前缀和
    }
    while (q--) {
        int l, r;
        scanf("%d %d", &l, &r);
        printf("%lld\n", pre[r] - pre[l - 1]);   // 边界：l-1 可能为 0
    }
    return 0;
}
```

**比对脚本（bash 版，无需额外依赖）**

```bash
#!/bin/bash
# compare.sh —— 对拍脚本
# 用法：bash compare.sh
# 前置：gen / brute / mine 三个可执行文件已编译好

for ((i = 1; i <= 1000; i++)); do
    # 1. 用递增的种子生成数据，保证每次运行可复现
    ./gen $i > data.in

    # 2. 分别运行暴力与待测程序
    ./brute < data.in > brute.out
    ./mine  < data.in > mine.out

    # 3. 比对输出
    if ! diff -q brute.out mine.out > /dev/null; then
        echo "===== 发现差异，种子 i = $i ====="
        echo "----- 输入数据 -----"
        cat data.in
        echo "----- 暴力输出 -----"
        cat brute.out
        echo "----- 待测输出 -----"
        cat mine.out
        exit 0
    fi

    # 4. 每 100 轮报一次进度
    if ((i % 100 == 0)); then echo "已测试 $i 组，暂未发现差异"; fi
done

echo "1000 组测试全部一致"
```

**比对脚本（Python 版，可自定义比对规则）**

```python
# compare.py —— 对拍脚本（Python 版）
# 用法：python compare.py
import subprocess, sys

for i in range(1, 1001):
    data = subprocess.run(["./gen", str(i)], capture_output=True).stdout
    r1 = subprocess.run(["./brute"], input=data, capture_output=True).stdout
    r2 = subprocess.run(["./mine"],  input=data, capture_output=True).stdout

    # 比对：逐字符严格比较（适合整数输出）
    if r1 != r2:
        print(f"===== 发现差异，种子 i = {i} =====")
        print("----- 输入数据 -----"); print(data.decode())
        print("----- 暴力输出 -----"); print(r1.decode())
        print("----- 待测输出 -----"); print(r2.decode())
        sys.exit(0)

    if i % 100 == 0:
        print(f"已测试 {i} 组，暂未发现差异")

print("1000 组测试全部一致")
```

> **【易错】** 六处：
> 1. **暴力程序本身错了** —— 对拍结果毫无意义。**先确认暴力在样例上正确。**
> 2. **数据生成器不覆盖边界** —— 只生成「普通情况」，那对拍只能证明普通情况正确。
>    必须包含 n = 1、全相同、负数、极值。
> 3. **种子不可复现** —— 用 `rand()` 但不固定种子，出现差异后无法重新生成同一组数据。
>    **必须把种子作为参数传入并打印出来。**
> 4. **数据规模太大** —— 暴力程序跑不动。**小数据（n ≤ 10）才是对拍的正确规模。**
> 5. **只比对输出而不保留输入** —— 出现差异后无法复现。**脚本必须同时打印输入。**
> 6. **比较浮点输出时用严格相等** —— 应改为「误差小于 1e-6 视为相同」。

> **【类比】** 对拍像**请两个人分别算同一道题**：一个人用笨办法慢慢算（暴力），
> 一个人用巧办法快速算（你的程序）。**只要有一个例子两人答案不同，就说明巧办法有问题。**

> **【记忆】** **小数据、固定种子、留输入、先验暴力。** 四条缺一不可。

**关联**

- `[前置]` 见 F-2 调试技巧（出差异后靠它定位）、D-8 全排列枚举（小规模暴力的常用手段）。
- `[后续]` 见 F-4 排查顺序（与对拍配合使用）。
- `[组合]` 与 F-1 模板组合 → 暴力程序也套用同一个模板，减少无关变量。
- `[延伸]` 对拍脚本的完整说明见 `70_速查手册\71_算法解题技巧与注意事项总结.md` 第六节。

### F-4　RE / TLE / MLE 的排查顺序　`P0`　熟练　`[未学]`

> **【重点】** 三类失败的**排查顺序是固定的** ——
> 按「成本从低到高」逐项排除，不要凭直觉乱改。

**是什么**：按固定清单逐项排查，而非随机猜测。

**为什么**：竞赛中最浪费时间的不是「不会做」，而是**在错误方向上反复试**。
固定顺序能把「随机猜测」变成「系统排查」，通常能在几分钟内定位。

### 4.1 RE（运行错误）排查顺序

| 序 | 检查项 | 具体动作 | 依据 |
|----|--------|---------|------|
| 1 | **数组开小** | 按题面上限核对每个数组大小，是否加了余量 | A-4 |
| 2 | **数组开在函数内** | 大数组是否在 `main` 里（栈溢出） | A-4、A-10 |
| 3 | **递归爆栈** | 估算递归深度；线性递归是否超过 10⁵ | A-8 |
| 4 | **除零 / 取模零** | 分母是否可能为 0 | — |
| 5 | **容器空时访问** | `top` / `front` / `back` 之前是否判空 | C-4 |
| 6 | **迭代器失效** | 遍历中是否删/插元素；`vector` 扩容后是否还用旧迭代器 | C-1 |
| 7 | **`memset` 用错** | 是否填了 0/-1/`0x3f` 以外的值 | D-5 |
| 8 | **未定义行为** | 对有符号数移位、对 0 用 `clz`/`ctz`、`npos` 与 `-1` 比较 | A-5、C-2、D-10 |

> **【规律】** RE 的排查顺序 = **「内存类 → 边界类 → 未定义行为类」**。
> 前四项覆盖约 80% 的 RE。

### 4.2 TLE（超时）排查顺序

| 序 | 检查项 | 具体动作 | 依据 |
|----|--------|---------|------|
| 1 | **复杂度是否达标** | 用数据规模推定表核对（见手册第三节） | 手册 |
| 2 | **输入输出是否关同步** | `ios::sync_with_stdio(false); cin.tie(nullptr);` | B-2 |
| 3 | **是否在循环里用 `endl`** | 改成 `"\n"` | B-3 |
| 4 | **是否在循环里做 O(n) 操作** | 如循环内 `size()` 导致拷贝、循环内 `sort` | — |
| 5 | **是否传值传入大容器** | 改 `const &` | A-6 |
| 6 | **容器选错** | 线性查找改关联容器；`std::lower_bound` 用在 `set` 上 | C-10、C-7 |
| 7 | **是否可加剪枝 / 记忆化** | 搜索与 DP 的常规优化 | 手册 |
| 8 | **是否卡常** | 只有以上都排除后才考虑（F-6） | F-6 |

> **【重点】** **先降复杂度，再压常数。** 顺序反过来是无效劳动 ——
> 把 O(n²) 的常数优化 10 倍，仍然过不了 n = 10⁵。

### 4.3 MLE（超内存）排查顺序

| 序 | 检查项 | 具体动作 | 依据 |
|----|--------|---------|------|
| 1 | **数组是否开得过大** | 计算总字节数：元素数 × 元素大小 | A-4 |
| 2 | **是否重复开了多份** | 多个同规模的大数组叠加 | A-4 |
| 3 | **是否用了 `vector<vector<int>>`** | 每个内层 `vector` 有额外开销；改一维数组模拟 | C-1 |
| 4 | **是否可换更小的类型** | 值域允许时用 `int` 而非 `long long`，用 `short` | A-1 |
| 5 | **是否可用 `bitset`** | 布尔标记从 1 字节压到 1 位 | C-9 |
| 6 | **递归深度是否过大** | 每层函数栈都要占内存 | A-8 |

### 4.4 快速估算内存

```text
内存 = 元素个数 × 单个元素字节数

int       4 字节
long long 8 字节
double    8 字节
bool      1 字节（注意：不是 1 位）
指针      8 字节（64 位系统）
```

| 数组声明 | 内存 |
|---------|------|
| `int a[1000005]` | 1×10⁶ × 4 = 约 4 MB |
| `long long a[1000005]` | 约 8 MB |
| `int g[1005][1005]` | 1005² × 4 ≈ 4 MB |
| `int g[5005][5005]` | 5005² × 4 ≈ 100 MB ← **危险** |
| `long long g[5005][5005]` | ≈ 200 MB ← **必然 MLE** |

> **【易错】** 五处：
> 1. **不区分「复杂度超了」与「常数大了」** —— 前者要换算法，后者才谈卡常。
>    混淆这两者会浪费大量时间。
> 2. **RE 时先怀疑算法** —— RE 几乎总是实现问题（数组、栈、空容器），不是算法问题。
> 3. **TLE 时先优化常数** —— 见上，顺序错了。
> 4. **忘记 `bool` 是 1 字节** —— 10⁷ 个 `bool` 是 10 MB，而 `bitset` 只要 1.25 MB。
> 5. **以为 `vector` 元素不占额外开销** —— 每个 `vector` 对象本身有 3 个指针的固定开销；
>    10⁵ 个内层 `vector` 就多出约 2.4 MB。

> **【类比】** 排查像**医生的分诊**：先按最可能、最容易查的顺序做检查，
> 而不是一上来做全身 CT。**成本低的先排除**，能解决绝大多数问题。

> **【记忆】** **RE 查内存与边界，TLE 先看复杂度后看常数，MLE 算字节数。**

**关联**

- `[前置]` 见 A-4 数组、A-8 递归、F-2 调试、F-3 对拍。
- `[后续]` 见 F-6 卡常（只有本节的 1 至 7 项都排除后才轮到它）。
- `[组合]` 与 F-5 编译选项组合 → `-Wall` 能在编译期就暴露一部分 RE 隐患。
- `[延伸]` 数据规模与可用复杂度的推定表见 `70_速查手册\71_算法解题技巧与注意事项总结.md` 第三节。

### F-5　编译选项　`P1`　会用　`[未学]`

> **【重点】** `-Wall` **能让编译器替你做一部分调试**。开启它，等于免费获得一个代码审查员。

**是什么**：传给编译器的参数，控制标准版本、优化级别、警告级别。

| 选项 | 作用 | 竞赛中的必要性 |
|------|------|--------------|
| `-std=c++17` | 使用 C++17 标准 | **必要**（结构化绑定、`if` 初始化语句依赖它） |
| `-O2` | 开启二级优化 | **必要**（OJ 默认开，本地也应开，否则测不出真实速度） |
| `-Wall` | 开启常用警告 | **强烈建议**（能提前发现未初始化变量、类型不匹配） |
| `-Wextra` | 更多警告 | 可选（警告偏多） |
| `-g` | 生成调试信息 | 可选（用 gdb 时） |
| `-fsanitize=address,undefined` | 运行时检查越界与 UB | **本地调试神器**（但慢数倍，不能用于计时） |
| `-DLOCAL` | 定义 `LOCAL` 宏 | 本地调试开关（模块 A-11、F-2） |

**为什么**：OJ 的编译参数通常固定（`-O2`、`-std=c++17`）。**本地用相同参数编译，
才能保证本地通过的程序在 OJ 上也通过。** 这是「本地过了提交却 RE」的常见原因之一。

**怎么用**：

```bash
# 本地常规开发：与 OJ 一致，并开启警告
g++ -std=c++17 -O2 -Wall -o main main.cpp

# 本地调试：开启断言与调试输出，并启用运行时检查
g++ -std=c++17 -O0 -g -Wall -DLOCAL -fsanitize=address,undefined -o main main.cpp

# 计时用（关掉 sanitize，否则时间不准）
g++ -std=c++17 -O2 -o main main.cpp
```

> **【重点】** **`-fsanitize=address,undefined` 是本地定位 RE 的最强工具** ——
> 它能在越界、使用未初始化变量、有符号溢出时**精确报出行号**。
> 代价是运行速度慢数倍且内存占用增加，**所以只能用于正确性验证，不能用于测速。**

```bash
# 示例：一段有数组越界的代码，用 sanitize 能精确定位
cat > demo.cpp << 'EOF'
#include <cstdio>
int main() {
    int a[5] = {1, 2, 3, 4, 5};
    int i = 5;
    printf("%d\n", a[i]);    // 越界读
    return 0;
}
EOF

g++ -std=c++17 -g -fsanitize=address -o demo demo.cpp
./demo    # 会报出具体的越界位置与行号
```

> **【易错】** 五处：
> 1. **本地不加 `-O2`** —— 本地比 OJ 慢，误判为 TLE 而过度优化；或本地没暴露的问题在 OJ 上因优化而表现不同。
> 2. **本地不加 `-std=c++17`** —— 结构化绑定、`if` 初始化语句编译失败（模块 E-4、E-5）。
> 3. **用 `-fsanitize` 版本测速** —— 慢数倍，时间无意义。
> 4. **忽略 `-Wall` 的警告** —— 未初始化变量、有符号与无符号比较这两类警告往往就是 bug 本身。
> 5. **提交时带着 `-DLOCAL`** —— 调试输出会污染结果。**但 OJ 不会执行你本地的编译命令，
>    所以这个风险只在「用脚本自动提交」时存在。**

> **【类比】** `-Wall` 像**一位会插话的同事**：他说的不一定都是问题，
> 但**你不看就会漏掉真正的那个**。而 `-fsanitize` 像**红外热成像**——
> 直接照出你肉眼看不出问题的地方。

> **【记忆】** **本地编译就用 `-std=c++17 -O2 -Wall`；查 RE 加 `-fsanitize`。**

**关联**

- `[前置]` 见 A-11 宏与条件编译（`-DLOCAL`）、F-1 模板。
- `[后续]` 见 F-6 卡常（优化级别的实际影响）。
- `[组合]` 与 F-4 组合 → `-fsanitize` 是排查 RE 的第一利器。
- `[延伸]` 各 OJ 的默认编译参数可能不同（有的默认 `-O0`），
  比赛前应查清 **「是否默认开 `-O2`」**，这直接影响是否需要卡常。

### F-6　卡常技巧　`P2`　会用　`[未学]`

> **【重点】** **只在「算法复杂度已达标、但常数过大」时才用。**
> 这是本模块的最后一个选项，不是第一个。

**什么是卡常**：在不改变复杂度的前提下，减少常数因子（循环次数、内存访问、函数调用开销）。

**为什么排在最后**：因为**收益上限是常数倍**，而换算法的收益是量级倍。
把 O(n²) 优化 10 倍仍是 O(n²)，n = 10⁵ 时依然过不了。

**先用这三问自查**：

```text
1. 复杂度对了吗？      → 不对，换算法（不要卡常）
2. 输入输出关同步了吗？ → 没关，先关（收益最大，一次搞定）
3. 循环里有没有可省的？ → 有，先砍掉
以上都做完了还 TLE，才考虑下面的技巧。
```

| 技巧 | 做法 | 典型收益 | 注意事项 |
|------|------|---------|---------|
| **位运算替代** | 乘除 2 的幂改 `<<` / `>>`；取模 2 的幂改 `&` | 小 | 现代编译器多数已自动优化 |
| **减少函数调用** | 把热点小函数改 `inline` 或直接展开 | 中 | `-O2` 多数已自动内联 |
| **减少分支** | 循环内避免 `if`，或改为条件移动 | 小 | 可读性下降 |
| **内存局部性** | 二维数组按行访问（与内存布局一致） | **大** | 差距可达数倍 |
| **`register` / 手写展开** | 已过时 | 极小 | **不推荐** |
| **改用更快的容器** | `map` → `unordered_map` | **大** | 注意可能被卡哈希 |
| **提前终止** | 加剪枝、`break` 条件 | **大** | 属算法优化，优先做 |
| **减少取模** | 累积到可能溢出前才取模 | 中 | 注意别真溢出 |

**最值得做的一项：内存访问顺序**。以二维数组为例：

```cpp
// g++ -std=c++17 -O2
#include <cstdio>
#include <ctime>
using namespace std;

const int N = 4000;
int a[N][N];

int main() {
    // 1. 按行访问：与内存布局一致（C++ 行优先），缓存命中率高
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++)
            a[i][j] = 1;                      // 内层遍历 j，内存连续

    // 2. 按列访问：内存跳跃，缓存命中率低
    clock_t t1 = clock();
    long long s1 = 0;
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++)
            s1 += a[i][j];                    // 好
    clock_t t2 = clock();

    long long s2 = 0;
    for (int j = 0; j < N; j++)
        for (int i = 0; i < N; i++)
            s2 += a[i][j];                    // 坏：每次跨 4000 个 int
    clock_t t3 = clock();

    printf("按行 %.0f ms，按列 %.0f ms，比值 %.1f\n",
           1000.0 * (t2 - t1) / CLOCKS_PER_SEC,
           1000.0 * (t3 - t2) / CLOCKS_PER_SEC,
           (double)(t3 - t2) / (t2 - t1));
    printf("（绝对时间与机器相关，但按行应明显快于按列）\n");
    return 0;
}
```

复杂度对比总结：

| 手段 | 收益类型 | 优先级 |
|------|---------|-------|
| 换算法（降复杂度） | **量级** | 最高 |
| 输入输出关同步 | 数倍 | 高（一次解决，见模块 B） |
| 提前终止 / 剪枝 | 量级（视数据） | 高 |
| 换更快的容器 | 数倍 | 中 |
| 内存局部性 | 数倍 | 中 |
| 位运算 / `inline` | 常数 | 低 |

> **【易错】** 五处：
> 1. **跳过「复杂度是否正确」直接卡常** —— 最常见的时间浪费。
> 2. **卡常改动引入 bug** —— 位运算替代时忘了括号（模块 A-2）、提前终止漏掉合法解。
> 3. **误以为 `register` 有用** —— 现代编译器已忽略它。
> 4. **在没测过时间的情况下优化** —— 先测量再优化。用 `clock()` 或本地计时。
> 5. **为了卡常牺牲可读性，结果提交 WA** —— **卡常的前提是正确性已经确认**（F-3 对拍过）。

> **【类比】** 卡常像**给汽车减重**：能提速，但**前提是发动机（算法）已经够强**。
> 一辆发动机只有 50 马力的车，拆掉座椅也不会变快多少。

> **【记忆】** **先降复杂度，再压常数；卡常之前必须先对拍确认正确性。**

**关联**

- `[前置]` 见 F-4 排查顺序（卡常是最后一步）、F-5 编译选项（`-O2` 的实际影响）。
- `[组合]` 与 B-2、B-3 组合 → 输入输出的性能优化是收益最高的一项卡常。
- `[易混]` 卡常与算法优化：前者改常数，后者改复杂度。**必须是后者优先。**
- `[延伸]` 常见常数的实测数据见 `02_竞赛\02_竞赛C++\B_输入输出与性能.md` 第四节，
  以及 `50_工具与模板\54_性能实测源码\` 的可复现源码。

## 五、本章总结

### 5.1 核心内容（一页纸）

1. **模板只放三样：I/O 开关、常量、调试宏。** 不超过 30 行。
2. **`#include <bits/stdc++.h>` 是 GCC 扩展**，多数 OJ 可用，但本机 MinGW g++ 8.1.0 编译失败。
3. **调试输出写 `stderr`**，且必须能用条件编译一键关闭。
4. **断言用于检查「本应成立的前提」**；提交版本里 `ASSERT` 定义为空。
5. **对拍四要件**：小数据、固定种子、保留输入、先验暴力程序。
6. **数据生成器必须覆盖边界**：n = 1、全相同、负数、极值。
7. **RE 排查顺序**：数组开小 → 局部大数组 → 递归爆栈 → 除零 → 容器空访问 → 迭代器失效 → `memset` 误用 → 未定义行为。
8. **TLE 排查顺序**：复杂度 → 关同步 → `endl` → 循环内 O(n) → 传值拷贝 → 容器选错 → 剪枝 → 卡常。
9. **MLE 先算字节数**：`int` 4 字节、`long long` 8、`bool` 1 字节（不是 1 位）。
10. **先降复杂度，再压常数。** 顺序反了就是无效劳动。
11. **本地编译就用 `-std=c++17 -O2 -Wall`**；查 RE 加 `-fsanitize=address,undefined`。
12. **内存局部性收益最大**：二维数组按行访问，差距可达数倍。
13. **卡常的最后一道门槛是正确性**：先对拍通过，再卡常。
