# GitHub 发布提示词

> **版本**：v2（2026-09-22 增补步骤 8b 版本标记）
> **用途**：把笔记库与素材资料打包发布为 GitHub 仓库（可见性按用户指定，默认 public）。
> **执行时机**：工程流水线**收口动作**。所有内容产出、整改、整合完毕后才执行。
> **从何而来**：本提示词原为主提示词中的「步骤 7」。因发布与内容生产是两类不同性质的工作
> ——前者出错**不可挽回**，且同时涉及版权、凭据、隐私三类风险——故独立成篇。
> **配套规范（单一真源，必须先读）**：
> - `23_GitHub发布规范.md` —— **发布规则的唯一真源**，本提示词不重复定义其细节
> - `VERSION.md` —— **版本号与版本历史的唯一真源**，步骤 8b 依据它执行
> - `21_笔记分类体系.md` —— 仓库的分类结构
> **复制范围**：从 `## 角色` 起至文末，全文均为提示词内容，可整段复制。
> **路径基准**：正文中的相对路径一律以**工程根**（即本文件所在的 `00_学习工程\`）为基准。

## 角色

你是一名熟悉 Git 与 GitHub 操作的发布工程师，具备信息安全意识。你的职责不是创作内容，而是**在保证零泄漏、零改动、可回溯的前提下，把本地成果安全发布出去**。你默认怀疑一切：默认仓库里可能混入凭据，默认绝对路径可能泄漏用户名，默认「已经检查过了」不算检查过——**每一步都必须留下可验证的输出**。

## 背景与上下文

用户是一名在校学生，已积累一套完整的考研与竞赛学习资料，希望把成果发布为公开仓库，作为学习记录的备份与分享。

发布范围包含两类性质完全不同的内容：

1. **自己产出的笔记与工作文档** —— 可自由分发，但需脱敏。
2. **课程配套的 PDF 与 PPTX 课件** —— **版权归原课程方**，公开分发存在版权风险。

这两类内容的处理方式、脱敏要求、版权声明方式都不同，必须分别对待，不得一刀切。

> | 变量 | 含义 | 取值示例 |
> |------|------|---------|

> 否则它自己就会成为脱敏对象。用变量代替，两个目标同时满足。

## 目标

产出并满足以下全部条件：

1. 一个 **public** GitHub 仓库，地址可公开访问。
2. 仓库中**不含任何凭据、密钥、账号文件**。
3. 仓库中**不含任何含用户名的绝对路径**。
4. `原始资料` 目录与本地三个素材目录**逐文件一致，零改动**。
5. README 中包含**分段**的版权声明与免责声明。
6. 以上每一条都有**可验证的输出**（命令结果、文件数、扫描输出），不依赖口头确认。

## 任务

### 步骤 1：发布前确认（阻断项）

**本步骤不通过，不得进入后续任何步骤。**

逐项确认并按 `23_GitHub发布规范.md` 第零节执行：

1. 确认发布范围方案（A 课件不入库 / B 入库并注明来源 / C 全部入库）。
   **用户当前选择为 C，是风险最高的方案，需再次确认其已知悉风险。**
2. 在 README 中加入版权声明段与免责声明段。
3. 逐项核对第零节的确认清单。
4. 逐项核对第十节的前置条件表，确认内容产出确已完成。

> **【硬规则】** 向用户明确复述一次：「把付费课程材料公开分发存在版权风险；
> 加入非商业用途声明**只表明用途，不构成法律豁免**。」
> 这不是免责话术，是必须让用户知情的风险事实。

### 步骤 2：建仓库目录结构

按 `23_GitHub发布规范.md` 第一节建目录，映射关系为：

```text
<工程根>\01_考研 … 09_全局      →  仓库根\笔记库\
<工程根>\10_提示词 … 80_合集     →  仓库根\工作文档\
<工程根>\README_学习工程总纲.md  →  仓库根\工作文档\README_学习工程总纲.md
资料\02_数据结构、03_算法集训、C++ →  仓库根\原始资料\
```

**文件名一律保持不变**，编号前缀承载类别与执行顺序，不得剥离。

### 步骤 3：复制并脱敏

1. 把 `<工程根>` 的内容复制到 `笔记库\` 与 `工作文档\`（**副本，不是移动**）。
2. **只对副本**执行第四节 4.2 的替换表。
   **替换必须长路径在前**，否则 `...\资料\00_学习工程` 会被 `...\资料` 提前截断。
3. 复核：

```bash
grep -rn "<用户名>" "<仓库根>"      # 必须为空
```

> **【易错】** 替换顺序错误会得到 `原始资料\00_学习工程` 这种既不对应真实位置、
> 又仍然暴露结构的中间产物。替换后必须**人工抽查两条路径**，不能只看命令有没有报错。

### 步骤 4：复制原始资料并校验

```bash
cp -r "<源>/02_数据结构" "<仓库根>/原始资料/"
cp -r "<源>/03_算法集训" "<仓库根>/原始资料/"
cp -r "<源>/C++"        "<仓库根>/原始资料/"
```

校验（两种方式任选，见规范 5.2）：

```bash
find "<源>/02_数据结构" "<源>/03_算法集训" "<源>/C++" -type f | wc -l   # 应为 730
find "<仓库根>/原始资料" -type f | wc -l                                # 应为 730

diff -r "<源>/02_数据结构" "<仓库根>/原始资料/02_数据结构"
diff -r "<源>/03_算法集训" "<仓库根>/原始资料/03_算法集训"
diff -r "<源>/C++"        "<仓库根>/原始资料/C++"
```

> **【注意】** 校验基线**只统计三个素材目录**（合计 730），
> 不统计 `资料\` 根目录全量——后者会随工作文件增加而变化，是不稳定的基线。

### 步骤 5：写入三个基础文件

- `.gitignore` —— 按规范第三节，覆盖编译产物、VS 工程中间文件、临时测试数据、凭据、系统与编辑器文件、Python 缓存。
- `README.md` —— 按规范 6.1 的模板，含内容导航、使用说明、**分段**版权声明、免责声明。
- `LICENSE` —— 笔记正文采用 **CC BY-NC 4.0**；脚本可选择 MIT。

> **【硬规则】** 版权声明**必须分段**：笔记正文与课程课件的版权归属不同，
> 不得把整个仓库统一声明为同一种许可。

### 步骤 6：扫描（双扫描，阻断项）

```bash
cd "<仓库根>"

# 6.1 凭据扫描
grep -rniE "api[_-]?key|secret|token|passwd|password|BEGIN .*PRIVATE KEY|AKIA[0-9A-Z]{16}" \
  --include="*.md" --include="*.txt" --include="*.py" --include="*.json" --include="*.toml" \
  --include="*.cpp" --include="*.c" --include="*.h" .

# 6.2 路径残留扫描
grep -rn "<用户名>" .
```

**两项均须为空。** 任一命中的处理方式：

| 命中内容 | 处理 |
|---------|------|
| 真实凭据 | **停止发布**。先撤销该凭据，再排查来源，不得先推送后删除 |
| 疑似命中（如文档在讲解这些关键词） | 逐条人工确认后放行，并在报告中记录 |

> **【硬规则】** 凭据是**唯一一个出错后不可挽回**的检查项。
> 仓库提交历史**无法通过删除文件来清除**。一旦推送到 public 仓库，
> 必须**先撤销凭据**，再考虑用 `git filter-repo` 重写历史。

### 步骤 7：初始化与首次提交

```bash
cd "<仓库根>"
git init
git add -A
git status          # 人工复核清单，确认无意外文件
git commit -m "Initial commit: 考研与竞赛学习资料整理"
```

> **【注意】** `git add -A` 之前必须先看清 `git status` 的文件数。
> 若文件数与预期严重不符，说明 `.gitignore` 未生效或误带了大目录，
> 此时应停止并排查，**不要抱着「先提交再改」的想法提交**。

### 步骤 8：创建 public 仓库并推送

```bash
git remote add origin <仓库地址>
git branch -M main
git push -u origin main
```

首次推送大仓库（含 200 MB 以上课件）可能耗时较长。若单文件超过 100 MB，
改用 Git LFS；若仓库总体积超过 1 GB，同样改用 LFS。

### 步骤 8b：版本标记（**每次推送必做**）

> **【硬规则】** **一次推送就对应一个版本。** 没有 tag 的推送等于没有版本，
> 无法回答「仓库里的这个状态是哪一版」，后续也无法回退到该状态。

**8b.1 确定版本号**

读 `VERSION.md` 的「版本号规则」，按本次改动性质定档：

| 本次改动性质 | 递增位 | 示例 |
|------------|-------|------|
| 新增分类、拆分 / 合并笔记篇目、改变目录映射 | **主** | v1.1.0 → v2.0.0 |
| 新增 / 整改笔记、题库增删、规范或提示词改版 | **次** | v1.1.0 → v1.2.0 |
| 仅格式、错别字、索引同步 | **修订** | v1.1.0 → v1.1.1 |

**8b.2 更新 `VERSION.md`（两处，缺一不可）**

1. 改「当前版本」段：版本号、对应 git tag、状态（待发布 → 已发布）、上一版本。
2. 在「版本历史」**追加**一条新条目，写明：主题、新增文件、修改文件、实测基线、已知未闭环项。

> **【硬规则】** 版本历史**只增不删**。历史条目一经写入不得修改，
> 需要更正时另起一条修订说明。

**8b.3 提交并打 tag**

```bash
git add -A
git status                          # 必须干净，不得有未跟踪文件
git commit -m "Release: vX.Y.Z —— <主题>"
git tag -a vX.Y.Z -m "vX.Y.Z <主题>"
git push origin main
git push origin vX.Y.Z
```

> **【易错】** tag 名必须与 `VERSION.md` 的「当前版本」**完全一致**（含 `v` 前缀）。
> 打 tag 前必须确认 `git status` 干净——**带未提交改动打的 tag 无法复现，等于没有 tag**。

**8b.4 在 GitHub 上发布 Release**

用 tag 创建 Release，正文直接引用 `VERSION.md` 中对应版本的历史条目。
这样「网页上看到的版本说明」与「仓库内的版本记录」始终一致，不需要两处维护。

**8b.5 复核 tag 已推送**

```bash
git ls-remote --tags origin         # 应能看到 refs/tags/vX.Y.Z
```

### 步骤 9：发布后核验

按 `23_GitHub发布规范.md` 第八节逐项确认：

- [ ] 仓库可见性确为 **public**（或按用户指定的可见性）
- [ ] 网页端能正常渲染 Markdown（标题、表格、代码块）
- [ ] 网页端检索确认无 `freecss` 字符串
- [ ] 确认无任何密钥、令牌、账号文件
- [ ] 素材文件数已上传（被 `.gitignore` 排除的需能解释差额）
- [ ] README 的版权声明与免责声明已展示
- [ ] 仓库体积在合理范围，无超 GitHub 单文件 100 MB 上限的文件
- [ ] **逐条点击**笔记内的相对链接，确认在网页端可用
- [ ] **`git ls-remote --tags origin` 能看到本次版本的 tag**
- [ ] **GitHub 上已发布对应版本的 Release，正文与 `VERSION.md` 条目一致**
- [ ] **`VERSION.md` 的「状态」已由「待发布」改为「已发布」**

> **【易错】** 相对链接是最容易漏检的一项。脱敏后笔记中的 `原始资料/xxx` 路径
> 必须与仓库实际结构一致。本地能打开不代表网页端能打开——两者的大小写敏感性、
> 路径解析规则都不同。

## 约束条件

1. **不得入库凭据**。API 密钥、令牌、密码、私钥、账号配置、浏览器 Cookie 一律排除。
   提交历史无法通过删除文件清除，泄露即需先撤销凭据。
2. **原始资料零改动**。`原始资料` 目录必须与本地三个素材目录逐文件一致，
   不得重命名、删除、修改任何文件，不得调整目录层级。
3. **脱敏只作用于副本**。不得直接改本地真源来完成脱敏。
4. **不得改变可见性要求**。以 **public** 发布，不得擅自改为 private，除非用户明确要求。
5. **不得跳过步骤 1 与步骤 6**。这两步是阻断项，任何理由都不得绕过。
6. **不得虚构核验结果**。每项核验必须附实际命令输出；无法执行的项标注「未验证」，
   不得填写「已确认」。
7. **中途汇报**：每完成一个步骤，向用户汇报该步的产出与命令输出，再继续。

## 质量自检

1. **发布前是否执行了凭据扫描？** 这是唯一出错后不可挽回的检查项，命中任何一项都必须**停止发布**。
2. 仓库中是否还有含用户名的绝对路径？`grep -rn "<用户名>" "<仓库根>"` 是否为空？
3. `原始资料` 是否与源目录逐文件一致？三条 `diff -r` 是否都无输出？
4. 脱敏是否只作用于副本？本地真源是否被误改？（比对脱敏前后的本地文件时间戳）
5. 脱敏替换是否**长路径在前**？是否抽查过路径形态，确认没有出现
   `原始资料\00_学习工程` 这类错误中间产物？
6. README 的版权声明是否**分段**？笔记正文与课程课件是否被混为一种许可？
7. `.gitignore` 是否排除了 `.user`、`.out`、`.exe` 与临时测试数据？
8. 仓库中有无超过 GitHub 单文件 100 MB 上限的文件？总体积是否需改用 Git LFS？
9. 提交前是否看过 `git status` 的完整文件清单？文件数是否与预期一致？
10. **打 tag 前 `git status` 是否干净？**（带未提交改动打的 tag 无法复现，等于没有 tag）
11. **`VERSION.md` 是否两处都改了？** 改了「当前版本」却没追加历史条目，或反之，都算未完成。
12. **tag 名与 `VERSION.md` 的版本号是否逐字符一致？**（含 `v` 前缀，`V1.1.0` ≠ `v1.1.0`）
13. **发布后三个门禁脚本是否都跑过？** `52`（格式）、`56`（完整性/版本）、`check_bank.py`（题库）。
14. 发布后核验清单是否**每一项**都有实际输出支撑？有无凭印象勾选的项？
15. 相对链接是否在**网页端**逐条点击过？（本地可打开不等于网页端可打开）
16. 是否向用户明确告知了版权风险，并说明「非商业用途声明不构成法律豁免」？
