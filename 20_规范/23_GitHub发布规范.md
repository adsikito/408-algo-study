### 4.2 替换规则

| 原文 | 替换为 |
|------|-------|
| `C:\Users\<用户名>\Desktop\资料\00_学习工程` | `<工程根>` |
| `C:\Users\<用户名>\Desktop\资料\<子路径>` | `原始资料/<子路径>` |
| `C:\Users\<用户名>\Desktop\资料` | `原始资料` |
| `C:\Users\<用户名>\Desktop\学习1` | `原始资料`（旧目录名，同上） |
| `C:\Users\<用户名>\WorkBuddy\<会话ID>` | `<工作副本>` |
| `C:\Users\<用户名>\.workbuddy\...` | `<用户配置目录>/...` |

> **【易错】** 替换必须**长路径在前**。
> 若先替换 `...\Desktop\资料`，则 `...\Desktop\资料\00_学习工程` 会被提前截断，
> 得到错误的 `原始资料\00_学习工程`。

> **【要点】** 本表统一使用 `<用户名>` 占位，不写本轮的实际用户名。
> 这样规范本身也能安全对外发布；执行时把 `<用户名>` 换成本机用户名即可。

### 4.3 作用范围的界定

> **【硬规则】** 脱敏**只作用于我们生成的笔记与文档**，
> `原始资料` 目录下的文件**一个字节都不改**。
>
> 理由：用户明确要求「保持原有代码不做任何修改」。
> 原始代码是历史资料，改动会破坏与其他笔记的引用关系，也会让「原始」二字失去意义。

### 4.4 脱敏的执行方式

**不要用批量替换工具直接改原文件**，而是：

1. 按第一节的映射表，把 `<工程根>\`（即 `资料\00_学习工程\`）的内容复制到
   `仓库根\笔记库\` 与 `仓库根\工作文档\`。
2. **只对副本执行替换**。
3. 替换后用脚本复核：`grep -rn "<用户名>" 仓库根` 应为**空**。
4. 本地 `<工程根>\` 保持不动，作为未脱敏的真源副本。

> **【要点】** 这样既完成了脱敏，又满足了「不做任何修改」的要求——
> 修改的是**副本**，真源零改动。

## 五、原始资料零改动原则

> **【硬规则】** `原始资料` 目录必须与 `C:\Users\<用户名>\Desktop\资料` 下的
> 三个素材目录**逐文件一致**。

### 5.1 复制方式

使用能保留元数据的复制命令，逐个素材目录复制：

```bash
# 目录级复制，保留时间戳与属性
cp -r "<源>/02_数据结构" "<仓库根>/原始资料/"
cp -r "<源>/03_算法集训" "<仓库根>/原始资料/"
cp -r "<源>/C++"        "<仓库根>/原始资料/"
```

### 5.2 一致性校验

复制后必须校验，两种方式任选：

```bash
# 方式一：比对文件数。只统计三个素材目录，不统计资料根目录全量
find "<源>/02_数据结构" "<源>/03_算法集训" "<源>/C++" -type f | wc -l   # 应为 730
find "<仓库根>/原始资料" -type f | wc -l                                # 应为 730

# 方式二：逐目录比对（更严格）
diff -r "<源>/02_数据结构" "<仓库根>/原始资料/02_数据结构"
diff -r "<源>/03_算法集训" "<仓库根>/原始资料/03_算法集训"
diff -r "<源>/C++"        "<仓库根>/原始资料/C++"
# 三条命令均应无输出
```

> **【重点】** **校验基线只统计三个素材目录，不统计 `资料\` 根目录全量。**
>
> 这是 2026-09-13 的一处重要修正。早期版本把「资料目录全量文件数」当基线，
> 结果每往该目录写一个工作文件，基线就要改一次（730 变 731、再变 731+N），
> 既脆弱，又容易被误判为「原始资料被改动」。
>
> 现在基线是稳定的：
>
> | 统计对象 | 文件数 | 是否会变 |
> |---------|-------|---------|
> | `02_数据结构\` | 106 | 否 |
> | `03_算法集训\` | 149 | 否 |
> | `C++\` | 475 | 否 |
> | **三目录合计** | **730** | **否** |
> | `00_学习工程\` | 随内容增长 | 是，但**不属于原始资料** |
>
> **判断依据**：`00_学习工程\` 是本任务新建的工作目录，与课程素材性质不同，
> 天然应排除在「原始资料」之外。

### 5.3 禁止的操作

- 不得重命名任何原始文件
- 不得删除任何原始文件（含编译产物、工程文件）
- 不得修改任何原始文件的内容
- 不得调整目录层级

> **【补充】** `.gitignore` 会阻止部分文件入库（如 `.user`、`.out`、`.exe`），
> 但这些文件**仍保留在本地 `原始资料` 目录中**，只是不进入版本库。
> 这是「保持原目录完整」与「不污染仓库」之间的正确平衡点。
> 若用户要求连这些也入库，需单独说明。

## 七之二、版本标记规则

> **【硬规则】** **一次推送对应一个版本。** 没有 tag 的推送等于没有版本，
> 无法回答「仓库里的这个状态是哪一版」，也无法回退。

### 7b.1 版本号真源

版本号与版本历史的**唯一真源**是工程根的 `VERSION.md`。
其他任何地方（README、执行报告、提示词）**不得另行定义版本号**，只能引用。

### 7b.2 版本号规则

采用 `v主.次.修订` 三段式：

| 段 | 递增条件 |
|----|---------|
| **主** | 内容库结构级变更：新增分类、拆分或合并笔记篇目、改变目录映射 |
| **次** | 内容实质变更：新增 / 整改笔记、题库增删、规范或提示词改版 |
| **修订** | 仅格式、错别字、索引同步等不影响内容的修正 |

### 7b.3 发布必做（四件事，缺一不可）

1. **改 `VERSION.md` 的「当前版本」段**：版本号、对应 tag、状态、上一版本。
2. **在 `VERSION.md` 的「版本历史」追加条目**：主题、新增、修改、实测基线、未闭环项。
   历史条目**只增不删**，需要更正时另起一条修订说明。
3. **打 tag 并推送**：`git tag -a vX.Y.Z -m "..."` → `git push origin vX.Y.Z`。
4. **在 GitHub 发布 Release**：正文直接引用 `VERSION.md` 的对应条目，
   避免版本说明两处维护。

### 7b.4 三条硬约束

| 约束 | 说明 |
|------|------|
| **打 tag 前 `git status` 必须干净** | 带未提交改动打的 tag 无法复现，等于没有 tag |
| **tag 名与 `VERSION.md` 逐字符一致** | 含 `v` 前缀；`V1.1.0` 与 `v1.1.0` 是不同的 tag |
| **Release 正文不得与 `VERSION.md` 冲突** | 冲突时以 `VERSION.md` 为准，并回头修正 Release |

### 已知的核验难点

| 难点 | 说明 |
|------|------|
| 大文件 | GitHub 单文件上限 100 MB。需先确认资料中无超限文件 |
| 仓库体积 | 若超过 1 GB 会触发警告，建议用 Git LFS |
| 中文文件名 | GitHub 网页端可正常显示，但克隆到部分系统可能乱码 |
| 相对链接 | 笔记中的 `原始资料/xxx` 链接需与仓库实际结构一致 |

## 九、风险与撤回

| 风险 | 应对 |
|------|------|
| 误传凭据 | **立即撤销该密钥**（改密钥比删仓库更紧急），再删除提交历史 |
| 版权投诉 | 将仓库转为 private 或删除，或按投诉方要求移除对应目录 |
| 仓库过大 | 用 Git LFS 迁移大文件，或改为只发布笔记库 |
| 想反悔 | GitHub 支持仓库转 private 或删除；本地副本始终保留 |

> **【要点】** 提交历史**无法通过删除文件来清除**。
> 一旦凭据被推送到 public 仓库，必须**先撤销凭据**，再考虑用 `git filter-repo` 重写历史。
> 这是发布前扫描必须严格执行的根本原因。
