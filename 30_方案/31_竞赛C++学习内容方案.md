## 零、设计前提：两条实测事实

本方案不是凭经验编排，而是先对现有资料做了实测。结论直接决定了后面的取舍。

### 0.1 现有 C++ 资料的实际定位（与竞赛需求错配）

| 模块 | 规模 | 实际定位 | 与竞赛的关系 |
|------|------|---------|------------|
| `C++基础篇` | 25 讲 | 语言入门，教学向 | **部分相关**。第 23 讲 STL 是唯一直接相关的部分 |
| `C++常用新特性` | 36 个特性 | 工程向（智能指针、移动语义、协程、Modules、filesystem） | **基本无关**。C++20 的协程、Modules，C++17 的 filesystem、optional、variant，竞赛都用不到 |

2. **现代语法糖**完全空白（`auto`、lambda、结构化绑定都是零），意味着代码冗长、易错、写得慢。
3. **输入输出性能意识**薄弱（见下条）。

### 0.3 一个已经存在的具体隐患

`03_算法集训/12_单调栈/例题代码/P5788.cpp` 的题面约束为 **n ≤ 3×10⁶**，但代码写作：

```cpp
#include<iostream>
#include<stack>
using namespace std;
int main()
{
  cin>>n;
  for(int i=1;i<=n;i++) cin>>a[i];   // 循环读入 3×10^6 个数
```

**问题**：既未调用 `ios::sync_with_stdio(false)`，也未使用 `scanf` 或手写快读。
C++ 默认状态下 `cin` 与 C 标准流同步，读入 3×10⁶ 个整数在多数 OJ 上会**超时或接近时限**。

**这不是个例**：竞赛代码（75 个文件）中 `ios::sync_with_stdio` 出现 **0 次**，而 `cin>>` 出现 **112 次**。
**结论三**：输入输出性能是当前最优先要补的知识点，它不增加算法能力，但直接决定已有算法能否通过。

## 一、知识范围与深度

### 1.1 范围划定原则

竞赛 C++ 的范围不等于「C++ 语言」。划定原则是三条：

1. **只学能提升「写对」与「写快」的部分**。竞赛的瓶颈是算法，不是语言；语言知识必须直接服务于编码速度与正确率。
2. **不学无法在赛场上带来收益的部分**。凡是「知道更好但不知道也不影响通过」的，一律划出。
3. **不学导致代码更复杂、更慢的部分**。例如异常处理、智能指针，在竞赛里是纯粹的负担。

### 1.2 六大模块与深度要求

深度分三级，含义如下：

| 深度 | 含义 | 判定标准 |
|------|------|---------|
| **会用** | 能查文档、能默写基本形式 | 不看书能写出正确代码 |
| **熟练** | 条件反射，无需回忆 | 在限时环境中能自动写出 |
| **理解** | 知道原理、复杂度与适用边界 | 能说清「什么时候不能用」 |

#### 模块 A　语言基础子集

| 知识点 | 优先级 | 深度 | 竞赛相关性 |
|--------|--------|------|-----------|
| 整型范围与溢出（`int` / `long long` / `unsigned`） | P0 | 熟练 | 溢出是最常见的隐性错误，`long long` 统计出现 85 次 |
| 运算符与优先级（尤其位运算与逻辑运算混用） | P0 | 熟练 | 优先级写错是典型 bug |

| 数组与多维数组（含数组开大小的经验公式） | P0 | 熟练 | 数组开小是 RE 首因 |
| 函数与参数传递（值传递 / 引用传递 / 数组传参） | P0 | 熟练 | 引用传参可避免大结构体拷贝 |

## 二、整体内容框架

### 2.1 五阶段学习顺序

按学习先后顺序排列，后一阶段依赖前一阶段。

```text
阶段 1　语言基础子集与输入输出
        ├─ 模块 A 语言基础子集
        └─ 模块 B 输入输出与性能
        目标：能写出正确、读入不超时的代码
        验收：独立完成 5 道纯模拟题，全部通过且无 IO 超时

阶段 2　STL 容器
        └─ 模块 C STL 容器
        目标：知道每种容器在什么场景用，能默写常用操作
        验收：见到题目能立刻说出该用哪个容器及理由

阶段 3　STL 算法
        └─ 模块 D STL 算法
        目标：能用现成算法替代手写循环
        验收：能不用手写循环完成排序、查找、去重、统计

阶段 4　现代语法糖
        └─ 模块 E 现代语法糖
        目标：编码速度提升，代码长度下降
        验收：同一道题的代码长度与出错率明显下降

阶段 5　竞赛工程化
        └─ 模块 F 竞赛工程化与技巧
        目标：具备自查与排查能力
        验收：能对一个错误程序完成对拍并定位错误
```

> **【要点】** 阶段 1 与阶段 2 可以并行推进，但阶段 1 的模块 B（输入输出与性能）**必须先于一切**。
> 理由见 0.3 节：它不提升算法能力，却是当前已有代码的失分点。

### 2.2 与算法集训知识体系的衔接

C++ 阶段与已有 `03_算法集训` 的八阶段不是替代关系，而是**并行支撑**：

| C++ 阶段 | 支撑的算法阶段 | 衔接点 |
|---------|--------------|--------|
| 阶段 1 | 阶段 0 至 1 | IO 优化是全流程前置；数组开大小在网格题中立即用到 |
| 阶段 2 | 阶段 3 至 5 | `set` / `map` 支撑去重与映射；`priority_queue` 支撑 Dijkstra 与贪心 |
| 阶段 3 | 阶段 1、5、8 | `lower_bound` 支撑二分；`unique` 支撑离散化；`sort` 支撑 Kruskal |
| 阶段 4 | 阶段 7、8 | 结构化绑定支撑图论与线段树；lambda 支撑区间排序 |
| 阶段 5 | 全阶段 | 对拍是验证所有算法的通用手段 |

### 2.3 每篇笔记的内容结构

沿用上一轮已确定的笔记模块结构，五段固定：

```text
一、本章速览        知识点表（序 / 知识点 / 等级 / 掌握 / 前置）
二、前置检查        进入本章前必须会的内容（可勾选）
三、知识点逐讲      每点：是什么 / 为什么 / 怎么用 / 常见误区 / 关联
四、典型例题与自测  含思路、过程、复杂度、易错提示
五、本章总结        核心内容（一页纸）+ 知识点串联图 + 自测清单
```

C++ 笔记的**特殊要求**（区别于算法笔记）：

- 每个知识点必须给出**可直接复制的代码片段**，且片段必须能独立编译。
- 必须标注**该知识点在什么数据量下才必要**（例如「`ios::sync_with_stdio` 在 n 超过 10⁵ 时必要」）。
- 必须给出**反例**：什么写法是错的、为什么错、会出什么结果（TLE / RE / WA）。
- 涉及性能的知识点必须给出**量级对比**（例如 `endl` 与 `\n` 在 10⁶ 次输出下的实测差距）。

### 3.2 标题层级规定

Notion 导入 Markdown 时，超过四级的标题会被压平或显示异常。因此**全库标题层级硬性限制为四级**：

| 层级 | Notion Block | 用法 | 示例 |
|------|-------------|------|------|
| 一级 `#` | Page Title（或 H1） | **每个文件只用一次**，作为页面标题 | `阶段 1 语言基础与输入输出` |
| 二级 `##` | H2 | 模块级 | `模块 B 输入输出与性能` |
| 三级 `###` | H3 | 知识点级 | `B-2 同步关闭与 tie` |
| 四级 `####` | H4 | 知识点内的固定小节 | `是什么` / `为什么` / `怎么用` |

> **【注意】** 禁止出现五级及以深的标题。若确实需要更细的层次，改用**加粗行**或**有序列表**表达，不使用标题。

### 3.4 Notion 特有的注意事项

| 事项 | 说明 |
|------|------|
| **不支持 `[[双链]]`** | Markdown 里的 `[[ ]]` 会变成纯文本。Notion 的关联要用 `@` 提及或 Relation 属性 |

| **数学公式可用** | 支持 `$...$` 与 `$$...$$`，但要确认导入时未被转义 |

### 4.2.1 与常规 C++ 的隔离方式

| 隔离维度 | 做法 |
|---------|------|
| 目录 | 竞赛 C++ 在 `02_竞赛\02_竞赛C++\`；常规课程在 `03_常规课程\`。两者不在同一父目录 |
| 内容 | 工程向知识点（类与继承、智能指针、协程、Modules、filesystem 等）一律不写入竞赛侧，清单见 `21_笔记分类体系.md` 4.2 表 |

> **【硬规则】** 竞赛侧笔记中不得出现「完整语法讲解」形态的段落。
> 若某段内容在常规课程中已有完整讲解，此处只保留赛场相关的部分与一行链接。

### 4.3 双链的设计方式

Obsidian 的双链是它相对 Notion 的**唯一结构性优势**，必须用足。

**链接粒度选择**：C++ 知识点颗粒度小，若一个知识点一篇笔记，会产生大量两百字的碎片。因此采用**章级文件加标题锚点**：

```markdown
学习 `[[C_STL容器#C-3 set 与 multiset]]` 之后，再回头看
`[[C_STL容器#C-2 map 与 unordered_map]]`，会发现两者的差异只在是否有序。
```

**双链的三种用法**：

| 用法 | 写法 | 作用 |
|------|------|------|
| 前置链接 | `前置：[[A_语言基础子集#A-1 整型范围与溢出]]` | 定位必需的前导知识 |
| 后续链接 | `后续：[[D_STL算法#D-3 unique 与 erase 去重]]` | 指出深化方向 |
| 对比链接 | `对比：[[E_现代语法糖#E-5 结构化绑定]]` | 建立并列关系 |

**自动反向链接**：只要在笔记 A 里写了 `[[B#标题]]`，Obsidian 的「反向链接」面板会在 B 中自动显示「被 A 引用」。**这就是双向关联，不需要手工回填**——这是 Obsidian 相对手工维护关联表的根本优势。

**Graph View 的用法**：把所有内容笔记加入图谱，可以直观看到哪些知识点是枢纽（被引用多）、哪些是孤岛（无任何链接）。**孤岛即断链，是需要立即处理的问题。**

### 4.4 标签体系

标签在 Obsidian 里承担 Notion 数据库中 Select 属性的职能：

```text
#cpp/阶段1  #cpp/阶段2  #cpp/阶段3  #cpp/阶段4  #cpp/阶段5
#cpp/模块A  #cpp/模块B  #cpp/模块C  #cpp/模块D  #cpp/模块E  #cpp/模块F
#cpp/P0  #cpp/P1  #cpp/P2
#cpp/状态-未学  #cpp/状态-学过  #cpp/状态-会做  #cpp/状态-易错  #cpp/状态-掌握
#cpp/类型-模板  #cpp/类型-易错  #cpp/类型-类比
```

**标签命名规范**：一律使用「前缀 / 层级」的两段式，不用中文空格。
理由：中文空格会让标签在搜索面板中被拆开，无法按层级折叠。

### 4.5 可选增强：Dataview 与 CSS

| **CSS Snippets** | 实现上一轮的配色方案 | 已有 `53_笔记配色样式.css` 可直接用 |

## 六、跨平台兼容性处理

### 6.1 单一真源原则

**Markdown 文件是唯一真源，Notion 只做展示层。**

| 平台 | 角色 | 数据流向 |
|------|------|---------|
| 本地 Markdown（Obsidian 库） | **真源** | 一切修改在此发生 |
| Notion | 展示与数据库视图 | 从真源单向导入 |
| GitHub / 其他 | 备份与分享 | 从真源单向同步 |

**禁止在 Notion 上直接编辑内容**。一旦双向编辑，两边会分叉，合并成本远高于收益。

### 6.2 语法兼容性对照与降级方案

| 语法 | Obsidian | Notion | GitHub | 通用 Markdown | 处理方案 |
|------|---------|--------|--------|--------------|---------|
| 标题 `#` 至 `####` | 支持 | 支持 | 支持 | 支持 | 直接使用 |
| 加粗、斜体 | 支持 | 支持 | 支持 | 支持 | 直接使用 |
| 表格 | 支持 | 支持 | 支持 | 支持 | 直接使用，限 5 列 |
| 任务列表 `- [ ]` | 支持 | 支持 | 支持 | 支持 | 直接使用 |
| 围栏代码块加 `cpp` | 支持 | 支持 | 支持 | 支持 | 直接使用 |
| 数学公式 `$...$` | 支持 | 支持 | 支持 | 部分支持 | 直接使用，复杂公式附文本说明 |
| 引用块 `>` | 支持 | 支持 | 支持 | 支持 | **承载语义标签的唯一载体** |
| `[[双链]]` | 支持 | **不支持** | 不支持 | 不支持 | **改用 `路径/文件.md#标题` 文本链接**；迁移时用脚本还原 |
| Callout `> [!note]` | 支持 | 降级为引用块 | 降级为引用块 | 降级为引用块 | **可选使用**，降级后仍有 `【标签】` 文字可读 |
| HTML `<span class>` | 支持 | **不支持**，会显示为文本 | 部分支持 | 部分支持 | **迁移前必须剥离** |
| `==高亮==` | 支持 | 不支持 | 部分支持 | 不支持 | **一律改用加粗** |
| 嵌入 `![[file]]` | 支持 | 不支持 | 不支持 | 不支持 | 不使用，改用普通链接 |
| 注释 `%%...%%` | 支持 | 不支持 | 不支持 | 不支持 | 不使用 |
| Dataview 查询块 | 支持 | 不支持 | 不支持 | 不支持 | **作为附加视图**，不得承载独有信息 |

### 6.3 三条降级路径

**路径一：Markdown 到 Notion（导入）**

1. 运行剥离脚本，去掉 HTML `span`、把 `[[X#Y]]` 转为 `X#Y` 纯文本。
2. Notion 中选「导入 → Markdown 与 CSV」，逐个文件导入到对应子页面。
3. 导入后手工补三项：数据库的 Relation 属性、Callout（可选）、公式检查。

**路径二：Notion 到 Markdown（导出）**

1. Notion 中导出为「Markdown 与 CSV」。
2. 导出的文件会带 UUID 后缀，用脚本批量清理文件名。
3. 数据库导出的 CSV 需要转成 Markdown 表格。

> **【注意】** Notion 导出的 Markdown 表格格式常不标准，需要人工校对。

**路径三：Markdown 到通用平台（发布）**

只使用第一层与第二层语法即可，无需任何处理。这正是分层设计的收益。

### 6.4 迁移前检查清单

每次迁移前逐项核对：

- [ ] 无 emoji 与装饰性图形字符
- [ ] 无 HTML 标签（`<span>`、`<br>`、`<details>` 等）
- [ ] 无 `==高亮==`
- [ ] 无 `%%注释%%`
- [ ] `[[双链]]` 已转为文本链接或已确认目标平台支持
- [ ] 无五级及以深标题
- [ ] 表格列数不超过 6
- [ ] 代码块语言标注统一为 `cpp`（纯文本与树状图写 `text`）
- [ ] 数学公式未被转义（`$` 与 `_` 前后无多余反斜杠）
- [ ] 文件名无非法字符
- [ ] 折叠内容在目标平台可展开，或已改为普通段落

配套的 `52_检查_跨平台兼容.py` 可自动完成以上全部检查：

```bash
python 52_检查_跨平台兼容.py <笔记目录>              # 检查并列出问题
python 52_检查_跨平台兼容.py <笔记目录> --quiet      # 只看汇总
python 52_检查_跨平台兼容.py <笔记目录> --fix-copy   # 额外生成剥离平台专属语法的副本
```

> **【注意】** 若某个文档本身就在**讲解这些语法**（例如本方案自身），
> 可在文件顶部加 `<!-- compat-ignore-file -->` 整文件跳过检查；
> 单行可用 `<!-- compat-ignore -->` 跳过。实际内容笔记不应添加该标记。
>
> **实测结论**：本方案配套的 6 个文件经该脚本检查，问题总数为 **0**，可直接迁移。

### 6.5 迁移风险的兜底

| 风险 | 兜底措施 |
|------|---------|
| 平台语法变更导致渲染异常 | 第一层语法是各平台长期稳定的最小交集，风险最低 |
| Notion 导入破坏表格 | 保留本地 Markdown 真源，Notion 坏了就重导 |
| 双链在 Obsidian 之外失效 | 双链旁始终保留可读的文本说明，不依赖链接传达信息 |
| 公式渲染差异 | 复杂公式附「文字描述」与「代入示例」两行 |
| 平台弃用 | 纯 Markdown 文件可被任何编辑器打开，不会因平台消失而丢失 |

## 八、结论

1. **范围上做减法**。现有 475 个 C++ 文件里不到 15% 与竞赛相关。智能指针、协程、Modules、filesystem、多线程、网络全部划出。
2. **顺序上把输入输出提前**。实测发现 `ios::sync_with_stdio` 全库只用 1 次，而 `cin` 用了 114 次，且存在 n 达 3×10⁶ 却未优化的实例。这是**已经在丢分**的点。
3. **补齐两块空白**。关联容器（`set` 零使用、`map` 各 1 次）与 STL 算法（`unique`、`reverse`、`lower_bound` 几乎为零），以及现代语法糖（`auto`、lambda、结构化绑定全为零）。
4. **兼容性靠分层，不靠适配**。信息全部落在通用核心层，平台专属语法作为可剥离的增强层，降级后不失真。
5. **Notion 与 Obsidian 各取所长**。Notion 用数据库做筛选与调度，Obsidian 用双链做关联与图谱，两者通过「本地 Markdown 为唯一真源」统一。
6. **每处设计都要有依据**。本方案的每一条取舍都对应一条实测数据或竞赛场景，不凭经验编排。
